The Ravel book

Run sessions

A caller starts a session, gives its instructions and interprets its result. The owner policy chooses the program. Ravel supervises that managed process and returns an opaque result only after it confirms the cleanup. This chapter shows how to give a request and how to run nested or confined sessions. It also shows how to identify each outcome that a caller can see.

Follow chapter 3 to install Ravel and check its version. These examples use real policy evaluation and small local programs. They do not need an agent account or a model service. If you came here for an exit code, go to the status table. It gives each normal status of the CLI and the three cancellation signals that Ravel handles, with an action for each.

Supply the prompt and caller data

Pass exactly one of --prompt TEXT and --prompt-file PATH. Ravel gives the text to the policy unchanged, also when it is an empty string or ends with newlines. Ravel adds no instructions to end the session. It never reads a prompt from terminal stdin. A prompt is UTF-8, contains no NUL and has a maximum size of 1 MiB. Ravel does not truncate input that is not valid, but stops the invocation with status 2.

The argument limits of the operating system can be smaller than 1 MiB. These limits also apply when the policy puts a prompt from a file into the arguments of the selected program.

Use a file when the exact text is important. Shell command substitution removes trailing newlines. Thus, --prompt "$(cat prompt.txt)" can change the text before Ravel receives it. --prompt-file prompt.txt reads the file directly, relative to the caller’s working directory. Ravel changes no text before the policy receives it. Then the policy makes the arguments of the selected command and decides how to give the prompt to that program.

The kind is a required caller token that is not empty. Ravel has no catalogue of kinds and does not get a kind from a file name. A policy can route review, refuse it or treat it as any other kind. The caller and the policy author agree on these tokens.

These inputs give data to the policy. They do not tell Ravel to read a task or to give the task a meaning:

InputWhat the policy receives
--param profile=carefulrequest.params.profile with the string careful. Each name is not empty, contains no = and occurs one time. The value can be empty or contain more = characters. The limit for all names and values together is 65,536 UTF-8 bytes.
--task-file tasks/check.mdAn absolute UTF-8 request.taskFile. Ravel makes it from the given path and the caller’s working directory. Ravel does not read that file, and the file does not have to exist. Ravel gets no kind or identity from it.
--task-id example-17An opaque request.taskId. It is UTF-8, is not empty and has a maximum of 1,024 bytes. Ravel does not search for a stored task.
--context caller-context.jsonA version-1 JSON document that Ravel measures and validates. If the policy has no loader, the document becomes the second argument to select. A loader can make a different document for the policy.

That last document is policy context, which is data that the policy uses to choose the route. It is different from the working directory of the request, cwd. It is also different from the session-result context, which later lets the managed process send a result. Chapter 4 teaches policy context and loaders and bounds and environment grants. The --timeout-ms bound applies to policy evaluation, not to the time that the managed process works.

The selected program runs in the caller’s working directory. The form of its program path sets the base that Ravel uses to find the program:

Selected programResolution base
Absolute pathThe path itself
Relative path that contains /The caller’s working directory
Bare program nameThe caller’s PATH

Ravel gives the argument strings directly to the program, without shell word splitting or expansion. An unconfined managed process inherits the caller’s environment, with two changes. Ravel removes RAVEL_RUN_ID, RAVEL_STATE_DIR, HARNESS_DISPATCH_EXIT_FILE, HARNESS_DISPATCH_RUN_ID and HARNESS_DISPATCH_STATE_DIR, and it replaces RAVEL_EXIT_FILE for the new session. Put the installed ravel on the PATH of the managed process. As an alternative, write the absolute path of ravel in the prompt’s instructions to end the session. A confined managed process gets a smaller environment, which Confine the managed process describes.

Complete example: pass a prompt from a file, with its final newline, and caller data. The policy uses profile as an argument. It does not use the task fields or the policy context. The fake agent sends the prompt itself as the result, so the result shows what the agent received. Create the labelled files in a new directory. Make bin/echo-prompt executable before you run the command.

import { definePolicy } from "ravel/sdk";

export const policy = definePolicy({
  schemaVersion: 2,
  version: "prompt-demo",
  select(request) {
    return {
      status: "selected",
      program: "echo-prompt",
      args: [request.prompt, request.params.profile ?? "default"],
      provider: "local",
      model: "fake",
      effort: "none",
      reason: "Show the caller's prompt unchanged",
    };
  },
});

Accept a result only after success

Keep the result bytes and the status of start-session together. Status 0 means that all of these conditions are true:

  • A program in the session sent a valid result.
  • Ravel reaped the direct child.
  • Ravel confirmed that the process group of the managed process is gone.
  • The required cleanup succeeded.
  • The final write and flush of the result succeeded.

An empty sent result is a successful result with zero bytes. If a managed process exits with status 0 and sends no result, the status is 1. Ravel then returns no result to the caller. But if a program sends a result and the child then exits with a nonzero status, start-session can still give status 0. Ravel’s status shows whether Ravel delivered a sent result after cleanup. It does not show whether the work in the prompt was correct.

end-session takes one UTF-8 argument with a maximum size of 1 MiB. Quote it, and put -- before a value that looks like an option, such as --help. Ravel writes an empty, multiline or Unicode value unchanged to standard output and does not interpret it. The operating system can apply a smaller limit for command arguments before end-session starts.

Ravel keeps the first complete result that it receives through the result channel. When that first result arrives, Ravel starts to stop the harness. Thus, a second end-session call and the shutdown are in a race: either can occur first. For example, another process in the group can send a result before Ravel stops that process. Ravel keeps the first result, even if the second command succeeds.

Complete example: compare three outcomes. In the first, the program sends a result and then tries a second call before it exits with status 7. The shutdown can stop the program before that call or that exit. In the second, the program sends an empty result. In the third, it sends no result and exits naturally with status 0. This chapter writes INT, TERM, HUP and KILL without the SIG prefix. Other signal names keep that prefix. Code and diagnostic text keep their literal names.

end-session returns before the enclosing session finishes its cleanup. When Ravel detects the sent result, a job that still runs gets 2 seconds to finish. Then Ravel sends TERM, waits for up to 5 more seconds and sends KILL if necessary. These waits end early if the direct child exits. Ravel then stops the other group members before it reaps the child. Those members do not get a new 2-second wait.

Send the result after the work that has to finish, because Ravel can stop code that comes after end-session.

For an automated caller that needs trailing newlines intact, redirect stdout to a file. Read the file only after you check the status. Shell command substitution removes trailing newlines. Use it only when the caller’s result convention accepts this change. A failed final write can leave only the first part of the result in the file, so the bytes alone do not prove success. Ravel has no persistent store for results, so it cannot recover a result after a failed delivery.

Fragment: capture the unchanged result and the status. This fragment omits the policy, the prompt file and how the caller handles each successful value or failure.

if ravel start-session --kind review --config policy.ts --prompt-file prompt.txt >result.txt; then
  status=0
else
  status=$?
fi

Keep nested sessions separate

A managed process can be the caller of another start-session. The inner session allocates its own result channel. It replaces RAVEL_EXIT_FILE only for its own managed process. The outer process keeps the value of its enclosing session. When the inner invocation returns, the outer process decides what to send for the outer session. When the inner process sends its result, the outer session does not finish, and end-session accepts no session ID or target argument.

Each process uses the session-result context that it inherited to send a result. Ravel does not change the inner result into an outer result. The outer process does this itself:

ProcessSession-result contextWhat its end-session call sends
Outer managed process, also the inner callerKeeps the RAVEL_EXIT_FILE of the outer sessionThe result of the outer session
Inner managed processGets a new inner RAVEL_EXIT_FILEThe result of the inner session. Ravel returns it to the outer process after the inner cleanup.

Complete example: the inner program sends inner, and the outer program uses that result in inner|outer. Create these files in a new directory and make both files under bin/ executable. These values have no trailing newlines, so command substitution keeps them unchanged.

policy.ts

import { definePolicy } from "ravel/sdk";

export const policy = definePolicy({
  schemaVersion: 2,
  version: "nested-demo",
  select(request) {
    return {
      status: "selected",
      program: request.kind === "outer" ? "outer" : "inner",
      args: [`${request.cwd}/policy.ts`],
      provider: "local",
      model: "fake",
      effort: "none",
      reason: "Give each nested session its own result",
    };
  },
});

Each layer’s Ravel CLI supervises only the group of its own managed process, and it does the cleanup only for that group. Thus, if an inner Ravel CLI dies before it completes its cleanup, the group of its managed process can remain. The outer Ravel CLI does not stop that group. The operational limits apply at each layer. The example checks that the results stay separate. It does not check interactive job control for nested sessions.

Confine the managed process

Confinement restricts the filesystem access and the environment of the managed process. Add --confine when you want that restriction. The owner policy and its policy worker stay outside the confinement. Policy is trusted executable configuration.

On macOS, Ravel uses /usr/bin/sandbox-exec. On Linux, it uses the system bubblewrap executable, /usr/bin/bwrap or /bin/bwrap. Before Ravel evaluates the policy, it tests whether the backend can make a sandbox. If the backend is not available or not usable, the invocation stops with confinement_unusable and status 2. Ravel does not then launch the process without confinement.

These paths have different grants for the confined managed process:

PathAccessHow the process gets access
Canonical working directory and private run directoryRead and writeRavel grants them for each confined launch.
System runtime paths, selected executable and real executable file of the Ravel CLIRead-onlyRavel grants them for each confined launch.
One additional regular file that existsRead-only--runtime-read FILE. Repeat it for each file. It requires --confine and grants no directory tree.
Parent of the result directoryRead and write--exit-dir DIR. The directory must exist and be writable.

If the managed process needs a full directory, copy the task data into the working directory. A read-only runtime grant stays read-only, even inside a writable directory. Confinement permits network access. It is not an offline mode.

--exit-dir DIR puts the private result directory of the session in a writable directory that exists. It works with or without confinement. With confinement, it also gives write access to that parent directory. Thus, do not choose a parent directory that contains files that the managed process must not change. Without the option, an unconfined session uses the system temporary directory. A confined session puts the result channel in its private run directory.

Keep the policy directory and the owner settings outside every filesystem grant. Ravel makes each path canonical. If paths overlap, Ravel stops with an error before it evaluates the policy. This check also finds overlaps through symlinks or through the system runtime grants. For example, if you run --confine --config ./policy.ts from the directory that contains that policy, the policy overlaps the writable working directory. Put the policy in a separate owner directory, and invoke Ravel from the project directory.

confinement_overlap reports the paths that overlap. confinement_unusable reports a resource or a backend that Ravel cannot use. Both use status 2. Before selection, an --exit-dir that is not valid can also give exit_dir_unusable. Later failures of allocation or cleanup have their own diagnostics.

The confined environment keeps HOME, USER, LOGNAME, PATH, LANG and LC_*. Ravel sets TMPDIR, TMP and TEMP to the private run directory and gives the managed process a new RAVEL_EXIT_FILE. The HOME variable does not give access to the directory that it names. The other caller variables are not in the environment. This also applies to --policy-env. It grants a variable to the policy worker, not to this managed process.

A confined launch starts a new POSIX session and is not interactive. Ravel does not lend it the caller’s controlling terminal. An unconfined launch uses a new process group in the caller’s POSIX session. Ravel lends it the terminal if Ravel’s own process group is the foreground group of the terminal. This difference is important for an interactive program. Chapter 9, “Jobs, signals and the terminal”, teaches the mechanism.

Confinement is separate from the permission flags of an agent program. Neither the unconfined mode nor the confined mode confines the owner policy. Use this comparison to choose confinement together with its effects on the environment and the terminal:

Read notices separately from results

For start-session, stdout contains only the result. Ravel writes the result unchanged, with no added newline, and does not interpret it. The stdout of the managed process goes to the caller’s stderr, together with its stderr, Ravel’s diagnostics and the routing notice. In text form, the routing notice is one line that Ravel writes before the launch. The line starts with ravel: starting provider and gives the selected provider, model, effort and kind. These labels are owner text, not integrations with model providers.

--json changes the routing notice and the failure document of Ravel into JSON on stderr. It does not change the result into JSON, and it does not change other stderr output. The managed process can still write any text there. Keep stderr as a diagnostic stream, and do not parse the full stream as one JSON document. The managed process can write a line that looks like a Ravel notice. Thus, the form of a line does not prove that Ravel wrote it.

Read stdout only as the result of a successful session. Keep stderr as a mixed diagnostic stream, even with --json:

OutputDestinationEffect of --json
Unchanged opaque result after a successful sessionCaller stdout, with no added newlineNone
Stdout and stderr of the managed processCaller stderrNone. Any program text stays.
Routing notice and failure document of RavelCaller stderrJSON documents replace their text form

The version-1 routing notice gives selection, policy, worker, selectionMs, the delivered context, the effective bounds, policyEnvironment, resolution, promptSource and the captured policy diagnostics. The field context is policy context, not the result channel. Grant diagnostics show the name of each environment variable and whether it is set. They never show its value. Policy code can still write values itself. Thus, keep its diagnostics with the care that those values need.

Ravel writes this JSON notice after the supervision attempt and before it decides the final outcome. If the runner completed supervision and returned its record of how the job ended, operationReports holds the operational reports that the runner kept. The array is empty if there are no reports. If supervision failed before the runner returned that record, the notice has no such field.

Some reports, such as a failed stop attempt, stay visible even when later checks confirm successful cleanup. A report alone does not decide success, and the routing notice also does not. Check the final status.

A JSON failure has schemaVersion: 1 and an error object with code, stage, message, remedy and exit. It adds the fields that apply, such as input, source, location, policyCode, bound and signal, and the captured policy diagnostics when they are available. Read the code and the stage together. These examples distinguish a policy decision from failures before and after launch:

CodeStageMeaning
policy_refusedselectionThe owner policy declined the request.
worker_identity_mismatchworkerThe policy worker does not match the Ravel CLI. Ravel stops before policy evaluation.
session_result_missingexecThe managed process ended without a sent result.

The text form of each failure starts with ravel: refused, also when no policy refused the request. The code and the status show the difference between a policy refusal and an operational failure.

If later cleanup also fails, an original failure keeps its code and status. Ravel reports the cleanup problems together with the original failure. Cancellation has precedence over both. Ravel then sets the cancellation status, keeps the original and cleanup diagnostics and returns no result to the caller. If required cleanup fails, Ravel also returns no result to the caller, even when everything else succeeds. Thus, keep the complete stderr stream, even after the caller classifies the exit status.

A caller checks the status of start-session. It does not use the status of the managed process or the earlier status of end-session. For a session result, accept stdout only with status 0 from start-session. A help or version request is a separate invocation for information, and it sends no result.

The last three numbers follow the shell convention: 128 plus the signal number. Ravel reports the cancellation, attempts the cleanup and then raises the signal again. Thus, a process API reports termination by that signal, not a numeric exit. If the propagation of the signal fails, Ravel reports that failure and exits with the same number as a fallback. A caller that uses a process API handles both forms.

A signal such as KILL can stop the Ravel CLI at any point. The normal procedure of Ravel does not apply to such a signal. Then the shell status does not show that cleanup or result delivery occurred. Also, a new signal that arrives after the final cancellation decision can interrupt the result write. No atomic guarantee covers both the arrival of a signal and an arbitrary write to stdout.

The following view expands one step of chapter 3’s outcome state machine: the step where Ravel decides the final outcome. Cancellation wins over an original failure. An original failure keeps its status if later cleanup also fails. Only a valid result with confirmed cleanup gets to the final write. The view shows the precedence of outcomes, not the order of function calls. Ravel attempts the applicable cleanup before it reports an outcome.

Cancel during selection or supervision

A cancellation during selection stops the policy worker and prevents the managed launch. Ravel attempts the worker teardown and reports the cancellation with any teardown problems. The worker has no session-result context. Thus, it cannot send a result for an enclosing session through the usual end-session interface.

The selection sequence shows why a cancellation can need worker cleanup, although Ravel launched no managed process. It follows the example below, where the worker sends INT directly to the Ravel CLI.

In these UML sequences, no lifetime ends with an X. Ravel attempts cleanup, and a failed attempt does not confirm a reap or a removal.

Open the selection cancellation sequence at full size.

Complete example: the policy sends INT directly to its parent, the Ravel CLI. Then it waits indefinitely. This example causes a cancellation during selection without a terminal or a managed process. Create the policy in a new directory.

import { definePolicy } from "ravel/sdk";

export const policy = definePolicy({
  schemaVersion: 2,
  version: "cancel-selection",
  async select() {
    process.kill(process.ppid, "SIGINT");
    return await new Promise<never>(() => {});
  },
});

During supervision, a cancellation stops the group of the managed process. Ravel attempts the reap, the terminal recovery and the temporary cleanup before it reports the signal. Ravel returns no result to the caller, even when it already received a result. A cleanup failure does not change the cancellation into success. Ravel reports the failure together with the cancellation.

The supervision sequence shows why a cancellation returns no result to the caller, even after the managed process sent a result. The result reaches the temporary result channel, but Ravel does not write it to stdout. The runner runs inside the Ravel CLI. The group of the managed process includes the descendants that stay in that group. The cleanup steps in the figure are attempts, and Ravel keeps their failures as diagnostics.

A signal that you send to the Ravel CLI is different from Ctrl-C at the terminal. After Ravel lends the terminal, the group of the managed process is the foreground group of the terminal. Ctrl-C then makes the terminal send INT to that group, not to the Ravel CLI. If only that group receives INT and exits with no sent result, the Ravel CLI reports session_result_missing with status 1. It does not report cancellation with status 130.

An interactive program can also handle or ignore the keyboard signal itself. Use the status and the diagnostic of the Ravel CLI. Do not infer the outcome from the key that you pressed. Chapter 9 explains signal inheritance and terminal recovery.

Understand the operational limits

Ravel’s cleanup guarantee does not apply under the conditions in this table. Use the table to decide what an unsuccessful invocation can leave for the caller to examine:

ConditionConsequence
Code that runs as the same user makes unauthorised changes to the result channel or the installation.Private paths and the inherited session-result context keep ordinary sessions apart. They are not a defence against hostile code of the same user. The worker identity check confirms that the policy worker matches the build of the Ravel CLI. It does not check a trusted signature.
The Ravel CLI dies abruptly, for example from KILL.It cannot complete supervision or cleanup. The group of the managed process and the temporary directories can remain. There is no successful completion and no persistent recovery record.
A managed descendant deliberately leaves its process group.It is outside the cleanup guarantee of that group. The absence of the group does not prove that the detached process is gone.
Trusted owner policy starts a detached child.Worker teardown does not guarantee the cleanup of that child. The confinement of the managed process does not contain policy code.
Another process changes the foreground group of the terminal during recovery, or the system gives a recorded group ID to an unrelated group.Recovery assumes two conditions between the runner’s check and its handback. No other process or thread changes the foreground group. No unrelated group gets the recorded group ID. Ravel reports a failed handback. Do not treat a launch failure as proof that Ravel restored the terminal. Chapter 9 explains the conditions.
The host is different from the measured platforms.The project measured how Ravel handles inherited signal settings, cancellation, cleanup and terminal recovery. It measured them on aarch64 macOS and aarch64 GNU/Linux. The project built Ravel for x86_64 GNU/Linux and ran it only under emulation. Native x86-64 qualification is not complete. These checks do not cover all combinations of kernel, libc and compiler.

Chapter 2 explains these trust limits. Ravel issue 1 tracks the native x86-64 qualification. The examples in this chapter check the choice of command, the delivery of the result and the status. They do not show the behaviour of real agents, interactive terminal operation or whether a new reader can use the book. Chapter 6, “Reference”, gives the reference entries for the inputs and outputs that this chapter teaches.
