The Ravel book

What Ravel is for

Ravel runs LLM sessions in agent harnesses, such as Claude Code and Codex, as supervised parts of another program. A harness is the program in which an LLM works on a prompt. It gives the prompt to the LLM and runs the commands that the LLM requests, for example shell commands. The person who configures Ravel chooses which harness runs each request. Ravel starts that harness and supervises it. After cleanup succeeds, Ravel returns the result that the session sent.

A harness such as Claude Code or Codex can run under the subscription of its user. Thus, a caller can use that subscription for LLM work instead of paid API access. The cost can be much lower for work that the subscription covers. The Claude Code documentation and Codex documentation explain their access options and link to their plans and terms. This paragraph agrees with those pages as they were on 18 October 2026.

An orchestrator is a program that runs LLM sessions as steps of its own work. It can request a session from Ravel and wait for its result. Then it uses that result to decide its next step.

For example, an orchestrator can ask an LLM to review a code change. The orchestrator knows the files to review and what to do with the answer. The person who operates the orchestrator wants to choose the harness for their account. Each participant has a different responsibility in that review:

ParticipantResponsibility in the review
OrchestratorChoose the work to review and interpret the result
Person who configures RavelChoose the harness command through their policy
RavelRun the selected command and supervise it until cleanup completes

An interactive harness waits for more input when the LLM completes its task. Ravel’s end-session command lets the LLM send a result and ask Ravel to stop the session. Thus, the orchestrator can continue after cleanup.

From a request to a result

The person or program that makes the request is the caller. The caller invokes ravel start-session with a prompt and a kind. A kind is a token that names the sort of work that the caller wants. In the review example above, the caller can use review as the kind. The caller and the owner policy agree on that token. Ravel has no built-in review category.

The owner controls the configuration of the account. Their owner policy is a configuration file with TypeScript code. Its default path is $HOME/.config/ravel/policy.ts. The policy receives the request. Then it selects a program and its arguments, or it refuses to launch a program.

The policy can use the kind to choose a harness and the arguments that set the model and the effort level of that harness. The provider, model and effort fields of a selection are labels for the notice that Ravel writes when the session starts. These labels do not configure the harness. The policy puts the actual options in the arguments of the command.

The caller can also use the kind to choose instructions for the prompt. If the harness supports skills, the prompt can tell the LLM which skill to load. A skill is a set of instructions for a particular task. This use of the kind is a caller convention. Ravel gives the prompt to the policy unchanged and adds no task instructions. The policy decides whether and how to include the prompt in the arguments of the selected command.

One start-session invocation is a session. During the session, Ravel supervises the program that the policy selected. This program is the managed process of the session. The harness runs the LLM session that works on the prompt. That LLM session is not the Ravel session. Ravel supervises the harness process, not the conversation of the LLM in that process.

The contract with the selected program is loose. The policy selects a program, Ravel runs it, and a program in the session sends one value with end-session. Ravel needs nothing more from the program. The selected program does not have to use an LLM or understand a prompt.

An interactive harness does not exit when its LLM completes the task. It waits for more input. Thus, the caller’s prompt tells the LLM to run ravel end-session RESULT when the task is complete. RESULT is a placeholder for the text to send. The caller’s prompt gives the permitted values and tells the LLM when to use each value.

For example, the caller can choose the text continue as a result value. The prompt can tell the LLM to run ravel end-session continue when the review is complete. The command sends that text to Ravel and asks Ravel to end the session. After successful supervision and cleanup, Ravel returns the text unchanged. The caller can interpret continue as permission to start its next task. Ravel gives continue no meaning and does not start a next task.

The book calls this text an opaque result, because Ravel does not interpret it. end-session finds the enclosing session through its inherited session-result context. It takes no session ID or target argument.

When end-session sends the result, it requests the end of the session. This request does not prove that cleanup succeeded. A process group is an operating-system unit that contains the managed process and its descendants. Ravel stops the harness and each other process that remains in that group. Then it completes the cleanup of the group.

To reap a child process, its parent collects the exit status of that child. Before Ravel returns a successful result, it confirms that the managed process ended and that Ravel reaped it. Ravel also confirms that the process group is gone and that it removed the temporary files of the session. Chapter 3, “A complete session, end to end”, explains these mechanics at the point where a session needs them.

After a successful session, Ravel writes the result unchanged to standard output. Ravel does not interpret the result and adds no newline. Ravel redirects the standard output of the managed process to standard error. Thus, the caller can keep the output of the managed process and the diagnostics of Ravel separate from the result stream.

The caller checks whether start-session succeeded before it interprets that stream. A failure during the write of the final result can leave only the start of the result on standard output. Thus, the output alone does not prove success.

Some outcomes return no result to the caller:

  • A refusal means that Ravel launches no program.
  • If the managed process exits and no program sent a result, the session has no result and fails. This is also true when the exit status is zero.
  • Cancellation of the session suppresses the result, even if a program sent the result before the cancellation.
  • A supervision failure or a cleanup failure also prevents success.

But a session with a sent result can succeed after cleanup, even if the managed process then exits with a nonzero status. The result is the value that the caller’s instructions to end the session asked for. The exit status tells how the process ended. The work is what the program changed. None of these three outputs can replace another.

The table keeps the three outputs separate. Thus, you do not confuse an exit status or a changed file with the result that the caller requested.

Decide whether Ravel fits

Ravel fits when your program needs to use an LLM session in an interactive harness as a step of its own work. Your program can let the owner policy of the account choose the harness. In each harness that the policy selects, the LLM uses the same command, end-session, to send the result. Ravel supervises the session and returns its explicit result after cleanup. Your program still owns the task and the decisions after the session ends.

The Ravel CLI, the ravel command-line program, is a launcher CLI. One invocation supervises one managed launch, reports its result or failure, and then exits. A persistent runner is a host that continues to run after a launch is complete. Ravel does not provide one. A program that exits after one session does not give what such a host needs.

Ravel has no persistent session store and no history lookup. Its result channel uses temporary files for one session. It is not a record of past work. If a caller needs a permanent record, that caller saves it. Owner policy is executable code and can itself use files or network services. Ravel has no store, but the absence of a store does not restrict what that trusted code can do.

Grove, a task-tree driver, is one illustrative caller. It is an orchestrator that runs LLM sessions in harnesses as steps of the work on its task tree. It supplies its own task kinds and interprets its own result values. These conventions belong to Grove. Another caller can use different kinds and results without a Ravel adapter.

The actors and their words

Each request has three decisions:

  • which work the caller wants
  • which program does the work
  • whether the session completed successfully

Ravel gives these decisions to different participants. If you know who makes each decision, you can change a rule in the owner policy without a change to the caller. You can also interpret the outcome of a session, and you do not confuse a policy response with a completed session.

Caller and owner

The caller is the person or program that invokes Ravel and interprets the result that Ravel returns. An orchestrator is one such caller. An orchestrator is a program that runs LLM sessions in harnesses as steps of its own work. The caller supplies the prompt, with the instructions to end the session. The caller also decides the next step after the session.

A session is one ravel start-session invocation. It starts with the request and ends when Ravel reports the result or the failure of the selected program. A Ravel session is not a POSIX session that setsid creates. It is also not a login session or the LLM session in a harness. Ravel supervises the harness process, not the conversation of the LLM.

The caller supplies a kind. A kind is an open token that names the sort of session that the caller wants. Ravel checks that the token is not empty and gives it no meaning. The policy code of the owner interprets it. For example, a caller can request review. But Ravel has no registry of task kinds and does not know what a review includes.

The owner is the person who controls the configuration of Ravel for the account. Their owner policy is executable TypeScript configuration. It selects a program and its arguments, or it refuses the request. The caller and the owner can be the same person, but their roles stay different. The choice of the work does not set the rules that select a command.

The table shows which decisions stay separate, even when one person has both roles.

By default, Ravel uses the account’s policy file, $HOME/.config/ravel/policy.ts. --config PATH names a different policy file. Ravel resolves that path relative to the working directory of the caller. Ravel does not search the repository of the caller for a policy.

A selection contains a program, arguments and descriptive labels in the provider, model and effort fields. These labels are text from the owner, not built-in model integrations. The policy selects the actual command that starts the chosen program. Ravel runs that command without shell expansion or word splitting. A shell runs only if the policy selects one.

The system-context figure in chapter 1 shows these roles around Ravel. An orchestrator can choose the work, and the owner chooses the harness. Ravel supervises that harness as the managed process.

Policy evaluation and supervision

The Ravel CLI is the ravel command-line program, written in Rust. During start-session, it keeps the environment, the terminal and the standard output of the caller. It evaluates the request and supervises the selected program. Its runner is the Rust library code that launches and supervises the managed process. The runner runs in the process of the Ravel CLI. It is not a separate service.

The policy worker is a separate process that evaluates the owner policy for the Ravel CLI. Its executable contains the Bun runtime. Thus, it can run TypeScript policy and the modules that the policy imports, without a separately installed runtime. Here, “worker” means a process. It is not a Bun Worker thread, which policy code can itself create.

This separation lets policy run ordinary TypeScript, while only the Ravel CLI supervises. Ravel gives the worker a request with a size limit and a restricted environment. The worker gets no session-result context. The Ravel CLI checks the response of the worker. Only the Ravel CLI supervises the managed process. Policy evaluation is complete before that process starts.

A refusal is a decision not to launch. The owner policy makes it, or Ravel makes it when it cannot accept the file, behaviour or data of the policy. Ravel does not try a different route. A failure of the worker, a failure of supervision and a selection timeout are different outcomes. A caller needs to tell a refusal from a failure during evaluation or supervision.

The managed process and its result

The managed process is the direct child that owner policy selects and that the Ravel CLI supervises. Cleanup applies to its full process group, with all descendants that stay in that group.

A harness is the agent program, such as Claude Code or Codex, in which an LLM session works on the prompt. The harness gives the prompt to the LLM and runs the commands that the LLM requests, for example shell commands. Owner policy selects the harness command. Here, “harness” means the agent program, not a test harness. Ravel supervises it as it supervises any other selected program.

The policy decides whether to pass the prompt to that program. Ravel does not require an LLM or a program that understands prompts. An ordinary program can take the place of the harness and send a value with end-session, as the examples do.

An interactive harness waits for more input when the LLM completes its task. Thus, the caller’s instructions to end the session tell the LLM to run ravel end-session. This command sends a result. Then Ravel stops all processes that still run in the process group of the managed process. Ravel completes the cleanup before it returns the result.

The opaque result is text that a program in the session sends as one UTF-8 argument with ravel end-session. In the prompt’s instructions to end the session, the caller gives the permitted values and tells when to use each value. For example, the caller can choose continue to mean that it can start its next task. Ravel gives this text no meaning. After successful supervision and cleanup, Ravel returns the text unchanged. Then the caller decides its next step.

The result is separate from the exit status of the managed process. It is also separate from the files or other work that the program produced. A program can send an empty result. If no program sends a result, the session has no result, even when the managed process exits with status zero.

The result channel is the private temporary directory and completion file through which end-session sends that value. Ravel keeps the first complete result that it receives. That first end-session requests shutdown, which normally ends the harness. A second end-session races that shutdown. For example, another process in the group can send a result before Ravel stops it. Ravel keeps the first result, even if the second command succeeds.

Three different kinds of information

The word “context” can mean three different inputs. The book names each one. Thus, you do not confuse request data with permission to end a session.

The session-result context is the inherited RAVEL_EXIT_FILE path. It identifies the result channel of the enclosing session. end-session uses that path. It reads no policy or settings and accepts no target argument. It fails if the path is missing, empty or stale, that is, from a session that already ended. Ravel has no persistent session lookup that it can use in place of that path.

In a nested launch, the outer managed process invokes a new start-session as a caller. Ravel gives a new path to the inner managed process. This path replaces the outer path only in the environment of that child. The outer managed process keeps its own session-result context. Thus, with normal inheritance, each end-session goes to its enclosing session, not to a session that an ID selects.

The policy context is version-1 JSON data that the select function of the policy receives. It comes from the caller or from the optional policy-context loader of the policy. It can describe the work and the sources that inform a choice. Ravel measures each read through the host operations that it provides. For each source, it records the canonical name, the byte count and the SHA-256 digest of the bytes that it read.

Policy code can also read data directly, but Ravel does not measure these reads. Policy context is data for selection. It gives no permission to send a result, and it does not prove that the data is trustworthy.

The working directory of the caller is the cwd of the request. It tells the policy where the caller works. It is not one of the two forms of context above. The selected program starts in the working directory of the caller. A policy author uses the cwd of the request when the location of the caller is important. The author does not assume that the current directory of the worker is the same.

The Ravel CLI creates the private directory of the worker, which is empty, and starts the worker there. The worker changes to / before it registers its embedded modules or imports owner policy. Policy code can then change the working directory of the worker again. During worker cleanup, before it launches the selected program, the Ravel CLI removes the private directory of the worker.

Trust and confinement

Owner policy is trusted executable code. The worker is separate and gets restricted inputs. Thus, policy has no part in the normal paths of supervision and of the result. But this separation does not make arbitrary owner code safe. Policy can access files or the network and can start unrelated processes. Its detached children are outside the cleanup guarantee of the worker.

Confinement is the optional restriction of the filesystem access and the environment of the managed process. It is separate from owner policy. Owner policy selects a command, and confinement restricts the access of that command. --confine applies to the managed process, not to the policy worker. If the request asks for confinement and Ravel cannot provide it, Ravel does not launch the process unconfined.

The inherited session-result context keeps nested sessions separate while each process uses the path that it inherited. It is not a security check against code that runs as the same user. That code can tamper with files or launch unrelated processes. Also, descendants that leave the process group of the managed process are outside its cleanup. If KILL stops the Ravel CLI, the managed process can continue to run without a supervisor. The Ravel CLI cannot catch KILL.

These limits are important when you decide what a caller can trust. A successful Ravel result confirms the supervision and cleanup that this chapter describes. It does not confirm that Ravel contained arbitrary same-user code. It also does not confirm that the work for the task of the caller is correct.

Check the request and evaluate the policy

The Ravel CLI first reads the settings and the command-line inputs and checks the policy file. --config policy.ts names a file relative to the caller’s working directory. Ravel resolves its real path and requires a readable regular file. It does not search the caller’s repository for a different policy. Settings still come from $HOME/.config/ravel/settings.json, even when --config is present. The private home of the example is empty, so the defaults apply.

The Ravel CLI finds the worker that matches it and starts it in the empty private directory of the worker. It checks the identity of the worker before it sends the policy request. The worker receives a restricted environment and no session-result context. It changes to / before it imports the owner policy. The cwd of the request keeps the caller’s working directory. The directory of the worker does not change that value.

The worker imports policy.ts and calls select. The literal import ravel/sdk resolves to the embedded SDK of the worker. Thus, this example needs no local installation of dependencies. The policy has no policy-context loader, and the caller supplied no policy context. In this example, the selection therefore depends only on the request.

Launch the managed job

After selection, Ravel makes a new result channel. This channel is a private temporary directory and a path where a program can send a result. Ravel gives that path to the managed process in RAVEL_EXIT_FILE. This path is the session-result context of the managed process. The PATH of the example also lets the fake find the same installed ravel for end-session.

The runner in Ravel launches the managed process in a process group of its own. A process group is a set of processes. A program can send one signal to all processes in the group. A child usually inherits the group of its parent. Thus, with one signal to the group, Ravel can stop the fake and each descendant that stays in that group.

The managed process and the members of its group form the job that Ravel supervises. Here, “job” has its job-control meaning: a process group that a program controls as one unit. Ravel stays the parent of the managed process while it supervises the process. start-session does not replace itself with the selected program.

The new process group does not make a new Ravel session or a new login. These three terms name different units:

UnitWhat it meansIn this unconfined example
Ravel sessionOne start-session invocationCovers selection, the managed job and cleanup
Process groupProcesses that can receive a signal as one groupThe managed process leads a new group
POSIX sessionAn operating-system unit that job control usesThe managed process stays in the caller’s POSIX session

A confined launch uses a new POSIX session. Chapter 5, “Run sessions”, teaches that separate case.

This chapter writes INT, TERM, HUP and KILL without the SIG prefix. Other signal names keep that prefix. Code and diagnostic text keep their literal names.

If you start Ravel from an interactive terminal, one more group is important: the foreground process group of the terminal. The controlling terminal sends keyboard input to that group. It also sends the signals that the terminal makes, such as INT from Ctrl-C, to that group.

If Ravel’s own process group is the foreground group, Ravel saves the terminal modes. Then it makes the group of the managed process the foreground group. Ravel does these two steps before the managed process executes the selected program. This book says that Ravel lends the terminal. The selected program can then read from the terminal as a foreground job. If a different job has the foreground, Ravel launches the program and does not lend the terminal.

If Ravel lent the terminal, it makes its own group the foreground group again at completion and restores the saved modes. The modes include settings such as whether the terminal shows typed characters. This recovery is important when a program changes the modes. The fake does not read input or change terminal modes. The automatic example check runs without a terminal. Thus, its transcript shows the choice of command and the delivery of the result, not a change of the foreground group.

Chapter 9, “Jobs, signals and the terminal”, gives the terminal rules. These rules include, for each case, the process group from which Ravel recovers the terminal. Chapter 9 also gives signal masks and failure guarantees.

Send the result and finish the job

The fake prints its argument and calls ravel end-session -- "finished". That command reads the inherited RAVEL_EXIT_FILE path. It reads no policy or settings and needs no session ID. It writes the complete value into a temporary file. Then it sends the value into the result channel, but it does not replace a result that is already there. Ravel keeps the first complete result that it receives.

When end-session sends the result, it asks the Ravel CLI to end the session. This request does not mean that the job already ended. Also, end-session does not wait for the cleanup of the enclosing session. In this fake, the script has no more commands, so it exits.

A managed process can continue to run after it sends the result. The runner then uses these stages. Chapter 9 gives the exact times.

StageWhen it startsRunner action
Grace periodThe runner detects the sent resultAllows time for the managed process to exit
TERMThe managed process still runs after the grace periodSends TERM to the process group, then allows a second grace period
KILLThe managed process still runs after the second grace periodSends KILL to the process group

The exit of the managed process does not complete the cleanup. Before it reaps the direct child, Ravel stops the members of the process group that still run. To reap a finished child, the parent collects its exit status. This action also releases the last record of that child in the operating system.

The managed process leads its group. Thus, the ID of the group is the PID of the managed process. The operating system does not use that PID again until Ravel reaps the process. Thus, Ravel sends the last group signals before the reap, so that they cannot go to an unrelated group that took the same ID.

Then, if the runner lent the terminal, it recovers the terminal. It also confirms that the process group is gone. The Ravel CLI checks and reads the sent result. It removes the temporary directory of the result channel. Then, before it writes to the caller’s standard output, it checks the outcomes of cancellation and cleanup. The appearance of the result file does not remove any of these steps.

Success means that the result reaches the caller only after Ravel reaps the managed process, the whole process group is gone and cleanup succeeds. start-session exits with status 0 only if the final write also succeeds. If the write fails, the caller can receive only the start of the result, and the invocation fails. Thus, bytes on standard output alone do not prove success.

That guarantee is for the process group of the managed process. It does not include these three cases:

  • a descendant that leaves the group
  • a detached child that trusted policy starts
  • a KILL that stops the Ravel CLI (the Ravel CLI cannot catch KILL)

The trust limits in chapter 2 also explain why code that runs as the same user can change files or launch unrelated processes. A successful session shows that Ravel delivered a sent result after it confirmed the cleanup. It does not show that the work that the prompt requests is correct.

Recognise the other outcomes

Refusal, cancellation, natural exit without a result and failure are normal outcomes. Each one is different from the successful example and from the others. A caller needs to recognise each one.

  • A refusal occurs before the launch. It occurs when the owner policy declines the request, or when Ravel cannot accept the file, behaviour or data of the policy. Ravel does not try a different route and returns no result to the caller.
  • Cancellation by an INT, TERM or HUP signal can occur during selection or supervision. The session then returns no result to the caller, even if a program already sent a value.
  • A natural exit without a sent result also returns no result to the caller, even when the managed process exits with status 0. An empty sent result is different. A program sent an empty value, and the session can succeed after cleanup.
  • A failure of the worker, of supervision or of cleanup prevents success. A failure of the final write of the result also makes the invocation fail after cleanup.

Also, a managed process can send a result and later exit with a nonzero status. That exit does not make the result invalid. Ravel checks the sent result, cancellation and cleanup separately from the exit status of the program. Chapter 5 teaches the outcomes and their exit codes with examples.

In words, a refusal stops selection before the launch. Cancellation and failure can stop selection or supervision. A natural exit without a sent result is part of supervision, even if the managed process exits with status 0. On each path, Ravel attempts the necessary cleanup.

Then Ravel decides the final outcome, and cancellation has priority. If no cancellation occurred, the outcome is the original refusal or failure. A missing result is one of these failures. Ravel reports any further cleanup problems next to that outcome. A cleanup failure prevents success, even when everything else succeeds.

Only a valid sent value with no cancellation, a confirmed reap, confirmed absence of the group and confirmed cleanup reaches the final write and flush. An empty sent result is a value. A later nonzero exit of the managed process does not, by itself, make the value invalid.

A failed write can leave only the start of the result on standard output. Chapter 8 gives the full outcome decision.

Define a policy and read the request

The entry file exports a plain object with the name policy. Import definePolicy from the literal module name ravel/sdk. Give that object to definePolicy as its argument. The helper returns the object unchanged. It gives TypeScript sufficient information to check your fields and to find the parameter types of select. Ravel still validates the policy at runtime, when it evaluates the policy.

The policy object can have these four fields. They identify the policy interface, give a label to your revision and supply the functions that Ravel calls:

FieldMeaning
schemaVersionThe literal number 2. It identifies the policy shape.
versionA nonblank label that you maintain, such as book-routing-1. It is independent of Ravel’s own version.

The simplest select uses only its first parameter, request. Ravel also gives select the delivered policy context, which can be undefined, and a host. The host has diagnostic(text) and an AbortSignal at signal. With the host, asynchronous work can monitor the selection deadline, and the policy can write diagnostic text. The host of select has no operations that read files. Only the host of the policy-context loader has them.

Select a command or refuse

A selection describes the process that Ravel starts. program is one of these:

  • an absolute path
  • a relative path that contains a separator, which Ravel resolves against the caller’s working directory
  • a name that Ravel finds on the caller’s PATH

Each string in args becomes one argument after the program. Ravel does no shell expansion or word splitting. A shell runs only when the selected command needs one. The fake in this section needs one: its shebang line names /bin/sh.

A selection has these fields. Some give the command that Ravel executes. The others give the labels and the explanation that Ravel reports:

Selection fieldMeaning
statusThe literal "selected".
programThe path or the name of the executable.
argsThe argument strings, in order. The array and its strings can be empty.
provider, model, effortOwner labels that the routing diagnostics report. They do not configure a service or change the arguments.
reasonYour explanation of this decision. The routing diagnostics report it verbatim.

Each string field is nonblank, except the entries in args. The program and the arguments cannot contain a NUL. Ravel validates the shape of the selection. It does not examine whether the command is sensible or whether it passes the prompt. Your policy and its tests own those decisions.

A refusal gives a reason that the caller can identify and an action that the caller can take. It has these fields:

Refusal fieldMeaning
statusThe literal "refused".
codeYour nonblank code that identifies the reason.
messageA nonblank explanation of the problem.
remedyA nonblank action that the caller or the owner can take.

Ravel reports your refusal as policy_refused, together with your code (policyCode in JSON diagnostics). Then it exits with status 3 and launches nothing. It does not try a different route. If select returns nothing, returns malformed data or throws an error, Ravel also launches nothing. But then the caller does not get the message and the remedy of your refusal. If evaluation does not finish before the selection deadline, the outcome is selection_timeout, which is different from an explicit policy refusal.

The table below gives the steps of evaluation, in order, on the path to a launch. A returned selection does not let Ravel skip the worker cleanup. If evaluation stops at an earlier step, it also needs worker cleanup, but no managed launch can follow.

StepWorkCondition to continue
1Ravel imports the owner policy.The import succeeds, and the named policy export has the accepted shape.
2Ravel assembles the policy context. It calls loadContext if it exists.The caller data and the delivered document obey their shape and size rules. If the loader refuses, evaluation stops here, and Ravel does not call select. Without a loader or a caller document, selection continues with undefined.
3Ravel calls select with the request and the delivered policy context.The returned value is a valid selection. An explicit refusal becomes policy_refused. Malformed data or a thrown error also prevents the launch.
4Ravel reaps the policy worker and removes its private directory before the managed launch.Ravel confirms the reap and the removal. If the cleanup fails, a returned selection is not sufficient for a launch.

One deadline, selectionMs, starts when Ravel spawns the worker. It covers the import, the assembly of the policy context and select. It does not start again for each step. When it expires, evaluation stops with selection_timeout (exit status 124), and Ravel launches nothing. A refusal has exit status 3. Ravel can refuse an invalid caller document before the loader runs.

The evaluation table above gives only the order from the policy to the launch. Chapter 3’s outcome view also gives the outcomes of cancellation and supervision.

Offer a checkout choice

A policy can let a checkout choose from arrangements that the owner wrote before. The SDK’s readChoice(request.cwd, offered) reads .ravel-choice in that directory. It splits the contents of the file at whitespace and returns the names as an array. If the file does not exist, it returns undefined, so the policy supplies the default. It does not search parent directories. For an empty file, it returns an empty array, not undefined.

The helper accepts a regular UTF-8 file of 4 KiB or less. For a file that exists but that the helper does not accept, it returns a refusal with the code choice_unreadable:

  • a file that it cannot read
  • a file that is too large
  • a file that is not valid UTF-8
  • a file that is not a regular file

For a name that is not in offered, it returns a refusal with the code choice_unoffered. Return each refusal of readChoice from select.

The exported constant CHOICE_FILE holds the file name. The helper does an ordinary filesystem read, not a measured read of policy context. If the selection must explain the choice, put the applied choice in its reason.

Nothing reads this file unless your policy calls the helper. The file can choose offered names, but it cannot add a program or arguments. Your code decides how many names the policy accepts and what each name means.

The sample that you can edit is crates/ravel/worker/sample/policy.ts in the checkout, and libexec/ravel/examples/sample.ts in an installation. The example below uses the decisions of the sample:

  • Without a choice file, the choice is default.
  • The policy accepts exactly one name.
  • careful sets the selected effort and its argument to high.

The careful value replaces the effort of each route. It is not a minimum. Thus, it also replaces the table’s xhigh for migration and architecture. If you want a different arrangement, edit the names and the behaviour together.

Complete example: validate the two arrangements of the sample on all five routes. Then validate its four refusals: an unknown kind, the wrong number of names, a name that it does not offer and an unreadable file.

import { definePolicy, readChoice } from "ravel/sdk";
import { selectRoute, routes } from "ravel/examples/static";

export const policy = definePolicy({
  schemaVersion: 2,
  version: "owner-choice-1",
  select(request) {
    const choice = readChoice(request.cwd, ["default", "careful"]);
    if (choice !== undefined && "status" in choice) return choice;
    const names = choice ?? ["default"];
    if (names.length !== 1) {
      return {
        status: "refused",
        code: "one_choice",
        message: "choose one arrangement",
        remedy: "write default or careful in .ravel-choice",
      };
    }
    const selected = selectRoute(routes, request);
    if (selected.status === "refused" || names[0] !== "careful") return selected;
    return {
      ...selected,
      effort: "high",
      args: ["--model", selected.model, "--effort", "high", request.prompt],
      reason: "careful choice",
    };
  },
});

Supply policy context

A caller can supply a JSON document with --context PATH. The path is relative to the caller’s working directory, and it names a readable regular file. The document’s schemaVersion is 1, independently of the policy’s version-2 interface. The document holds facts and attributed judgements. Your policy can use them to choose from the commands that it defines. The document does not give permission to run a command that its facts name.

The document has the fields in the table below. The choice of the executable stays in owner code.

FieldAccepted data
schemaVersionRequired: the number 1.
summaryAn optional string. It can be empty.
acceptanceCriteriaAn optional array of strings.
factsAn optional object with JSON data as its values.
assessmentsAn optional object with values of the form { by, value }: a nonblank author name and JSON data.
sourcesAn optional array of 256 source records or fewer. Each record has a nonblank name. It identifies the source with sha256, with a nonblank version, or with both. An optional bytes is a nonnegative whole number. A digest is 64 lowercase hexadecimal digits.

An absent field means that the value is unknown. For example, an absent facts is different from a known empty object. Ravel refuses each unknown top-level field, for example program, args, argv, command, select, loadContext, env, environment, exec, shell and script. Nested JSON facts stay data, also when a key has one of those names. The caller and the loader do not supply the measured field. Ravel adds it.

Ravel reserves one JSON object shape, also in facts and in assessment values: an object whose only key is $ravel. Ravel uses that shape to mark values that JSON cannot hold. It refuses that shape as context_invalid. Use a different key for your own data.

Without loadContext, select receives the caller’s document with Ravel’s measured field attached. If the caller supplied no document, select receives undefined. With a loader, select receives the return value of the loader instead. The loader receives request.context. Thus, it can explicitly keep or replace the caller’s data. Ravel does not merge the two documents for you.

The loader can be asynchronous. It shares the selection deadline with the policy import and select.

Find the row for your caller input and your policy. A loader replaces the document that select receives, unless the code of the loader keeps the caller’s data. Each row assumes that the documents are valid and that the loader, if the policy has one, returns a document:

Caller document?Policy has loadContext?Policy context that select receives
NoNoundefined.
YesNoThe caller’s document, with Ravel’s measured list attached.
NoYesThe document that the loader returns, with measured attached. The loader receives no request.context.
YesYesThe document that the loader returns, with measured attached. The loader receives the caller’s document at request.context, and it decides what to keep. Ravel does not merge the two documents automatically.

Choose a synchronous host read for the value that your loader needs. Each read returns a source record that identifies the bytes that it read:

OperationReturn value
host.readText(path, maxBytes?){ text, source }. It decodes the file as UTF-8.
host.readJson(path, maxBytes?){ value, source }. It decodes the file as UTF-8 and parses the JSON. Validate that JSON value for the needs of your policy.

The two reads resolve relative paths against request.cwd. They accept only a regular file. They return a source with the canonical name, the actual bytes and the sha256 of the file. The default read limit is 65,536 bytes, or the policy-context budget if the budget is smaller. A positive whole number in maxBytes sets the limit of one read. That limit can be as large as the policy-context budget.

These read problems cause a refusal, even if the loader catches the exception that the read throws:

  • a read that is larger than its limit
  • a read that asks for a limit larger than the budget
  • a read that makes the number of measured sources larger than its limit

A missing file, invalid UTF-8 or invalid JSON causes an exception. If the loader does not catch that exception, the refusal identifies the source of the read that failed. A loader that needs valid content can return its own refusal, as select can. Then Ravel does not call select.

Ravel attaches a measured array to the frozen document that it delivers. Its records have name, bytes, sha256 and via ("--context", "readText" or "readJson"). The caller’s document comes first. The successful host reads follow, in order, and each repeated read of a file makes its own record. The limit is 256 measured records, and the record of the caller’s document, if there is one, counts toward it. The document’s own sources array has a separate limit of 256 records.

The complete delivered JSON, with measured, cannot be larger than the policy-context budget. Thus, a small input file can give a delivered document that is too large when Ravel attaches its measurement.

These fields distinguish claims about sources from Ravel’s own measurements:

FieldWho supplies itWhat it identifies
sourcesThe caller or the loaderThe stated origin of a claim, by digest, version or both.
assessments[name].byThe caller or the loaderThe stated author of an assessment.
measuredRavelThe bytes read from the caller document and through the host, with each path, size, digest and method.

None of these fields proves who the author is or that the claim is true. Trusted owner code can also read files or the network directly, but measured does not record those reads.

Keep the policy decisions in owner code. Use outside information to choose a route that the policy defines. Do not use outside text as a program or as a template of arguments to execute.

Resolve policy imports

Use the literal import names ravel/sdk and ravel/examples/static for the embedded modules. They resolve to the worker’s embedded copies, also when a package beside your policy supplies the same names. Ravel reserves only those two exact names. ravel/anything-else is an ordinary package lookup. A change to the installed SDK source or to a copy of the static table does not change the embedded copies. To use a local copy, import it by its file path.

This table gives the location from which each reference resolves. A relative import and a relative host read do not always refer to the same directory:

ReferenceResolution base or destination
Literal ravel/sdk or ravel/examples/static importThe worker’s embedded module, also beside a package with the same name.
Relative import such as ./routes.tsThe directory of the file that contains the import. For a symlinked policy, the directory of its real file.
Ordinary package importBun’s package resolver, from the location of the file that contains the import.

A relative import resolves in the directory of the file that contains it. If your entry is a symlink, the location of its real file applies. Keep a helper beside the policy. Import it with a relative path, for example import { route } from "./routes.ts". The agent example below uses that layout. A relative host read is different: it resolves against the caller’s request.cwd, as the policy-context example showed.

Bun’s package resolver resolves ordinary dependencies from the location of the file that imports them. The nearest package.json that Bun can read as a package supplies the imports map, the package’s own name and its exports. Bun skips a package.json file that it cannot parse or that is not a package. Resolution through the main and exports fields of a package stays enabled. Install the dependencies yourself, because the standalone worker does not install a missing dependency automatically.

An alias in a package’s imports map with the target ravel/sdk is still a package lookup. It never reaches the embedded module. Thus, it can load a package that supplies the same name instead. When you need the embedded module, use the literal ravel/sdk import. The same rule applies to ravel/examples/static.

The compiled worker controls which configuration files Bun loads automatically. These controls apply at runtime:

tsconfig.jsonDisabledA path alias can help your editor, but that alias alone does not make a runtime import work.

The Ravel CLI clears the runtime-injection variables and disables Bun’s runtime transpiler cache. Then it starts the worker in a private empty directory. Before the worker imports owner code, it changes its directory to /. File imports still resolve from their files. Imports without a file location, such as a virtual module, resolve from that process directory.

The worker changes its directory to /. Thus, the lookups for imports without a file location do not search the parent directories of the temporary directory. But the resolver can still find /package.json and /node_modules. Owner code can change its directory or import arbitrary code itself.

If policy code creates a native Bun Worker, that Worker starts a different runtime instance. The worker disables dotenv autoloading. Thus, that instance does not load the dotenv files that it finds. The controls in this section change how the worker starts and resolves modules. They do not confine trusted owner code. The policy is never in a managed-process confinement.

Run sessions

A caller starts a session, gives its instructions and interprets its result. The owner policy chooses the program. Ravel supervises that managed process and returns an opaque result only after it confirms the cleanup. This chapter shows how to give a request and how to run nested or confined sessions. It also shows how to identify each outcome that a caller can see.

Supply the prompt and caller data

Pass exactly one of --prompt TEXT and --prompt-file PATH. Ravel gives the text to the policy unchanged, also when it is an empty string or ends with newlines. Ravel adds no instructions to end the session. It never reads a prompt from terminal stdin. A prompt is UTF-8, contains no NUL and has a maximum size of 1 MiB. Ravel does not truncate input that is not valid, but stops the invocation with status 2.

The argument limits of the operating system can be smaller than 1 MiB. These limits also apply when the policy puts a prompt from a file into the arguments of the selected program.

Use a file when the exact text is important. Shell command substitution removes trailing newlines. Thus, --prompt "$(cat prompt.txt)" can change the text before Ravel receives it. --prompt-file prompt.txt reads the file directly, relative to the caller’s working directory. Ravel changes no text before the policy receives it. Then the policy makes the arguments of the selected command and decides how to give the prompt to that program.

The kind is a required caller token that is not empty. Ravel has no catalogue of kinds and does not get a kind from a file name. A policy can route review, refuse it or treat it as any other kind. The caller and the policy author agree on these tokens.

These inputs give data to the policy. They do not tell Ravel to read a task or to give the task a meaning:

Accept a result only after success

Keep the result bytes and the status of start-session together. Status 0 means that all of these conditions are true:

  • A program in the session sent a valid result.
  • Ravel reaped the direct child.
  • Ravel confirmed that the process group of the managed process is gone.
  • The required cleanup succeeded.
  • The final write and flush of the result succeeded.

An empty sent result is a successful result with zero bytes. If a managed process exits with status 0 and sends no result, the status is 1. Ravel then returns no result to the caller. But if a program sends a result and the child then exits with a nonzero status, start-session can still give status 0. Ravel’s status shows whether Ravel delivered a sent result after cleanup. It does not show whether the work in the prompt was correct.

end-session takes one UTF-8 argument with a maximum size of 1 MiB. Quote it, and put -- before a value that looks like an option, such as --help. Ravel writes an empty, multiline or Unicode value unchanged to standard output and does not interpret it. The operating system can apply a smaller limit for command arguments before end-session starts.

Ravel keeps the first complete result that it receives through the result channel. When that first result arrives, Ravel starts to stop the harness. Thus, a second end-session call and the shutdown are in a race: either can occur first. For example, another process in the group can send a result before Ravel stops that process. Ravel keeps the first result, even if the second command succeeds.

Keep nested sessions separate

A managed process can be the caller of another start-session. The inner session allocates its own result channel. It replaces RAVEL_EXIT_FILE only for its own managed process. When the inner process sends its result, the outer session does not finish, and end-session accepts no session ID or target argument.

Confine the managed process

Confinement restricts the filesystem access and the environment of the managed process. Add --confine when you want that restriction. The owner policy and its policy worker stay outside the confinement. Policy is trusted executable configuration.

On macOS, Ravel uses /usr/bin/sandbox-exec. On Linux, it uses the system bubblewrap executable, /usr/bin/bwrap or /bin/bwrap. Before Ravel evaluates the policy, it tests whether the backend can make a sandbox. If the backend is not available or not usable, the invocation stops with confinement_unusable and status 2. Ravel does not then launch the process without confinement.

These paths have different grants for the confined managed process:

PathAccessHow the process gets access
Canonical working directory and private run directoryRead and writeRavel grants them for each confined launch.
System runtime paths, selected executable and real executable file of the Ravel CLIRead-onlyRavel grants them for each confined launch.
One additional regular file that existsRead-only--runtime-read FILE. Repeat it for each file. It requires --confine and grants no directory tree.
Parent of the result directoryRead and write--exit-dir DIR. The directory must exist and be writable.

If the managed process needs a full directory, copy the task data into the working directory. A read-only runtime grant stays read-only, even inside a writable directory. Confinement permits network access. It is not an offline mode.

--exit-dir DIR puts the private result directory of the session in a writable directory that exists. It works with or without confinement. With confinement, it also gives write access to that parent directory. Thus, do not choose a parent directory that contains files that the managed process must not change. Without the option, an unconfined session uses the system temporary directory. A confined session puts the result channel in its private run directory.

Keep the policy directory and the owner settings outside every filesystem grant. Ravel makes each path canonical. If paths overlap, Ravel stops with an error before it evaluates the policy. This check also finds overlaps through symlinks or through the system runtime grants. For example, if you run --confine --config ./policy.ts from the directory that contains that policy, the policy overlaps the writable working directory. Put the policy in a separate owner directory, and invoke Ravel from the project directory.

confinement_overlap reports the paths that overlap. confinement_unusable reports a resource or a backend that Ravel cannot use. Both use status 2. Before selection, an --exit-dir that is not valid can also give exit_dir_unusable. Later failures of allocation or cleanup have their own diagnostics.

Read notices separately from results

For start-session, stdout contains only the result. Ravel writes the result unchanged, with no added newline, and does not interpret it. The three signal statuses in the table follow the shell convention: 128 plus the signal number. Ravel attempts the cleanup and then raises the same signal again. Thus, a process API reports termination by a signal. If the propagation fails, Ravel reports the failure and uses the numeric status in its place. A caller that uses a process API handles both cases. If a signal is ignored or blocked when Ravel starts, that signal does not automatically cause a cancellation.

Note: KILL or another abrupt death can stop Ravel before it decides the final outcome. A signal that arrives after the final decision about cancellation can interrupt the result write. Neither case confirms the cleanup or that the caller received the complete result. A failed final write can leave a prefix on stdout. The operational limits describe these cases.

The parts of Ravel

Ravel separates the choice of a command from the supervision of that command. The owner policy chooses a program. The Ravel CLI checks that choice, runs the program and decides the final outcome. The caller interprets the result. A session is one start-session invocation, from the request to the reported outcome.

This chapter explains the parts of the source that hold those roles. After it, you can locate each part and explain why Ravel uses TypeScript and two Rust packages. Chapter 8 follows one session through the functions. Chapter 9 explains the process and terminal mechanics.

The Ravel CLI coordinates the session

The CLI connects the policy’s selection to the supervision of the job. Its choice.rs prepares the request and obtains a checked policy response. Its run.rs creates a fresh result channel and gives that channel to the runner with the selected command. After supervision, the CLI combines the result, cancellation and cleanup reports before it writes to standard output.

The ravel process keeps the caller’s environment and the authority over the terminal while policy code runs in the worker. It also reserves standard output for the result. The standard output of the managed process and Ravel’s diagnostics go to standard error. A policy response cannot write the session’s final result.

The package has a library target as well as an executable target. The library exports SessionChannel, publish_result and end_session, with the result constants. The executable uses this library and keyed-launch. This division lets the result-channel tests compose a channel with a runner without policy evaluation.

The CLI retains a coordination cost. Neither the worker nor the runner knows all the conditions for a successful Ravel session. For example, a runner can report a reaped child while the CLI still owes temporary-file cleanup. A change to final output or failure precedence therefore belongs in the CLI’s coordination code.

The worker executes TypeScript before the launch

Owner configuration is executable TypeScript. A policy can import modules, use asynchronous functions and read files or network services. A static table parser cannot preserve that contract. Bun supplies the language runtime and module support. Ravel does not implement another TypeScript engine.

The build compiles the worker and its Bun runtime into ravel-policy. An installed Ravel therefore needs no separate Bun or Node.js installation. Rust owns supervision, while TypeScript supplies the policy execution environment. This choice costs a second build tool, a larger executable, the licence notices of the Bun runtime and checks on each delivery target.

The worker is a separate process so owner code does not execute inside the process that supervises the session. In worker.rs, the CLI starts it with a cleared environment, null standard input and a private socket at file descriptor 3. The worker’s standard output and standard error carry bounded diagnostics. Length-prefixed JSON messages on the socket carry the protocol.

The CLI supplies the base environment and permitted grants. It also sets BUN_RUNTIME_TRANSPILER_CACHE_PATH=0 to disable Bun’s runtime transpiler cache. environment.rs excludes RAVEL_* from grants, so a nested caller cannot pass its RAVEL_EXIT_FILE to the worker through this path. The CLI allocates the new session’s result channel only after policy evaluation succeeds. Thus, the worker receives neither session’s session-result context.

The worker stops before the managed process starts. A valid response does not let it continue beside the managed process. The CLI closes the protocol socket, ends the worker and confirms its reap. A parent reaps a child when it collects the exit status of that child. The CLI also removes the worker’s private directory.

The separate process is not a sandbox for hostile owner code. Policy is trusted code. It can start detached children, which the worker cleanup guarantee does not cover. Same-user code can also tamper with files. Chapter 2 explains how these controls differ from the confinement of a managed process.

Three parts of Ravel control the worker’s startup. The CLI filters environment variables before the worker starts. The worker build disables dotenv, bunfig and tsconfig autoloading. The worker starts in a private empty directory, then changes to / before it registers embedded imports or loads owner policy. These controls limit the files and variables that can change policy evaluation without a request from the policy.

Package imports still need Bun’s resolver. The build keeps package autoloading enabled. /package.json and /node_modules stay reachable inputs for the resolver. The module-resolution reference gives the supported import rules and their limits. A runtime replacement needs to preserve those rules as well as TypeScript syntax.

The runner owns the local job mechanics

keyed-launch contains the process-group setup, escalation, reap and terminal recovery, with Rust launch types as their interface. It forwards cancellation signals to the job. Argv holds a program and its arguments as separate words. Launch adds the working directory, environment removals and grants, an optional completion channel, signal state and escalation durations. The runner spawns the command directly. A shell participates only when the command selects one.

The runner does not choose a policy or interpret provider and model labels. It also does not read the Ravel result. Its completion channel tells it only that a file appeared. Its Rust result is Ended or LaunchError, not the opaque result that the caller receives.

Ravel supports no separate component. Its runner serves the Ravel CLI, which supervises one session and then exits. Another program invokes the Ravel CLI as a child process and leaves supervision to it. These private packages do not establish a contract for a persistent runner.

The result channel carries the value

The result channel adds contents to the runner’s file-appearance mechanism. SessionChannel owns a private temporary directory, the completion path and an open directory handle for reads. end_session obtains the destination from RAVEL_EXIT_FILE. publish_result writes a complete temporary file, then tries a hard link that cannot replace an earlier result.

The runner observes the file’s appearance. The result-channel code reads the contents and rejects invalid files. Its result_after checks the group state and cancellation in the supplied Ended. An empty string is a sent result. An absent file is no result.

The program contract stays loose

The policy selects a program, Ravel runs it, and a program in the session sends one value with end-session. Ravel expects a harness in normal use, but it requires no model-provider interface from the selected program. The policy decides whether the command receives the prompt.

This separation appears in the code, not only in the examples. Rust checks the selection’s shape in policy.rs. Then run.rs constructs Argv from the selected executable and argument words. The runner adds no prompt argument. end_session accepts text and uses the inherited path. The final CLI write returns that text unchanged after successful cleanup.

Finish the managed job

Jobs, signals and the terminal

A result requests the end of a job. It does not prove that the job has ended. The Ravel CLI stays alive to supervise that end before it returns the result to the caller. The runner inside the CLI supplies the process and terminal operations.

Chapter 3 introduced a job and its reap through one session. This chapter explains why the order matters, how Ravel ends a process that does not exit, and what confinement changes. It also explains terminal recovery, entry signals and the limits of these guarantees. Chapter 8 shows where these operations occur in the code.

The managed process leads a job

The managed process is the direct child that Ravel starts from the selected command. For an ordinary unconfined launch, Ravel creates a new process group for that child. The group’s ID is the child’s PID. Descendants inherit this group unless they explicitly change it. The managed process and the members of its group form the job.

A signal to a process group can reach its members together. A signal to the child’s PID reaches only that child. If Ravel stopped only the child, a helper could keep a file lock or continue to change the caller’s files. The group gives Ravel a scope for shutdown that includes ordinary descendants.

A POSIX session can contain several process groups and can have a controlling terminal. An ordinary unconfined launch keeps the caller’s POSIX session. Thus, Ravel can give the terminal’s foreground to the new group. The terminal rules select which group can read terminal input and receive signals from the keyboard.

Choice for the managed launchConsequence
A new process group in the caller’s POSIX sessionRavel can signal the job together and can lend the caller’s terminal
A new POSIX session through setsidThe child starts without the caller’s controlling terminal. This suits the detached modes below
Only the child’s PID as the shutdown targetDescendants can survive their parent. This does not meet Ravel’s cleanup contract

A descendant can leave the job’s group, for example through its own setsid call. Group cleanup does not cover that descendant. Ravel does not promise to track every process descended from the managed process. A new process group also creates no new Ravel session: that term means one start-session invocation.

Follow the escalation after a result

An interactive harness can finish its work and then wait for another prompt. The caller therefore tells it to send an opaque result with end-session. The command creates the completion file in the result channel. The runner observes that file’s presence. Ravel checks its contents separately.

A signal name such as SIGTERM has the prefix SIG. This chapter writes INT, TERM, HUP and KILL without that prefix, as the shell trap command does. Other signals keep their full names.

Until it sends KILL, the runner checks the child and channel at 500-millisecond intervals. Its first observation of the file starts the grace period. Thus, the schedule starts at observation, not at the instant the sender calls end-session.

TERM lets the program handle its own shutdown. A program can ignore TERM. It cannot catch or ignore KILL. If the child exits during either grace period, Ravel proceeds to final cleanup without the later escalation stages. Descendants receive no separate grace period after the child exits.

The 2-second and 5-second values belong to the Ravel CLI. The runner accepts its caller’s durations. These values are not a seven-second deadline for start-session: selection, observation delays and final cleanup also take time. Without a result or cancellation, this escalation places no time limit on the managed process.

After the escalation’s first KILL attempt, the runner uses a two-second bound for its exit checks and reap attempts. It does not restart that bound after an error. If the bound expires, the runner reports unresolved ownership, and Ravel returns no result to the caller. This bound limits retries. Stop the group before the reap

A process can exit before its parent collects its status. Until that collection, it remains a zombie: the system retains its identity and exit status, although it executes no more code. To reap the child, the parent collects that status and releases the retained process identity.

Ravel first observes exit without a reap. Its waitid call uses WNOWAIT for that purpose. The unreaped child reserves its PID, which is also the job’s group ID. Ravel uses that reservation for the last group signals.

If Ravel reaped first, the system could reuse the ID for an unrelated group. A later KILL to that number could then reach that unrelated group. The normal cleanup path therefore has this order:

StepOperationWhat it establishes
1Observe the child’s exit with waitid and WNOWAITThe child has exited, but still reserves its identity. A stop is not an exit
2Send KILL to its group twice, with a 20-millisecond pauseAttempt to stop the other members while the identity remains reserved
3Reap the direct child with waitpidConfirm the child’s status and release its identity
4Recover the terminal if Ravel lent itCheck foreground recovery and restore the saved modes
5Query the group without a signal, for up to one secondConfirm absence only when the system returns ESRCH, meaning no such process group

The second KILL addresses a macOS case where a fork overlaps the first group signal and leaves a new member. Both attempts precede the reap. They do not change the direct child’s status: it has already exited. Ravel reaps its direct child. Other descendants’ parents, or the system, reap those descendants.

A successful signal operation does not prove that the group is gone. The final query uses kill with signal 0, which sends no signal. Success or EPERM means that absence remains unconfirmed. An unrelated group that reuses the ID also prevents confirmation. Ravel does not signal that number after the reap.

On macOS, a group with only zombies can reject KILL with EPERM, or Operation not permitted. Ravel can retain this stop report without a session failure, but only after confirmed reap, successful terminal recovery and an ESRCH absence check. The report alone never confirms cleanup. Ravel writes retained reports as ravel: lines on standard error, or in operationReports with --json.

If the group still answers the query with success or EPERM after the confirmation wait, Ravel reports it and returns no result to the caller. A query error also prevents success. On an observation or reap error, Ravel attempts bounded cleanup and reports what it cannot confirm. Once it loses or releases the child identity, it stops all numeric signal attempts. After a timeout, it never reports a reap that did not occur.

Handle cancellation

Cancellation differs from a sent result. INT, TERM or HUP received by the Ravel CLI suppresses the result, even if the managed process already sent it. The runner checks for cancellation before it accepts an observed child exit. The CLI also checks signals around supervision and final cleanup.

Separate noninteractive execution from confinement

The runner has a separate run_noninteractive interface. It starts a new POSIX session, supplies end-of-file (EOF) on standard input, and closes inherited descriptors above standard error at exec. Both output streams go to a regular file that its caller supplies. It has no completion channel, so only child exit or cancellation ends the launch.

This interface isolates process control. It does not restrict filesystem access. It is also different from an ordinary start-session invocation that runs without a terminal.

A new POSIX session removes the inherited controlling terminal relationship. It does not restrict file access, and a descendant can still move to another group. The confinement backend supplies filesystem restrictions separately. These distinctions explain why the runner hides process mechanics behind separate launch interfaces, while the CLI owns policy and result decisions.

Confinement restricts the managed process and its descendants. It does not restrict the trusted owner policy or its policy worker. Lend and recover the terminal

A controlling terminal belongs to a POSIX session. It has one foreground process group at a time. That group can read terminal input. With the default terminal modes, Ctrl-C sends INT to that group. A background group’s attempt to read can instead stop it with SIGTTIN.

The runner opens /dev/tty, which names its controlling terminal. Redirected standard input does not remove that relationship. If the open fails, the runner proceeds without terminal job control. Detached modes do not open the terminal at all.

An open terminal alone permits no handoff. The runner queries its foreground group with tcgetpgrp and lends it only when the runner’s own group holds it. A Ravel CLI that starts in the background takes no foreground for itself. A shell can later give the foreground to the CLI’s group, for example with fg. Then a later supervision poll can lend the terminal to the managed group.

Before the first handoff, the runner saves the terminal attributes with tcgetattr. These terminal modes control such behaviour as character echo, line input and keyboard signals. An interactive program can change them to receive individual characters without echo. If KILL ends that program, the program cannot restore the modes itself.

The ordinary foreground launch follows these steps:

A background group can receive SIGTTOU when it changes terminal foreground. The runner therefore temporarily ignores SIGTTOU for the handback (the return of foreground to the runner’s group) and for mode restoration. Then it restores its previous disposition. It checks both the terminal operation and that restoration. The child also suppresses SIGTTOU for its handoff before it restores its entry signal state.

The lease remembers whether this launch ever held foreground. If it never did, the runner takes no foreground and restores no modes. For a lease that did hold foreground, the child’s outcome changes the rule:

The wider signal-death rule covers a managed supervisor that gives foreground to another group, then dies without cleanup. Otherwise, that delegated group could retain a raw terminal and continue to read input. The accepted cost is that a nested job-control shell can lose its foreground after such a death. Unknown child status does not permit this wider takeover. The POSIX session leader is the process that created the terminal’s POSIX session.

Exec can fail after the child takes foreground. The parent therefore retains the lease across a spawn error. The private pipe closes across exec and provides an attempted-group record, not proof of exec or a live group. If the record is missing or invalid, recovery is unconfirmed and Ravel reports it. The runner never signals that recorded number after failed spawn.

Failed-spawn handback requires two conditions through recovery: no other process or thread changes foreground, and no unrelated group reuses the recorded ID. These conditions also apply to recovery from unknown status. The foreground query and handback are separate operations. A one-session CLI lifetime does not make them atomic or establish those conditions.

Ravel reports failures of foreground queries, handback, mode restoration and temporary SIGTTOU restoration. After a recovery failure, Ravel returns no result to the caller. After failed spawn, the original spawn error stays primary unless cancellation overrides it. Recovery reports remain visible beside that outcome.

Preserve the entry signal state

A signal’s disposition is the process-wide choice to use its default action, ignore it, or call a handler. A thread’s signal mask names signals whose delivery that thread blocks. A blocked signal can remain queued until the thread permits delivery. An ignored signal and a blocked signal are different states.

Exec replaces the program but preserves the thread’s signal mask. It resets caught handlers to default actions. It preserves ignored dispositions with one exception: portable code cannot assume that an ignored SIGCHLD stays ignored after exec. The POSIX exec specification states that exception. Ravel explicitly restores its recorded ignore/default values before exec on its supported targets.

On its supported targets, Ravel gives the managed process the signal state from the CLI’s executable entry, before Rust startup changes it. The table below gives the exclusions. For example, Rust startup ignores SIGPIPE. A capture in main would see that new ignore instead of the state that Ravel inherited.

The CLI’s initialiser in signal_state.rs records the ignored set and the initial thread’s mask before those runtime changes. It keeps that record separate from later repairs by the CLI and the runner. If a required query fails, the CLI refuses the launch. It does not accept a partial record. The runner receives the values through EntrySignals and Launch.transparent. It does not capture them itself.

StateChild behaviour in a transparent launch
Recorded ignoreSet the signal to ignored before exec
Other recorded dispositionSet the signal to its default action. Do not copy a host handler
Recorded maskApply the mask after the dispositions, so delivery uses the restored actions
KILL and SIGSTOPLeave these unchangeable dispositions alone
Unsupported or runtime-reserved signal numbersExclude the platform’s specified numbers. A failure for another required number remains an error

The CLI and the runner also need signal state of their own. An ignored SIGCHLD or the SA_NOCLDWAIT flag can let the system discard child status without a parent reap. That would remove both the wait result and the identity reservation needed for group cleanup. The CLI checks and repairs this state before the policy worker starts. The runner checks it before its managed child starts. These repairs do not change the immutable child entry values.

The runner installs handlers for nonignored TERM and HUP. It also handles nonignored INT when no terminal exists or the launch is transparent. Ravel uses a transparent launch, so a nonignored INT sent directly to the CLI can cancel it even while the managed group owns foreground. The runner leaves ignored cancellation signals ignored.

Terminal INT follows foreground ownership. Before handoff, it can reach the CLI’s group. After handoff, it reaches the managed group. The child’s death from that signal is not itself a cancellation observation by the CLI. Ravel can still return a result after child signal death if the CLI observes no cancellation and all required cleanup succeeds.

The runner’s handlers and SIGCHLD repair persist after its call returns, on success or failure. A synchronous return does not restore a host’s prior state. The table gives the restoration responsibility at each boundary:

The CLI blocks its handled signals across the spawn transition. After spawn reports success, its checked Started transition restores the parent’s entry mask. Failure enters bounded child teardown and terminal recovery. It does not return early with an abandoned child.

Started means spawn-reported success, not confirmed exec. A child can die before exec and still produce that event. Only an actual wait produces Reaped.

Policy-output reader threads retain a mask that blocks INT, TERM and HUP until those threads exit. A block on only the main thread would leave another thread able to consume a signal during handoff. A bounded output drain can leave such a reader thread alive until CLI exit.

On both success and failure, final cleanup keeps handlers installed while the CLI restores its entry mask and collects cancellation observations. Deliver Ravel

A release carries a matched pair: the Ravel CLI and its policy worker. Chapter 7 explains why the pair stays together. An archive check establishes that this pair has the right files and can run outside the checkout. A version number alone establishes neither fact.

The book that a release carries teaches this pair as one delivered tool. Ravel supports no separate component. The private runner serves the Ravel CLI, which supervises one session and then exits. The runner’s return does not restore process-wide signal state. Thus, another program invokes the Ravel CLI as a child process. The book explains that interface and the limits of the private package.

Start with chapter 10’s install and smoke tasks. Those tasks test a local installation. This chapter extends that check to archives and the environments where their programs run.

Keep the version and pair together

The workspace has one Ravel version, independent of the version of any caller. Cargo.toml supplies it to both Rust packages, and the worker build reads the Ravel package version. The checkout used for this chapter has version 1.0.0. Its local tags include v0.1.0 and v1.0.0, and CHANGELOG.md describes both.

An unreleased archive uses the checkout’s version even when its source differs from that version’s release tag. Thus, a local archive named with v1.0.0 can contain later changes. Its name does not make it the released artifact.

Before the Ravel CLI sends the owner policy for evaluation, it checks three worker values:

ValueWhat it establishes
Protocol numberBoth programs use protocol 1
Package versionBoth programs report the same Ravel version
Source identityBoth builds used the same worker source inputs

The source identity is a SHA-256 digest. Relative to crates/ravel, its inputs are the TypeScript files under worker/src, worker/sdk and worker/examples, both worker tsconfigs, and scripts/dispatch.sh. Both builds sort those paths, hash each file, then hash the same list of paths and digests.

The source identity shows that two builds belong together. It does not authenticate an installation or cover every Rust source file. A worker with a different protocol, version or identity causes worker_identity_mismatch, with exit status 5, before policy evaluation. A probe worker that the tests build also has a different identity, and causes the same failure. To correct a mismatch, rebuild and install the pair together.

The CLI finds libexec/ravel/ravel-policy relative to its own canonical path, which is its path with all symlinks resolved. A symlink to the CLI therefore still reaches that CLI’s worker. Another worker on PATH cannot replace it. The worker contains Bun 1.4.2, so an installation needs no separate Bun or Node runtime.

Each Linux route checks that the userland reports glibc 2.17. A probe built for that floor runs. A second probe needs GLIBC_2.25, and the userland rejects it. The two probes show that the environment both runs valid programs and rejects a newer library requirement.

The CPU controls use an instruction above each floor: an Armv8.1 LSE atomic operation for arm64, and AVX2 for x86-64. At the floor, the instruction causes SIGILL. The same probe runs under the same emulator with -cpu max. Thus, the failure at the floor comes from the CPU model, not from a defective probe.

Each emulated route checks that every ELF executable in the archive, the CLI and the worker included, matches its emulator registration. Thus, those executables run through QEMU, not directly on the host CPU. The routes also check guest address bounds and the presence of the vDSO, a kernel-supplied interface mapped into a process. The test programs run without network access, as an unprivileged user, with read-only test inputs.

Build and deliver the tagged book

The release procedure puts each book at https://linkuistics.github.io/Ravel/vX.Y.Z/, where X.Y.Z is the release version. The root page lists releases, newest first. The address is the script’s default. No public delivery has confirmed it yet.

The Pages branch, gh-pages, holds one vX.Y.Z/ directory per release, a root index.html and an empty .nojekyll file. A release directory is final. The script refuses different bytes in a release directory that already holds a book. A retry with the same bytes adds no commit to the branch.

This branch preserves earlier books when a new release adds its directory. A custom workflow would need to preserve them in its site artifact too. An artifact with only the newest book would lose those earlier books. Ravel needs no custom workflow file. GitHub still uses its own deployment workflow for the branch and recognises .nojekyll for prebuilt content. GitHub’s source settings explain this branch mode.

build uses git archive on the tag’s commit. Changes to the checkout’s book text cannot enter that export. publish uses a temporary clone and a push without force. It does not edit the checkout or its jj state. Before the push, the script requires a GitHub release with exactly the three expected, nonempty archive assets. verify then checks branch contents, not the pages that the site serves. live makes up to 30 attempts by default, with ten seconds between attempts.

release-publish.sh puts the book on the Pages branch after the GitHub release. It updates the tap only after the book’s verify step passes. Thus, the Pages branch holds a release’s book before the tap offers that release. Pages can still take time to serve the new files, so the task checks the served pages last.

The Pages limits include a 1 GB site maximum, with soft limits of 100 GB per month and ten builds per hour. The script refuses a total site size of 1,000,000 KB or more, as reported by du. A local build of the current book in target/book uses about 7 MB. Later releases add their own directories, so the site grows.

The book stays outside the product archives and the worker source identity. The local docs:book:build task writes target/book, and docs:book serves it locally. Neither task sends files to Pages.
