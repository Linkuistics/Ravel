The Ravel book

Develop Ravel

A contributor changes the code and checks its behaviour through real processes. The tests use temporary owner policies and fixture programs. They need no model account or other project checkout.

This chapter starts with a checkout, then shows where to change code and add a test. Chapter 7 explains the reasons for the parts. Chapter 8 traces the code that a change can affect.

Ravel supports no separate component. Its private runner serves the Ravel CLI, which supervises one session and then exits. The runner’s return does not restore process-wide signal state. A program that needs supervised harness sessions invokes the Ravel CLI as a child process. This chapter teaches changes to Ravel itself.

Links to files outside the book open repository sources on GitHub. Before a change reaches main, read its evidence and convention files from the checkout.

Build the matched pair

task build first compiles the policy worker and generates the SDK declarations. Then it runs cargo build --locked --workspace for both Rust packages. The Cargo lockfile pins the versions of the Rust dependencies. A first build can need network access for dependencies that the host Cargo cache does not hold. The table maps each build task to a change and its output or check.

TaskUse it whenOutput or check

These paths assume the default Cargo target directory. task typecheck needs the declarations from task worker or task build. It does not generate them. After a worker change, run task build before command-boundary tests. Ravel checks the worker identity, so a new CLI with an old worker can refuse to run. Chapter 7 explains this identity check.

Find the source for a change

The workspace has two Rust packages. ravel holds the CLI and its private TypeScript worker. keyed-launch holds the runner. The package boundary does not promise an independently supported component. The private result channel combines the runner’s completion signal with the contents of the result. end-session sends the result, and the complete result file appears in one atomic step. The CLI uses the result channel with the compiled policy evaluator. Subprocess fixtures check nested session-result context, cancellation, process cleanup, and empty and multiline results. A change to this boundary needs more than a test of a parser.

Choose a test seam

A test seam is the boundary at which a test supplies inputs and observes behaviour. The nearest useful seam depends on the behaviour that the change affects. The table connects each behaviour to a test boundary and a focused command.

Behaviour to checkSeam and sourceFocused task
A local conversion, parser or decisionRust unit tests beside the CLI codetask test:session -- --bin ravel

The private result-transport tests (task test:session -- --lib) and the runner tests (task test:runner) need no policy worker. The complete Ravel package suite (task test:session) includes the command-boundary tests and needs the built worker. task test:cli and task test also need it. Run task build before these tasks. The hostile-runtime tests also need the probe workers from task probes. task test:hostile, task test:session and task test include these tests.

The test tasks compile Rust code, but they do not build the policy worker or the probe workers. On a fresh checkout, if you run task test:session before task build, the tests that need the worker fail. When a test requests policy evaluation without the worker, the CLI reports the diagnostic code worker_missing. All of these test tasks use the executables and fixtures of the checkout. They need no host Bun or Node, no model account and no installed Ravel.

The runner’s terminal tests create a pseudo-terminal, or PTY. This private terminal lets a test observe foreground ownership and modes without a human terminal. The in_pty helper in crates/keyed-launch/tests/job.rs starts the command as the leader of a new POSIX session. It reads the terminal output throughout, so a full terminal buffer cannot stop the leader. At its deadline, it kills the leader’s process group and fails the test.

Tests that change process-wide signal state use a separate process. The job tests run their own binary in a fixture role, a test function marked #[ignore]. A parent test invokes that role with its required environment. The fixture role is not a check when it runs alone. Chapter 9 explains the terminal behaviour that these tests observe.

task test:list lists the cases before a run. The focused tasks pass arguments after -- to nextest. A package selector chooses code, --test chooses an integration-test binary, and -E chooses test names with a filter expression.

Run the checks before handoff

task check runs scripts/check.sh. It stops at the first failed stage. Its last stage runs the workspace tests with nextest and shows their report. The earlier stages run in this order:

StageWork
formattingcargo fmt --all --check checks Rust format without changes
scriptsShellCheck checks shell scripts under scripts/ and crates/ravel/scripts/
worker-buildRebuilds the worker and generated SDK assets
worker-probesBuilds test-only workers with individual runtime controls removed
runtime-integrityChecks runtime-cache recovery and the rejection of a corrupt download, with offline fixtures
worker-typesTypechecks the TypeScript source and consumers of generated declarations
lintClippy checks the workspace and all targets with the committed lockfile
terminal-recoveryRunner tests produce real-PTY receipts, then a CLI unit test consumes them

task runtime:integrity and task test:terminal-recovery run those two checks separately.

The workspace configuration sets Clippy’s all lint group to deny, so a Clippy report from that group fails the lint stage. Each stage prints a short result. On failure, scripts/check.sh names its log and shows the last 60 lines. For the three worker stages, scripts/worker-check.sh also names its own complete log.

task check creates a fresh target/check.* file for each run. It saves the earlier stages’ output and appends the nextest report. scripts/worker-check.sh writes target/worker-check.*. Builds also update worker assets, probes and Cargo artifacts under target/. The terminal-recovery check creates temporary receipts and removes them when its script exits. The format stage does not rewrite source files.

task check does not build the book or run its example, excerpt, figure or prose checks. It also does not install Ravel or test release archives. Those workflows have their own tasks. The workspace test run uses nextest’s default selection, so a pass does not mean every ignored fixture or native measurement ran.

Add a test

The following fragments came from tests added to a scratch checkout for this chapter. They use the helpers and imports of the named files. All four passed on macOS arm64. They demonstrate current behaviour and do not change the product.

For a defect, first add an assertion that fails because of that defect. Then change the code and run the same test again. A test that passes before the repair does not distinguish the old behaviour from the new behaviour.

Test a real child process

In crates/keyed-launch/tests/launch.rs, the test type Harness writes a shell script in a temporary directory. This type is not an agent harness. The launch helper builds the runner request. support::controls() gives the names of the inherited enclosing-session controls, and the runner removes them from the child. Keep tests separate from live sessions lists these controls.

Fragment from the scratch copy of crates/keyed-launch/tests/launch.rs: this test omits the file’s imports and helper definitions.

#![allow(unused)]
fn main() {
#[test]
fn book_child_exit_keeps_its_status() {
    let harness = Harness::new();
    let script = harness.script("exit 23\n");
    let argv = harness.argv(&script);
    let channel = Channel::allocate(&harness.control()).unwrap();

    let ended = run(launch(&argv, &channel, support::controls(), None)).unwrap();

    assert_eq!(ended.status.code(), Some(23));
    assert_eq!(ended.end, End::Exited);
    assert!(!ended.signalled);
}
}

The child exits with status 23 without a completion signal. The assertions separate the exit status, the reason supervision ended, and the channel state. This test needs no PTY because it makes no terminal claim.

For a terminal claim, the helper in job.rs supplies the PTY. The launcher role reports its foreground group before and after the child runs.

Fragment from the scratch copy of crates/keyed-launch/tests/job.rs: this test omits the imports, Scratch, the launcher role and the PTY helper.

#![allow(unused)]
fn main() {
#[test]
fn book_normal_exit_restores_foreground() {
    let scratch = Scratch::new();
    let child = scratch.script("exit 23\n");
    let (status, output) = in_pty(
        role_command(
            "launcher",
            &[("JOB_CHILD", &child), ("JOB_REPORT", &scratch.os("report"))],
        ),
        Duration::from_secs(20),
        |_| {},
    );
    assert!(status.success(), "{status:?}\n{output}");
    let report = report(&scratch.path("report"));
    assert_eq!(report["code"], "23");
    assert_eq!(report["before_foreground"], report["group"]);
    assert_eq!(report["after_foreground"], report["group"]);
}
}

The parent checks that the launcher completed its report, then reads the child status from that report. The two statuses belong to different processes. The table separates those observations in this foreground example.

ProcessWork and observation in this example
Parent testStarts the launcher role through in_pty. Checks the role’s exit status, then reads the report
Launcher roleRuns the same test binary in a separate process on the private PTY. Its linked runner supervises the child. Reports foreground values and child status
ChildRuns the shell script that exits with status 23. The report’s code field holds this status

This test checks final foreground ownership. It does not check recovery after a mode change. The nearby raw-mode test changes the modes and verifies that the change occurred before it checks recovery.

Test the command boundary

In crates/ravel/tests/cli.rs, Fixture gives the executable an empty environment with a private HOME, TMPDIR and working directory. Its PATH contains /usr/bin:/bin. The selecting helper creates a TypeScript policy that selects /bin/sh. The real compiled worker evaluates that policy.

Fragment from the scratch copy of crates/ravel/tests/cli.rs: this test omits the imports and Fixture definition.

#![allow(unused)]
fn main() {
#[test]
fn book_result_keeps_spaces() {
    let fixture = Fixture::new();
    let policy = fixture.selecting(r#""$1" end-session -- "$2""#, "  done  ");
    let output = fixture.start(&policy, "Check spaces.");

    assert!(
        output.status.success(),
        "{}",
        String::from_utf8_lossy(&output.stderr)
    );
    assert_eq!(output.stdout, b"  done  ");
    assert_eq!(fs::read_dir(fixture.root.join("tmp")).unwrap().count(), 0);
}
}

The helper supplies the built Ravel executable as $1 and the result as $2. The shell sends the result with end-session. The assertions check success, unchanged spaces and cleanup of the fixture’s temporary directory. A parser test alone cannot check this path through both executables.

Test a local rule

A CLI unit test can check the argument parser without a worker or child process. The separator -- makes a result such as --help into data.

Fragment from the scratch copy of crates/ravel/src/cli.rs: add this test module at file scope. The fragment omits the argument definitions above it.

#![allow(unused)]
fn main() {
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn book_result_after_separator_is_data() {
        let cli = Cli::try_parse_from(["ravel", "end-session", "--", "--help"]).unwrap();
        let Command::EndSession { result } = cli.command else {
            panic!("expected end-session");
        };
        assert_eq!(result, "--help");
    }
}
}

The parser returns Command::EndSession with the unchanged value. This test does not call end-session or need a result channel. The command-boundary tests cover the later effect of that command.

Install and test the installed pair

task install builds a release CLI and its matched worker. It copies the pair, SDK files, examples and notices into PREFIX, then tests that installation. The default prefix is ~/.local. With an explicit prefix, a contributor can test a build and keep their usual installation.

  2. Run task install with that prefix.
  3. Check the command’s status and the worker log that it names.

Check the book

Book checks are separate from task check. A source change can make a quoted excerpt stale even when every Rust test passes. A documentation change can break a command example without a change to product code.

task docs:book first builds the book, then serves it at http://127.0.0.1:8775. The server rebuilds after a source change. PORT=… selects another port. task docs:book:build only builds, under target/book. Its script, scripts/book.sh, fails on an mdBook ERROR or WARN diagnostic, even if mdBook exits with status 0. A successful build does not establish that every link resolves or that a figure is legible.

The table matches each kind of book change to the check that can detect a related defect.

Figure checks use the pinned Typst tool, packages and fonts from task setup. They render into a scratch directory. task docs:figures:update instead writes the SVGs and .layout.json files beside their .typ sources. After an intended figure change, run the update task, inspect the diff and view the built page. Then run the comparison again.

The figure convention describes the shared modules and visual checks. Equality with a fresh render does not establish that a diagram explains the right behaviour.

The example check rebuilds the pair. It evaluates real TypeScript policies and runs fake programs with a private home, temporary directory and PATH. Standard input is /dev/null. It compares the declared streams and exit status, with only the scratch path normalised. Its summary reports a skipped example as a skip, not as a pass.

Fragments do not run. The check also does not compare source excerpts. The example convention defines labels, output claims and platform requirements.

The excerpt check needs no build. Its comparison preserves spaces and indentation. It rejects untracked sources, symbolic links and generated paths. An exact quotation can still have an incorrect explanation. The excerpt convention describes the label and comparison.

The STE and prose-break tasks report problems without failure unless you pass --strict. By default, the STE check examines all chapter files, SUMMARY.md, CONTEXT.md, README.md and the text of each figure layout record. The prose-break check examines the chapters. A table, figure or code block breaks a prose run. Headings and lists do not.

Neither check can establish clear explanations or compliance with every STE rule. A human read still checks meaning, order and use of active verbs.

The checkers have their own tests. A control gives a checker a known bad input and requires it to reject that input. A mutant removes a safeguard from a copy of the checker. A control then needs to fail against that copy. These tests help show that a clean report has a useful meaning. The table identifies the controls to run after a change to a checker.

Keep tests separate from live sessions

A test can run inside an LLM session that Ravel supervises. If a test inherits that session’s real completion path, its end-session call can stop the developer’s session. The test boundary therefore removes inherited authority before it creates its own fixture inputs. The table maps each test boundary to its guard and the source that applies it.

BoundaryGuardSource
Cargo commandsForce the listed session controls to empty values.cargo/config.toml
Runner subprocess helpersRemove those names from commands, or pass the names as runner scrub controlscrates/keyed-launch/tests/support/mod.rs
CLI and hostile-runtime fixturesUse env_clear(), a private HOME and TMPDIR, and a fixture PATHcrates/ravel/tests/cli.rs and crates/ravel/tests/support/
Installed smokeStart with env -i, then supply only fixture inputscrates/ravel/scripts/dispatch.sh and installed-smoke.sh

The Cargo guards cover these names:

  • GROVE_LAUNCH_DIR, GROVE_SIGNAL_FILE and GROVE_RUN_SIGNAL_FILE.
  • HARNESS_DISPATCH_EXIT_FILE, HARNESS_DISPATCH_RUN_ID and HARNESS_DISPATCH_STATE_DIR.
  • RAVEL_EXIT_FILE, RAVEL_RUN_ID and RAVEL_STATE_DIR.

An empty value disables the inherited authority. It does not redirect authority to another path. The runner helpers also protect direct subprocess invocations that do not pass through Cargo. The CLI fixtures create temporary policies, so tests do not need the developer’s personal owner policy.

The GROVE_* and HARNESS_DISPATCH_* names deliberately remain in these guards. They protect tests from older enclosing-session controls. They are safety exceptions that remain from the extraction of Ravel, not product dependencies. Paths in source provenance and the retired-project record give historical attribution. Ravel does not load those projects or interpret their task trees. The caller-reference inventory classifies these references in source files and dotfiles.

For a new subprocess test, reuse the fixture at the chosen seam. Supply only the environment values that the case needs. If the case needs a result channel, create that channel inside its temporary fixture. Never supply the enclosing session’s real completion path.
