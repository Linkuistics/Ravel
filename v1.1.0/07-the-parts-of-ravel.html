The Ravel book

The parts of Ravel

Ravel separates the choice of a command from the supervision of that command. The owner policy chooses a program. The Ravel CLI checks that choice, runs the program and decides the final outcome. The caller interprets the result. A session is one start-session invocation, from the request to the reported outcome.

This chapter explains the parts of the source that hold those roles. After it, you can locate each part and explain why Ravel uses TypeScript and two Rust packages. Chapter 8 follows one session through the functions. Chapter 9 explains the process and terminal mechanics.

The workspace contains two Rust packages: ravel and keyed-launch. The policy worker is a separate TypeScript build within crates/ravel. The table separates source locations from process boundaries: a package or library does not always correspond to a separate process.

The runner is library code, not another service. end-session is another invocation of the same ravel executable, not a request to a persistent daemon.

The Ravel CLI coordinates the session

The CLI connects the policy’s selection to the supervision of the job. Its choice.rs prepares the request and obtains a checked policy response. Its run.rs creates a fresh result channel and gives that channel to the runner with the selected command. After supervision, the CLI combines the result, cancellation and cleanup reports before it writes to standard output.

The ravel process keeps the caller’s environment and the authority over the terminal while policy code runs in the worker. It also reserves standard output for the result. The standard output of the managed process and Ravel’s diagnostics go to standard error. A policy response cannot write the session’s final result.

The package has a library target as well as an executable target. The library exports SessionChannel, publish_result and end_session, with the result constants. The executable uses this library and keyed-launch. This division lets the result-channel tests compose a channel with a runner without policy evaluation.

The CLI retains a coordination cost. Neither the worker nor the runner knows all the conditions for a successful Ravel session. For example, a runner can report a reaped child while the CLI still owes temporary-file cleanup. A change to final output or failure precedence therefore belongs in the CLI’s coordination code.

The worker executes TypeScript before the launch

Owner configuration is executable TypeScript. A policy can import modules, use asynchronous functions and read files or network services. A static table parser cannot preserve that contract. Bun supplies the language runtime and module support. Ravel does not implement another TypeScript engine.

The build compiles the worker and its Bun runtime into ravel-policy. An installed Ravel therefore needs no separate Bun or Node.js installation. Rust owns supervision, while TypeScript supplies the policy execution environment. This choice costs a second build tool, a larger executable, the licence notices of the Bun runtime and checks on each delivery target.

The worker is a separate process so owner code does not execute inside the process that supervises the session. In worker.rs, the CLI starts it with a cleared environment, null standard input and a private socket at file descriptor 3. The worker’s standard output and standard error carry bounded diagnostics. Length-prefixed JSON messages on the socket carry the protocol.

The CLI supplies the base environment and permitted grants. It also sets BUN_RUNTIME_TRANSPILER_CACHE_PATH=0 to disable Bun’s runtime transpiler cache. environment.rs excludes RAVEL_* from grants, so a nested caller cannot pass its RAVEL_EXIT_FILE to the worker through this path. The CLI allocates the new session’s result channel only after policy evaluation succeeds. Thus, the worker receives neither session’s session-result context.

The worker stops before the managed process starts. A valid response does not let it continue beside the managed process. The CLI closes the protocol socket, ends the worker and confirms its reap. A parent reaps a child when it collects the exit status of that child. The CLI also removes the worker’s private directory.

This order closes the policy phase before the job phase starts. Thus the worker’s protocol messages and diagnostics cannot occur during the managed launch. The order also lets the CLI stop the session when worker cleanup fails, before the selected program can act.

The separate process is not a sandbox for hostile owner code. Policy is trusted code. It can start detached children, which the worker cleanup guarantee does not cover. Same-user code can also tamper with files. Chapter 2 explains how these controls differ from the confinement of a managed process.

Three parts of Ravel control the worker’s startup. The CLI filters environment variables before the worker starts. The worker build disables dotenv, bunfig and tsconfig autoloading. The worker starts in a private empty directory, then changes to / before it registers embedded imports or loads owner policy. These controls limit the files and variables that can change policy evaluation without a request from the policy.

Package imports still need Bun’s resolver. The build keeps package autoloading enabled. /package.json and /node_modules stay reachable inputs for the resolver. The module-resolution reference gives the supported import rules and their limits. A runtime replacement needs to preserve those rules as well as TypeScript syntax.

The SDK describes the policy interface

The SDK supplies the types for a policy, its request and its policy context. It also supplies types for the selected command or refusal. definePolicy returns its argument unchanged. Its purpose is to let the TypeScript checker check a policy object and infer the parameter types. The CLI still checks the data that crosses the worker socket at runtime.

The table pairs each SDK facility with its limit, so a policy author can distinguish type support from runtime checks and authority.

The worker embeds ravel/sdk and ravel/examples/static. Exact imports of those names use the embedded modules. The installation also supplies source and declarations for configuration authors. An edit to those installed source files does not replace the embedded modules.

The compatibility promise includes the supported owner policies, SDK use, settings and policy discovery. The CLI still uses the default policy path or an explicit --config path. Settings stay at their account path when the explicit policy path changes. The policy chapter teaches this interface. A change to Ravel’s internal structure does not justify a new configuration format.

A new command choice usually belongs in owner policy alone. A new SDK field crosses more boundaries: its TypeScript declaration, worker messages and Rust validation need to agree. The split leaves that coordination cost with Ravel’s developers.

The runner owns the local job mechanics

keyed-launch contains the process-group setup, escalation, reap and terminal recovery, with Rust launch types as their interface. It forwards cancellation signals to the job. Argv holds a program and its arguments as separate words. Launch adds the working directory, environment removals and grants, an optional completion channel, signal state and escalation durations. The runner spawns the command directly. A shell participates only when the command selects one.

The runner does not choose a policy or interpret provider and model labels. It also does not read the Ravel result. Its completion channel tells it only that a file appeared. Its Rust result is Ended or LaunchError, not the opaque result that the caller receives.

The table locates the runner interfaces through which the Ravel CLI supplies launch controls and receives job observations.

The separate Rust package lets developers exercise job mechanics without the TypeScript worker or Ravel’s policy conventions. Its only production dependency is libc, which supplies operating-system calls. A correction to terminal recovery can stay inside the runner while the policy interface stays unchanged. Chapter 9 explains those mechanics and their limits.

The code that calls the runner is its consumer. In Ravel, the Ravel CLI is the consumer. It supplies the environment rules, completion channel and escalation durations. It checks Ended.group before it acts on completion, and it keeps the operation reports that Ended carries. The runner can change process-wide signal state, and its return does not restore a host for unrelated future work.

Ravel supports no separate component. Its runner serves the Ravel CLI, which supervises one session and then exits. Another program invokes the Ravel CLI as a child process and leaves supervision to it. These private packages do not establish a contract for a persistent runner.

The result channel carries the value

The result channel adds contents to the runner’s file-appearance mechanism. SessionChannel owns a private temporary directory, the completion path and an open directory handle for reads. end_session obtains the destination from RAVEL_EXIT_FILE. publish_result writes a complete temporary file, then tries a hard link that cannot replace an earlier result.

The runner observes the file’s appearance. The result-channel code reads the contents and rejects invalid files. Its result_after checks the group state and cancellation in the supplied Ended. An empty string is a sent result. An absent file is no result.

The table shows why a successful send or a runner observation alone cannot establish a successful Ravel session.

PartWhat it knowsWhat it cannot establish alone
end-sessionThe inherited destination and whether the send succeededWhether supervision and cleanup succeeded

The Ravel CLI pairs the channel with the launch. The Rust type of SessionChannel::result_after accepts an Ended from any launch. run.rs passes the outcome of the launch that received that channel. It then explicitly closes the channel and checks the other cleanup results. A readable file alone cannot establish success.

A change to result storage therefore affects the result channel, the runner’s observation and the CLI’s coordination. It does not require a new policy choice. The result channel keeps its file format private, so owner policy and callers do not depend on it. But the CLI still needs to combine these observations in the correct order. Chapter 8 follows that order and the failure paths.

The program contract stays loose

The policy selects a program, Ravel runs it, and a program in the session sends one value with end-session. Ravel expects a harness in normal use, but it requires no model-provider interface from the selected program. The policy decides whether the command receives the prompt.

This separation appears in the code, not only in the examples. Rust checks the selection’s shape in policy.rs. Then run.rs constructs Argv from the selected executable and argument words. The runner adds no prompt argument. end_session accepts text and uses the inherited path. The final CLI write returns that text unchanged after successful cleanup.

The table shows which program, prompt and result decisions can change while the interfaces between the parts stay unchanged.

The command still needs to be executable, and a successful session still needs a sent result and successful cleanup. A program that exits with status zero without a result does not complete that contract. The complete example in chapter 3 uses a fake agent to demonstrate the contract without a real model.

The installed pair stays together

An installation contains bin/ravel and libexec/ravel/ravel-policy. The CLI locates the worker relative to its own canonical executable path. A symlink to the CLI therefore keeps the same worker. The CLI does not select the worker through PATH.

Before it sends the policy request, the CLI checks the worker’s protocol, package version and source identity. The source identity is a SHA-256 digest that both builds derive from the same worker sources and build inputs. A missing or incompatible worker stops selection. This check pairs builds. It does not authenticate files against the owner of the installation.

It does not establish compatibility with every owner helper, independent component use or safe concurrent use within another host.
