The Ravel book

Deliver Ravel

A release carries a matched pair: the Ravel CLI and its policy worker. Chapter 7 explains why the pair stays together. An archive check establishes that this pair has the right files and can run outside the checkout. A version number alone establishes neither fact.

The book that a release carries teaches this pair as one delivered tool. Ravel supports no separate component. The private runner serves the Ravel CLI, which supervises one session and then exits. The runner’s return does not restore process-wide signal state. Thus, another program invokes the Ravel CLI as a child process. The book explains that interface and the limits of the private package.

Start with chapter 10’s install and smoke tasks. Those tasks test a local installation. This chapter extends that check to archives and the environments where their programs run.

Keep the version and pair together

The workspace has one Ravel version, independent of the version of any caller. Cargo.toml supplies it to both Rust packages, and the worker build reads the Ravel package version. The checkout used for this chapter has version 1.0.0. Its local tags include v0.1.0 and v1.0.0, and CHANGELOG.md describes both.

An unreleased archive uses the checkout’s version even when its source differs from that version’s release tag. Thus, a local archive named with v1.0.0 can contain later changes. Its name does not make it the released artifact.

Before the Ravel CLI sends the owner policy for evaluation, it checks three worker values:

ValueWhat it establishes
Protocol numberBoth programs use protocol 1
Package versionBoth programs report the same Ravel version
Source identityBoth builds used the same worker source inputs

The source identity is a SHA-256 digest. Relative to crates/ravel, its inputs are the TypeScript files under worker/src, worker/sdk and worker/examples, both worker tsconfigs, and scripts/dispatch.sh. Both builds sort those paths, hash each file, then hash the same list of paths and digests.

The source identity shows that two builds belong together. It does not authenticate an installation or cover every Rust source file. A worker with a different protocol, version or identity causes worker_identity_mismatch, with exit status 5, before policy evaluation. A probe worker that the tests build also has a different identity, and causes the same failure. To correct a mismatch, rebuild and install the pair together.

The CLI finds libexec/ravel/ravel-policy relative to its own canonical path, which is its path with all symlinks resolved. A symlink to the CLI therefore still reaches that CLI’s worker. Another worker on PATH cannot replace it. The worker contains Bun 1.4.2, so an installation needs no separate Bun or Node runtime.

Build archives before a release

task release:archives builds local archives without a version cut. With no TARGETS argument, it builds these targets:

TargetArchive contents run on
aarch64-apple-darwinApple silicon macOS
aarch64-unknown-linux-gnuArm64 GNU/Linux
x86_64-unknown-linux-gnux86-64 GNU/Linux

The target names spell arm64 as aarch64 and x86-64 as x86_64. This chapter uses the target spelling only in target names and in the support statement.

Run the release tasks from the checkout. The full workflow needs an Apple silicon Mac, Bash 4 or later, Task, rustup with Rust 1.85 or later, curl, tar/xz and ShellCheck. The Linux builds also need Zig, cargo-zigbuild and both Linux Rust target libraries. The Linux smoke tests need an available linux/arm64 Docker daemon with kernel 6.7 or later.

The kernel requirement comes from the emulated routes. They register QEMU in a private binfmt_misc instance, which Linux 6.7 and later gives each user namespace. Thus, the registration does not change the Docker host’s own. The requirement applies to the test environment. It is not Ravel’s minimum kernel.

task setup supplies the checkout’s pinned Bun and development dependencies. The release build prefers rustup’s tools on PATH when its shims exist. An explicit RUSTC override can still select another compiler. The release doctor checks the compiler that the build will use and its target libraries. The worker build checks each target’s Bun runtime against a committed SHA-256 digest before compilation. It also generates the SDK declarations.

Fragment: prepare the target libraries and build local archives. This recipe omits tool installation and the command output.

rustup target add aarch64-apple-darwin aarch64-unknown-linux-gnu x86_64-unknown-linux-gnu
task setup
task release:archives

The build writes target/archives/ravel-v<VERSION>-<TARGET>.tar.xz. It clears target/archives before each build, even for one target. Thus, an archive from an earlier build cannot stand in for a target that failed. Each archive first has a temporary filename. The build gives the archive its final filename only after the manifest check passes, then prints its SHA-256 digest.

For a local macOS check, select only the native target. This selection replaces the archive directory’s contents and does not check Linux.

Fragment: build only the macOS archive. This recipe omits setup and output.

task release:archives TARGETS=aarch64-apple-darwin

If an unreleased build fails, correct the reported cause and repeat the task. It creates no release tag or remote release. The later release procedure builds fresh artifacts from the release tag into target/dist.

Check the archive contents

An archive has one top directory, ravel-v<VERSION>-<TARGET>/. That directory is an installation prefix. The manifest in scripts/release-common.sh permits exactly these files and their directories:

Path below the prefixPurpose
bin/ravelRavel CLI executable
libexec/ravel/ravel-policyMatched policy worker executable
libexec/ravel/sdk/index.ts, sdk/index.d.tsSDK source and declarations, both under libexec/ravel
libexec/ravel/examples/static.ts, examples/static.d.tsStatic example source and declarations, both under libexec/ravel
libexec/ravel/examples/sample.tsSample that an owner can copy and edit
libexec/ravel/notices/NOTICES.md, notices/bun-LICENSE.mdRuntime notices, both under libexec/ravel
README.md, LICENSEProject entry and licence

Chapter 6’s installed-layout view shows how the CLI, worker, SDK and examples fit together. In the checkout, the runtime notices are under crates/ravel/notices/. In an installation, they are under PREFIX/libexec/ravel/notices/.

The manifest check rejects extra files and directories, missing files, symlinks in place of files, and executables without execute permission. Caller programs, caller adapters, owner configuration, choice files, development dependencies and probe directories do not belong in an archive. The pack step also excludes macOS extended attributes and their AppleDouble metadata files.

task release:test tests the manifest check. It compares the manifest with a fresh production worker build, then uses deliberately incorrect archives. Each omitted file causes a failure. Other controls add unwanted assets, change types or permissions, and add macOS metadata. The task needs no Docker, but its metadata controls use macOS tools.

Fragment: test the manifest check. This recipe omits setup and output.

task release:test

The manifest check examines layout, types and execute permission. It does not prove that the file at the worker path is the right program.

The installed smoke test checks the pair through a real policy. The hostile-runtime suite separately puts probe workers at the worker path. It checks that each probe causes worker_identity_mismatch. Those tests need the probe workers that task probes builds. task check runs that build too.

Test the installed archive

task release:smoke rebuilds the selected archives, then tests them. With no selection, every target runs. A missing tool, failed target or unrun selected target fails the task. There is no successful skip path.

Fragment: rebuild and test all target archives. This recipe omits setup and per-target output.

task release:smoke

Each environment extracts its archive with its own tar into a fresh prefix. It checks the CLI version and runs crates/ravel/scripts/installed-smoke.sh. That script tests both the direct CLI path and a relative symlink from another prefix. Its private utility PATH has no Bun, Node or Grove. It supplies a fresh home and temporary directory through a cleared environment.

The test uses a shell fake agent, a real policy worker and installed assets. Each session returns the opaque result that the fake agent sends with end-session:

CheckWhat the test compares
SDK, static example and copied sampleThe sample uses the selected choice and starts the fake agent
Result valuesOrdinary, empty, multiline and option-like values return unchanged
Child outputChild standard output goes to diagnostics, separate from the result
TypeScript importsA relative helper and a declared package load from the test policy
Policy inputsMeasured policy context and --param values reach the policy
Missing session-result contextend-session fails and writes no result
Temporary resourcesThe sample sessions leave no resources in their temporary directory

No model or personal policy runs. The test does not exercise an interactive terminal or all lifecycle failures. Chapter 9 explains those separate obligations.

Read the platform checks correctly

A platform floor is the oldest library or CPU capability that a check exercises. The Linux CLI builds against glibc 2.17 through Zig. The worker uses its pinned Bun runtime. Both executables then run in the same archive smoke test.

RouteEnvironment and check
macOS arm64Native execution on the Mac that runs the task
Linux arm64, native CPUPinned CentOS 7.9 userland in arm64 Docker, with glibc 2.17
Linux arm64, CPU floorThe same userland under QEMU 10.2.2 with the Cortex-A53 model
Linux x86-64, CPU floorCentOS 7.9 under QEMU 10.2.3 with the Nehalem model

Each Linux route checks that the userland reports glibc 2.17. A probe built for that floor runs. A second probe needs GLIBC_2.25, and the userland rejects it. The two probes show that the environment both runs valid programs and rejects a newer library requirement.

The CPU controls use an instruction above each floor: an Armv8.1 LSE atomic operation for arm64, and AVX2 for x86-64. At the floor, the instruction causes SIGILL. The same probe runs under the same emulator with -cpu max. Thus, the failure at the floor comes from the CPU model, not from a defective probe.

Each emulated route checks that every ELF executable in the archive, the CLI and the worker included, matches its emulator registration. Thus, those executables run through QEMU, not directly on the host CPU. The routes also check guest address bounds and the presence of the vDSO, a kernel-supplied interface mapped into a process. The test programs run without network access, as an unprivileged user, with read-only test inputs.

These checks establish different limits:

ObservationLimit
Native macOS smoke passedIt checks the host macOS version, not an older macOS floor
glibc and CPU controls passedThey check these userlands and CPU models, not every distribution or processor
Linux container or user-mode QEMU passedIt uses the host kernel and does not measure a minimum kernel version
Archive smoke passedIt checks the installed workflow, not the full process and terminal campaign

The native-entry campaign measured aarch64 macOS and aarch64 Linux. x86_64 Linux is built and run only under emulation. Native x86-64 Linux remains unqualified, with qualification tracked in Linkuistics/Ravel#1. An archive smoke pass does not change that support statement.

Chapter 10’s evidence map locates the separate runtime, archive and native-entry records. Those records name their source revisions and measured environments. After a source or runtime change, run task release:smoke again. It rebuilds the archives before it tests them.

Prepare and test the Homebrew formula

A Homebrew formula tells Homebrew which archive to fetch, how to install it, and how to test the installation. Ravel’s template is scripts/templates/ravel.rb.tmpl. It selects one of the three target archives and installs its bin and libexec directories. It has no Grove dependency.

task release:formula requires all three current-version archives in target/archives. It builds the four native probe workers, checks each archive against the manifest, and fills the template with the version and archive digests. An unexpanded placeholder fails the task.

Fragment: after the full archive smoke task, test the formula. This recipe omits setup, archive construction and output.

task release:formula

The task needs Homebrew on Apple silicon macOS. It loads the rendered formula through Homebrew’s Ruby library and calls its actual install and test methods. Only the installation prefix and test directory change to private temporary directories. The task creates no Homebrew keg and edits no tap. A keg is Homebrew’s directory for one installed version.

Formula checkWhat it establishes
Installed pathsThe temporary prefix has exactly the archive’s bin and libexec contents
Real policy and shell fake agentThe SDK and static example work through a symlink to the installed CLI
Result comparisonsOrdinary, empty, multiline and option-like results return unchanged
Cleared environmentThe session uses private home and temporary directories, with no host TypeScript runtime
Temporary resourcesThe formula’s sessions leave their temporary directory empty
Four substituted workersEach probe causes worker_identity_mismatch, with exit status 5

The normal formula test first checks the matched production worker. Then the identity controls substitute autoload, tsconfig, unregistered and unmoved probe workers at that worker’s path. After the controls pass, the test restores the production worker. All these operations stay in the temporary prefix, and no model runs.

The output, target/archives/ravel.rb, is preparation material. Its URLs use the checkout’s version, but its digests describe the local archives. Those bytes can differ from the assets at the release URLs, even when the version agrees. Do not copy this formula into a tap or upload these archives as a release. The version-cut task builds fresh archives from the tag and tests their formula.

The final installation uses linkuistics/taps/ravel. Its brew test ravel checks the real installed keg. The temporary-prefix check above does not replace that final check.

Prepare a version cut

A version cut selects the next version and creates its source commit and tag. Ravel’s stable CLI uses semantic versions: compatible changes use patch or minor releases, and incompatible changes require a major release.

TaskEffect
release:doctorCheck tools, target libraries, host, GitHub authentication, the book version line and the Pages setting
release:notesFill empty Unreleased notes, or replace them with an explicit reviewed body
release:lifecycle:testTest release order, refusals, notes, book delivery and recovery in isolated repositories
release:patchCut, deliver and install the next patch release
release:minorCut, deliver and install the next minor release
release:majorCut, deliver and install the next major release

The three version-cut tasks have public effects. They push source and a tag, create a GitHub release, put the book on the Pages branch and update the tap. They also install or upgrade local Ravel. Choose one task for the intended change. Do not run them as a sequence.

In addition to the archive tools, delivery needs jj, Git, jq, Homebrew and cargo-release 1.1.2. It also needs authenticated gh access to Linkuistics/Ravel and a clean, synchronised clone of linkuistics/taps.

task setup supplies the pinned mdBook 0.5.4 as well as Bun. The lifecycle suite needs that setup because it builds books in its fixtures. The tap path defaults to ~/Development/homebrew-taps. If the clone is elsewhere, set RAVEL_TAP_DIR to its path. Put Homebrew’s Bash before /bin on PATH, so the scripts use Bash 4 or later.

The release procedure uses jj (Jujutsu), a version-control tool that can share a repository with Git. In jj, each change has a stable change ID and a description, which jj describe sets. A bookmark, such as main, is jj’s name for a branch. A colocated workspace has both .jj and .git in one directory.

Run the cut from Ravel’s default colocated jj workspace. The release task refuses other directories. First, give each intended change a description and put it on local main. The preparation step of the release task saves the current change ID, then creates a clean child of main. Unrelated work stays at the saved ID. Later, jj edit SAVED_CHANGE_ID returns to that work.

Fragment: check release prerequisites and remote tags. This recipe omits tool installation, notes review and the version cut. The tap check fetches its remote.

task release:doctor
scripts/release-publish.sh --check-tap
scripts/release-book.sh check-remote
git ls-remote --tags origin
task release:lifecycle:test

The doctor reports missing prerequisites and their remedies. It checks the pinned mdBook and reads the repository’s Pages setting. Disabled Pages produces a note, because an administrator enables it after the first book reaches the branch. A different branch, folder or deployment mode fails the check.

The separate check-remote command checks that Git can read origin, the remote that holds the Pages branch. Neither check changes the remote.

The doctor does not test tap synchronisation or prove that a prior release is complete. Preparation makes those separate checks. It fetches origin and refuses conflicts, divergence from origin, undescribed new changes on main, and version work outside main.

For the current version, preparation requires local and remote tags that agree, a complete non-draft GitHub release, and the remote tap’s version line. It also requires new commits after the baseline tag. An incomplete prior release therefore leads to recovery, not another version cut. The special absent-tag case applies only to version 0.0.0 with no local or remote version tags. The historical structured-plan-migration tag is not a release baseline.

Write meaningful release notes under the single ## Unreleased heading in CHANGELOG.md. Preparation preserves a nonempty body byte for byte. For an empty body, it uses first lines from nonempty, described commits since the current version tag, then commits those notes to main through jj. Only the initial 0.0.0 case uses repository history without a baseline tag. Review generated notes because commit descriptions can contain internal details.

Fragment: replace the notes with reviewed prose. This recipe omits creation of the input file and the later jj commit. The changelog must match main first.

task release:notes -- --to main --from-file /absolute/path/reviewed-body.md

Without arguments, release:notes uses the current jj revision and fills only an empty body. --from-file deliberately replaces a nonempty body too. The input contains a section body, with no level-two heading. The script preserves versioned sections and refuses missing, empty or invalid input.

It also refuses missing or duplicate Unreleased headings, an ambiguous revision, or a changelog that differs from the selected revision. Commit reviewed notes through jj before the cut. This procedure runs no harness or model.

Cut and deliver a release

Each version-cut task calls the internal release task, which runs the steps below in order. The task first creates the .jj/release-lock directory. While it exists, a second release task stops. A defer command in the task removes the lock when the task succeeds or fails.

StepWhat it changes or checks
Check prerequisitesRun the doctor, tap preflight and Pages remote check
Prepare mainPreserve unrelated work, check the prior release and prepare notes
Recheck the tap and sourceRepeat tap preflight, then run task check
Preview and cutRun cargo-release first as a preview without --execute, then with --execute --no-confirm
Check the tagged bookRequire the tag’s chapter 3 version line to match the cut
Record and build the bookMove main to the release commit, then build the tag’s book into target/book-release/vX.Y.Z/
Build the archivesBuild all archives into a fresh target/dist
Test the formula and archivesTest the formula in temporary prefixes, then run the smoke test for every target at its floors
Send the source and releasePush main, push the tag and create the GitHub release
Deliver the book and formulaPut the book on the Pages branch, check it with verify, then update the tap
Check the installationUpdate Homebrew, install or upgrade Ravel, run its test, and check its version and GitHub assets
Check the book on the siteRun scripts/release-book.sh live vX.Y.Z against the served pages

The activity shows which checks precede the first public write and where each failure resumes. After a version write, recovery keeps the selected version.

The eight grey exits refer to the recovery table. Each decision summarises the checks since the previous decision. A failure stops at its own step, before the later actions in that group. The book build stays local. The Pages branch check precedes the tap update. The served-site check comes last.

Open the release activity at full size.

release.toml disables cargo-release pushes and crates.io uploads. Cargo-release creates the local version commit and tag through Git. The procedure otherwise uses jj. This commit and the tag operations are its Git exceptions. The runner package, keyed-launch, sets release = false, so cargo-release does not release it separately. Only the ravel package’s configuration holds the changelog replacement.

The changelog replacement requires exactly one whole-line Unreleased heading. It inserts the version heading below a fresh Unreleased heading. The notes therefore become that version’s notes. The same release commit updates the manifests, lockfile and book version line.

The archive build checks the clean source, exact release tag and workspace version before it clears target/dist. It builds all three targets, their probe controls and the formula. The next step runs the smoke test for every target from that directory. A failed build, formula test or smoke test stops before any push.

Before it creates the GitHub release, scripts/release-publish.sh rechecks the tap, archive manifests and rendered formula. It requires exactly three archives and a formula that matches their version and digests. The GitHub release takes its notes from that version’s changelog section. The tap update changes only Formula/ravel.rb. It retains ravel-lite.rb, which supplies a separate command, and every unrelated formula.

The final version check uses the binary under brew --prefix, not the first ravel on PATH. A local task install can put another copy earlier on PATH. The task also inspects GitHub’s assets and checks their count. This release procedure installs Ravel alone. It does not replace Grove or the legacy harness-dispatch installation.

Keep a delivery record outside the book. Record the source revision, each archive’s SHA-256 digest, each target route and control, and any missing prerequisite. The check wrapper prints a summary and the full log path under target/release-archives.*, target/release-formula.* or target/release-lifecycle.*. Save the build and floor-smoke output too. These records show whether a result comes from a real target run or from a test of the procedure.

Keep the book with its release

Chapter 3’s version line lets a reader compare the book with ravel --version. A checkout between releases can show the placeholder or the last release’s version. Its other text can contain later changes.

The version line is ravel @RAVEL_BOOK_VERSION@ until the first release that carries the book. After it, the line is ravel X.Y.Z. The second replacement in release.toml finds this whole line in docs/book/src/03-a-complete-session.md. It accepts the placeholder or an X.Y.Z version and requires exactly one match. Cargo-release writes the new version into the same commit and tag as the product. The line is ordinary Markdown text, so raw-file, GitHub and mdBook views use the same value.

GuardWhat it reads and refuses
scripts/release-book-version.sh readyRead the checkout page. Refuse a missing page, or any count other than one line of the form ravel <version or placeholder>
scripts/release-book-version.sh released vX.Y.ZRead the page at the tag. Refuse an unreadable tag/page, a different version, duplicate or absent lines, or a placeholder anywhere in the page

The doctor runs ready before the cut. The task runs released after the cut and before the archive build. ready checks that replacement is possible. It does not require the current line to agree with the workspace version. The second guard checks what the tag actually carries. If it refuses, the cut stays local, and the task pushes nothing.

If ready refuses, edit chapter 3 until it has exactly one version line. Then run task release:doctor again. If released refuses, the local tag exists already. Use the local-cut rows of the recovery table, and do not start another version cut.

Build and deliver the tagged book

The release procedure puts each book at https://linkuistics.github.io/Ravel/vX.Y.Z/, where X.Y.Z is the release version. The root page lists releases, newest first. The address is the script’s default. No public delivery has confirmed it yet.

The Pages branch, gh-pages, holds one vX.Y.Z/ directory per release, a root index.html and an empty .nojekyll file. A release directory is final. The script refuses different bytes in a release directory that already holds a book. A retry with the same bytes adds no commit to the branch.

This branch preserves earlier books when a new release adds its directory. A custom workflow would need to preserve them in its site artifact too. An artifact with only the newest book would lose those earlier books. Ravel needs no custom workflow file. GitHub still uses its own deployment workflow for the branch and recognises .nojekyll for prebuilt content. GitHub’s source settings explain this branch mode.

scripts/release-book.sh separates the work into four modes:

ModeWork and refusals
build vX.Y.ZExport the tag’s book and build it into the stage with pinned mdBook. Refuse an absent tag, a wrong source version or export file count, and mdBook ERROR or WARN output. Refuse missing output pages, a wrong rendered version, a chapter 3 placeholder, or symlinks in the output
publish vX.Y.ZPut the staged book on gh-pages. Refuse an absent stage, a changed tag commit or changed staged files. Require the same tag commit on the remote and a complete non-draft GitHub release. Refuse a release directory that already holds different bytes, or a site at the script’s size threshold
verify vX.Y.ZCheck the remote branch against the stage. Refuse an absent or changed stage, an absent branch, root .nojekyll or release directory, different book contents, or an index that omits the release
live vX.Y.ZRead the served chapter 3 and root page. Refuse a wrong version code block or an absent release link after the last attempt

build uses git archive on the tag’s commit. Changes to the checkout’s book text cannot enter that export. After the tag and version checks pass, the build removes the old stage before it exports and builds the book again. The stage is target/book-release/vX.Y.Z/. Beside it, vX.Y.Z.identity records the commit, mdBook version and a digest of the staged files. The identity file does not go to Pages.

publish uses a temporary clone and a push without force. It does not edit the checkout or its jj state. Before the push, the script requires a GitHub release with exactly the three expected, nonempty archive assets. verify then checks branch contents, not the pages that the site serves. live makes up to 30 attempts by default, with ten seconds between attempts.

release-publish.sh puts the book on the Pages branch after the GitHub release. It updates the tap only after the book’s verify step passes. Thus, the Pages branch holds a release’s book before the tap offers that release. Pages can still take time to serve the new files, so the task checks the served pages last.

The Pages limits include a 1 GB site maximum, with soft limits of 100 GB per month and ten builds per hour. The script refuses a total site size of 1,000,000 KB or more, as reported by du. A local build of the current book in target/book uses about 7 MB. Later releases add their own directories, so the site grows.

The book stays outside the product archives and the worker source identity. The local docs:book:build task writes target/book, and docs:book serves it locally. Neither task sends files to Pages.

Set up Pages for the first release

A repository administrator enables Pages one time. The release script creates the branch but does not change the Pages setting.

  1. Run the first version cut. Its publish step creates gh-pages.
  2. In the repository’s Settings → Pages, select “Deploy from a branch”.
  3. Select the gh-pages branch and the / (root) folder.
  4. Save the setting.
  5. After Pages is enabled, run scripts/release-book.sh live vX.Y.Z for that release.

The branch must exist before step 2. If Pages is disabled during the first release, the release task stops at its final live check. Earlier successful release steps stay complete. After an administrator enables Pages, repeat only live.

An administrator can use the Pages REST endpoint instead of the settings page. The endpoint requires suitable repository rights.

Fragment: enable Pages after the first branch push. This recipe omits the release and the final live check.

gh api -X POST repos/Linkuistics/Ravel/pages \
  -f build_type=legacy -f 'source[branch]=gh-pages' -f 'source[path]=/'

No release carries the book yet. The newest release tag, v1.0.0, has no docs/book directory. Until a release carries it, there is no book on GitHub Pages to use. Read the checkout’s Markdown or local build. Check its version line. A pass of the version-line guards does not show a book on GitHub Pages.

The lifecycle suite’s fixtures build books with pinned mdBook and use a local bare remote, substituted GitHub responses and a loopback web server. They cannot establish the served public address, an administrator’s call to the create endpoint, the Pages delay or GitHub’s view of the book. An organisation domain setting can change the address.

Recover a partial release without another bump

After any cut step partly succeeds, do not repeat release:patch, release:minor or release:major. Another version cut, a bump, selects a new version and leaves the unfinished release incomplete under the old one. First inspect the source, local and remote tags, GitHub assets and tap.

Fragment: inspect a partial release. Replace vX.Y.Z with its selected tag. This recipe omits the tap inspection and every correction.

jj st
jj log --no-pager
git status --short
git tag --list 'v*'
git ls-remote --tags origin
gh release view vX.Y.Z --repo Linkuistics/Ravel --json isDraft,assets

If Task stopped abruptly, its lock can remain. Before you remove .jj/release-lock with rmdir, check that no release process remains. Preserve the saved jj change and each partial release write. The table has eight recovery branches. Choose the row for the last step that completed.

Failure pointNext action

For a partial local cut, inspect the cargo-release preview and log. Reconcile the workspace manifests and Cargo.lock to the selected version. If its changelog heading is absent and Unreleased still holds its notes, run cargo release replace --execute --no-confirm once. Do not repeat that replacement after the version heading exists. If only the book line needs a correction, correct that line without another changelog replacement.

When the manifests and lockfile agree, check them. Then describe the release change in jj. Move main to that commit and create its empty successor.

Create only a missing local tag at the intended commit. The release procedure uses an annotated Git tag for this operation. Inspect any tag that already exists. Never overwrite a tag to hide a source mismatch.

For a failed build or smoke test, return to a clean child of the release commit with jj new RELEASE_COMMIT. If the cut did not move main, set it to that commit with jj bookmark set main -r RELEASE_COMMIT.

Fragment: check the tag’s book line, build its book, then rebuild and test the release archives. Replace vX.Y.Z with the selected tag. This recipe omits source corrections and pushes.

scripts/release-book-version.sh released vX.Y.Z
scripts/release-book.sh build vX.Y.Z
scripts/release-build.sh

If the release source itself needs a correction, give the correction its own described change. Then decide which version and tag carry it. Do not move a tag that is already public. A correction in the checkout alone cannot correct the book page that released reads at the tag. If the source and the tag disagree, stop until that decision is made.

After all smoke routes pass, retry only a missing jj git push -b main or git push origin vX.Y.Z. Before you continue, check that the remote tag resolves to the release commit. Do not force a public tag.

If GitHub has no release for the tag, run scripts/release-publish.sh after the smoke test passes. If the release exists, upload only missing current archives with gh release upload. Inspect assets that already exist. Do not overwrite them. If the release is a draft, remove its draft status with gh release edit after all three assets are complete. If the push fails, the branch on the remote stays unchanged. A retry sends the same staged bytes and adds no commit if the branch already holds them. --tap-only requires a non-draft GitHub release with exactly the three nonempty assets. It downloads them and compares each with the local archive that the smoke test checked. The script does not run the smoke test. Thus, use this mode only after the smoke test passes for the same archives.

  2. Move main to that change.
  3. Create an empty successor.
  4. Push main.
