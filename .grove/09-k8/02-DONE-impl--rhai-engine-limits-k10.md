# rhai-engine-limits-k10

## Goal

Make the Rhai worker safe against a hostile or careless script. Each engine limit, the heap bound, the output bounds and the deadline end the evaluation with the specified code. The Ravel CLI survives and reports it.

## Context

- The input is the worker created by `rhai-policy-worker`. Read its running log first.
- The spec sections are "The policy worker", "Evaluation budgets and their composition" and "Cancellation and deadlines". The table of fixed engine limits is in "The policy worker".
- Rhai 1.27.0 has two known faults that the spec cites. `sleep` blocks the thread for a time that the script chooses. `pad` with an empty padding string loops for ever. Rhai 1.27.1 would fix the second fault, but it is not released.
- The engine limits of Rhai differ between debug and release builds. Set every limit explicitly, so that tests and releases agree.
- Rhai passes limit errors through the boundary of a script function, and `try` does not catch them. A host latch must still refuse when another path swallows one.
- The existing hostile tests in `crates/ravel/tests/hostile.rs` show the pattern. Each hostile class keeps a firing control in the same test.

## Done when

- The worker sets the fixed limits of the spec table: operations, call depth, expression depth, string size, array size, map size, variables and script functions. The worker evaluates on one thread with a stack of 64 MiB.
- A breach ends the evaluation as `script_limit`, and the report names the bound. A script cannot catch it with `try`.
- A counting allocator in the worker enforces the heap bound of 1 GiB. A breach reports `memory_limit`, and the worker exits.
- The worker checks a stop flag at each Rhai operation, so a cooperative script stops at once.
- Tests at the real CLI seam prove each class. The classes are `sleep(600)` at the deadline and the `pad` loop. The others are an array that grows without end, deep recursion, a large string, an endless loop and a `try` around a breach. The `sleep` case exits 124 within the deadline and the teardown bound.
- Tests prove the output bounds. A policy that prints without end ends as `output_limit`. A message above 1 MiB ends as `message_too_large`.
- Tests prove cancellation. INT, TERM and HUP during the evaluation kill and reap the worker, and nothing launches. The exit status is 128 plus the signal number.
- A test proves that a worker killed from outside refuses as `worker_failed`.
- A test guards the closure case of rhaiscript/rhai#1193. Ravel calls named script functions, so a closure that a host calls after the script ends must not occur. The test shows that no such call exists.
- The worker identity checks have tests where the seam allows them. The checks are `worker_missing` and `worker_identity_mismatch`.
- `task check` and `task test` pass. `task test:native-linux` passes once for the worker on a Linux target.

## Notes

- A script cannot reach the heap bound before a size limit fires unless it builds many small values. Pick the hostile cases so that each limit has a case that reaches it first.
- Keep the worker free of a credential and of any file or process access. This leaf adds no host function.

## Decisions (running log)

- One table, `Limit` in `rhai_worker/mod.rs`, holds the name, unit and value of the nine bounds of the spec table (operations, call depth, expression depth, string size, array size, map size, variables, script functions, heap). The worker sets the engine from it. A `ScriptFailure` carries the bound by name (`bound`), and the front turns the name back into the `Bound` of the refusal (`choice::limit_refusal`, origin `fixed`). So `script_limit` and `memory_limit` are exit 3, stage `evaluation`, and name the bound with its value.
- Every limit is set explicitly in `engine.rs`, and `every_limit_of_the_spec_table_is_set_on_the_engine…` asserts each getter. Rhai counts about two expression levels for each pair of parentheses, so "64 at the top level, 32 in a function" is about 32 and 16 nested parentheses. `expressions_nest_to_the_depth_of_their_place` shows that 20 pass at the top level and fail in a function.
- Operations are not an engine limit. `set_max_operations(0)` leaves it off, and the `on_progress` hook counts across the top level and `select` together and ends the run at the 100,000,000th. Reason: Rhai wraps every error that crosses a call of a function pointer (`FnPtr::call_raw`, rhai-1.27.0 `src/types/fn_ptr.rs`) in `ErrorInFunctionCall`, and `is_catchable` returns true for that wrapper (`src/types/error.rs`). So `try { [1].map(|x| { loop {} }) } catch (e) {}` swallows the engine's own `ErrorTooManyOperations`. The hook records the breach in a `Latch` at the moment it happens, and `evaluate_with` reads the latch after the script returns, so the breach refuses whatever the script returned. A swallowed breach also fires again at the next operation, because the count stays over the bound.
- **Finding for the review: the latch reaches only the operations bound and the stop.** Rhai 1.27.0 has no hook for a data-size, call-depth or variable breach, so a script that reaches one of those inside a closure call can still swallow it. Direct `try` does not catch them (tested). I did not find a host-side way to close the closure path without disabling `try` or every higher-order function. I changed the spec sentence "A host latch also refuses when any other path swallows one" to say what the latch covers and what it does not. The rest of the design stands because each swallowed breach was still prevented, and only the refusal is lost.
- Rhai checks a data size when a call returns a value. `push` and an index assignment grow an array or a map in place and are never checked, and an array counts its nested elements, so a loop that pushes arrays fires the array limit through the nested count first. The heap bound is the backstop for in-place growth. The CLI test therefore fills the heap with 400 separate variables that each hold a 900,000-element array, and its control (5 variables) selects. The map-size unit test joins two maps of 600,000 properties with `+`, because the index assignment that builds them is unchecked. The spec says this now ("Rhai checks a data size when a call returns a value").
- Rhai moves the position of a limit error to the call that entered the script function. For `select` that call is the worker's own expression `policy::select(request, context)`, so the position names nothing in the policy. A limit breach in `select` reports no line and column. A breach in the top level keeps its position.
- Heap: `rhai_worker/heap.rs` is the global allocator of the binary. It counts every live byte in the front and in the role, and does nothing else until `heap::arm` runs. The role arms it first, before the hello. The breach cannot allocate, so `arm` encodes the whole `memory_limit` frame ahead of time (leaked), and the breach writes it to fd 3 with `write(2)` and calls `_exit(4)`. The front reads a normal failure frame. The CLI test passes on macOS and in the arm64 Linux container.
- Stop flag: a thread in the role reads the socket after the evaluate frame. The front sends nothing more, so the read returns only when the front closed its end (a conversation dropped at the deadline, or a front that died). It sets the flag, and the progress hook ends the next Rhai operation. A stopped evaluation is an `Err`, and the role exits 2 with no reply. A native call is stopped by the signal that the supervision sends after the close.
- `[profile.dev.package.rhai] opt-level = 3` in the workspace `Cargo.toml`. The endless-loop test runs 100,000,000 operations, which took 14 s with unoptimised Rhai and takes 1.5 s now. Debug assertions stay on. The limits are explicit, so no test depends on the profile.
- Tests. `tests/rhai_limits.rs` (12) at the real CLI: operations, call depth, string, array, the `try` and closure-latch cases, the heap, `sleep(600)` and the `pad` loop at the deadline (exit 124 inside the deadline plus the teardown bound, and the private directory gone), print flood (`output_limit`), a result over 1 MiB (`message_too_large`), INT/TERM/HUP during the evaluation (worker gone by `kill 0`, nothing launched, the front dies of the signal), a worker killed with KILL (`worker_failed`, exit 5), and the closure guard. Every hostile test has a control of the same shape that selects and starts the harness, and the `pad` and `sleep` controls return at once while the hostile cases need the deadline. The engine unit tests cover the limits that need no process (expression depth, functions, variables, map size, the stop flag, the table). The closure guard (rhaiscript/rhai#1193) shows that a returned closure or function pointer is refused at its location, so no call of one can follow.
- The identity checks: `worker_missing` and `worker_identity_mismatch` cannot be produced at the CLI seam, because the worker is the running binary and the test cannot change it. The front unit tests produce them: a program that does not exist, and a real role process that reports another build through the test-only `RAVEL_ROLE_FIXTURE_BUILD` variable (`a_real_worker_of_another_build_refuses…`).
- Gates on macOS: `task check` (format, lint, 435 tests passed, 48 skipped), `task test` (same), `task docs:excerpts` (8 passed) and `task docs:examples` (14 passed). Linux: `task test:native-linux` still fails in its own rustup and Bun steps, as the two earlier leaves logged. I ran the worker tests by hand in the arm64 GNU/Linux container with `RUSTUP_TOOLCHAIN=1.99.1-aarch64-unknown-linux-gnu`. All 57 Rhai unit tests, all 12 limit tests, and 18 of the 19 policy tests pass there. The one failure is the test of the TypeScript path, which needs the Bun worker that the container does not build (it passes on macOS). The campaign itself needs the container toolchain repaired, which no Rhai leaf owns.
