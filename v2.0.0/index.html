The Ravel book

What Ravel is for

Ravel lets a program use an LLM in Claude Code or Codex as one step of its own work. This chapter opens with one such step, a code review. It follows that review from the request to the result. Then it explains which parts of the review apply to every use of Ravel.

You do not run anything in this chapter. Each code block is a fragment, a part of the review or of a real run, and its label says what it omits. Chapter 3, “Run the first session”, gives the first session that you run. It names the directory, each file and each command.

Follow one code review from request to result

An orchestrator is a program that runs LLM work as steps of its own work. Suppose that an orchestrator wants an LLM to review the last commit of a project. The commit changes two files, src/parse.rs and tests/parse.rs. The orchestrator knows these files, because it chose the work. It also knows what it will do after the review.

First, the orchestrator writes a prompt. The prompt is the text that tells the LLM what to do. This prompt also tells the LLM how to report the outcome of the review.

Fragment: the whole prompt file review-prompt.txt of the review example. This block omits the code of the orchestrator that writes the file. Ravel keeps the text unchanged in request.originalPrompt and does not interpret it.

Review the changes to src/parse.rs and tests/parse.rs in the last commit.
Check that the code is correct and that the tests cover each change.

When the review is complete, end this session with one command:
- If you found no problem, run: ravel end-session approved
- If you found a problem, write your findings to review-notes.md.
  Then run: ravel end-session changes-needed

The prompt has four parts. Each part has a different purpose:

Part of the promptPurpose
The work: review two named filesTells the LLM what to do
The two permitted results, approved and changes-neededGives the only values that the orchestrator expects
The condition for each resultTells the LLM which value to send
The command ravel end-session RESULTTells the LLM how to end the session and send the value

Then the orchestrator runs Ravel as a child process. --kind review names the sort of work. The prompt file is the prompt.

Fragment: the request of the review example. This block omits the code of the orchestrator that runs the command.

ravel start-session --kind review --prompt-file review-prompt.txt

Do not type this command now. It needs an installed Ravel, the file review-prompt.txt in the current directory and a configuration script with a rule for the kind review. Chapter 3 installs Ravel. Then it gives you the files and the command of a simpler first session.

Ravel gives the kind and the prompt to the owner’s configuration. The owner is the person who controls Ravel’s configuration for an account. The configuration chooses a harness for each kind. A harness is the program in which an LLM works on a prompt, such as Claude Code. In this example, the configuration chooses Claude Code for the kind review.

What happens next? The table follows the review in order. In this run, the LLM finds a problem.

The orchestrator now acts on the result. Its own code decides what each value means:

Outcome of ravel start-sessionWhat the orchestrator does next
Status 0 and the result approvedMarks the review as complete and moves to its next task
Status 0 and the result changes-neededReads review-notes.md, then requests a session of the kind fix with the notes in its prompt

Ravel does not know what approved and changes-needed mean. These two values are the orchestrator’s convention, which its prompt states. Ravel returns the value that the LLM sent, unchanged, after it stops Claude Code and completes cleanup. The orchestrator gives the value its meaning.

What the review shows about every session

The review had three participants with different responsibilities. Every use of Ravel has the same three. The table connects each general role to its part in the review.

ParticipantIn the reviewIn general
CallerThe orchestrator wrote the prompt and acted on changes-neededSupplies the kind and the prompt. The prompt gives the permitted results and the end-session instruction. The caller interprets the result.
OwnerConfigured Claude Code for the kind reviewWrites the configuration that chooses a program for each request
RavelLaunched Claude Code, stopped it and returned changes-neededRuns the chosen program, supervises it and returns the result after cleanup

The caller is the person or program that runs ravel start-session. The orchestrator is one caller, and you are the caller when you type the command yourself. The owner and the caller can be the same person, but their responsibilities stay separate. One run of ravel start-session, from the request to the result, is a session.

Why use a harness, and not a direct call to a model? A harness such as Claude Code or Codex can run under the subscription of its user. Thus, your program can use that subscription for LLM work instead of paid API access. The cost can be much lower for work that the subscription covers. The Claude Code documentation and Codex documentation explain their access options and link to their plans and terms. This paragraph agrees with those pages as they were on 18 October 2026.

Why does the prompt tell the LLM to run ravel end-session? An interactive harness waits for more input when the LLM completes its task. It does not exit by itself. Thus, the orchestrator cannot wait for the harness to exit. ravel end-session RESULT gives the LLM a way to say that the work is complete.

The caller chooses the permitted values and the condition for each value. Ravel stops the harness and, after cleanup, returns the value to the caller.

The caller asks for a session

The caller runs ravel start-session with a prompt and a kind. The prompt is the text that tells the LLM what to do. A kind is a short token that names the sort of work that the caller wants. The caller gives the prompt with --prompt TEXT or, as in the review, with --prompt-file PATH.

In the review example, the caller uses review as the kind. The caller and the owner’s configuration agree on that token. Ravel checks only that the kind is not empty. It has no built-in review category and gives the kind no meaning.

The caller can also use the kind to extend or modify the prompt. For example, if the harness supports skills, the caller can add a line to the prompt for the kind review. That line tells the LLM which skill to load. A skill is a set of instructions for a particular task. This use of the kind is a caller convention.

Ravel keeps the caller’s prompt unchanged in request.originalPrompt. With skill delivery enabled, request.prompt holds discovery instructions followed by the caller’s text in a separate block. The script passes that prepared prompt to the harness. Ravel adds no task meaning or instruction that ends the session. Chapter 6 explains skill delivery.

The configuration script chooses a program

The owner’s configuration has two parts. The configuration script is a file of Rhai code that selects a program for each request. The settings are values in a JSON file, such as limits and the harnesses that the script can run. The table gives the default path of each part:

Part of the configurationDefault pathWhat it holds
Configuration script$HOME/.config/ravel/config.rhaiRhai code that selects a program or refuses the request. --config PATH names another script for one session.
Settings$HOME/.config/ravel/settings.jsonThe deadline, limits, environment grants, harnesses, budgets and skill sources. The script cannot change them.

Ravel gives the request to the configuration script. Then the script selects a program and its arguments, or it refuses to launch a program.

What is Rhai? Rhai is a small computer language for programs that are written in Rust. A Rust program can contain the Rhai engine and run Rhai code in its own process. Ravel does this. Thus, the ravel executable already contains everything that runs your configuration script, and you install no separate language runtime.

Rhai’s feature list names these characteristics. Each one is important for a configuration script:

  • A familiar syntax. Rhai looks like a mix of JavaScript and Rust. It has variables, functions, if, loops, arrays and maps.
  • Dynamic types. You do not declare a type. Each value has its type while the script runs.
  • A sandbox. Rhai code changes things outside the script only through functions that the host program gives it. In Ravel, the configuration script reads files and runs harnesses only through ravel:: functions. The book calls these functions host capabilities.
  • Protection against runaway scripts. Rhai can stop a script that runs too long, calls functions too deeply or makes data that is too large. Ravel sets these limits, and one deadline covers each evaluation.
  • Modules. A configuration script can import other Rhai files.

Here is a short configuration script for the review example. The book’s examples must run without a real harness. Thus, this script selects fake-agent, a small program that stands in for Claude Code. It refuses every kind except review.

Fragment: a short configuration script for the review example. This block omits the program fake-agent and the command that runs the script. You read this script here, and you save nothing. Chapter 3 runs a script of this sort with a fake agent.

export const SCHEMA_VERSION = 4;
export const VERSION = "chapter-1";

fn select(request, context) {
    if request.kind == "review" {
        return #{
            status: "selected",
            program: "fake-agent",
            args: ["You are a careful code reviewer. " + request.prompt],
            provider: "local",
            model: "fake",
            effort: "low",
            reason: "Reviews go to the fake agent.",
        };
    }
    #{
        status: "refused",
        code: "unknown_kind",
        message: "This configuration script has no rule for the kind " + request.kind + ".",
        remedy: "Use the kind review.",
    }
}

Read the configuration script from the top. The table says what each part does:

Part of the scriptWhat it does
export const SCHEMA_VERSION = 4;Names the version of the interface between Ravel and the script that this file uses
export const VERSION = "chapter-1";Names this revision of the owner’s script
fn select(request, context)Defines the function that Ravel calls. request holds the kind, the prompt and other data of the request. context holds optional selection context, which is data for the choice.

The last mapIs the value of the function when no return ran. This map is a refusal.

How does Ravel run the script? The Ravel CLI, the ravel command-line program, does not run it in its own process. It launches a second copy of its own executable as a child process. That child is the Rhai worker. The worker evaluates the configuration script and sends the selection or the refusal to its parent.

Why a separate process? The parent stays in control while the script runs:

  • The deadline. Each evaluation has a deadline. When it expires, the parent ends evaluation and can signal the worker process. Rhai cannot interrupt some of its own functions, such as sleep. A kernel stall can delay the worker’s exit.
  • Requests from the script. The worker only computes. When the script reads a file or runs a harness, the worker asks the parent. The parent does the work and sends the data back.
  • Isolation of a failure. If the script exhausts the memory of the worker or overflows its stack, only the worker stops. The parent continues, reports the failure to the caller and launches no program.

The worker does not run at the same time as the selected program. Ravel waits until the worker exits and collects its exit status. Only then does Ravel launch the program that the script selected.

Do you want to learn more Rhai? Rhai has its own documentation. Chapter 4 teaches the Rhai that a configuration script needs, so you do not need these pages for this book:

  • The Rhai Book is the manual. On 27 October 2026, it documented Rhai 1.27.0, the version that Ravel contains.
  • The language reference gives the syntax in a short form.
  • The online playground runs Rhai code in your web browser. It has no ravel:: functions and none of Ravel’s limits. Thus, a script that calls a host capability does not run there.

The selection and the routing notice

What does the configuration script give back to Ravel? It gives back a selection or a refusal. A selection is the map that select returns when it chooses a program. Its status field is "selected". A refusal is a map with status: "refused".

After a refusal, Ravel launches no final managed process and returns no result to the caller. Evaluation harness runs can occur before the refusal.

The selection of the review example has these fields:

FieldValue in the exampleWho uses it, and how
programfake-agentRavel finds this program and runs it
argsOne string: the instruction, then the caller’s promptRavel gives these arguments to the program, without a shell
providerlocalRavel writes it in the routing notice
modelfakeRavel writes it in the routing notice
effortlowRavel writes it in the routing notice
reasonReviews go to the fake agent.Ravel writes it in the JSON form of the routing notice

program and args are the command that Ravel runs. The other fields are labels. A label describes the choice of the configuration script, but it does not configure the harness. For example, a script that selects Claude Code puts the model option of Claude Code in args. The model label only tells the caller which model the script chose. Ravel does not check that the labels agree with the arguments.

Why does the caller need these labels? The caller usually wants to know what the configuration script chose, but the caller does not read the owner’s script. Ravel tells the caller in the routing notice:

  • Who writes it: the Ravel CLI, the ravel command-line program.
  • When: in text form, after selection and before the launch. In JSON form, after the supervision attempt.
  • Where: one line on the caller’s standard error. Standard output carries only the result.
  • Who reads it: the caller, or the person who watches the terminal.
  • Why: this line is the way in which Ravel tells the caller which harness, model and effort the configuration script chose.

Fragment: the routing notice of the review example, as Ravel writes it on standard error. This block omits the other lines on standard error.

ravel: starting provider local, model fake, effort low for kind "review"

An LLM can help the configuration script choose

You may want an LLM to choose the best harness, model, effort and prompt additions for a kind and a prompt. You can do this with a harness run in your configuration script. A harness run is one run of a program from the harnesses entry of your settings. The script starts it with the host capability ravel::run_harness. The harness uses the owner’s sign-in, and Ravel holds no model credential.

The configuration script reads the answer of the harness as data. Then it builds its selection from that answer. A harness run does not complete the session. Its result goes back to the script, not to the caller. Ravel supervises each harness run within the owner’s evaluation budget, which limits the work of one evaluation of the configuration script. Chapter 4 gives the recipes for Claude Code and Codex.

Ravel runs the program, and the program sends a result

During the session, Ravel supervises the program that the configuration script selected. This program is the managed process of the session. The harness runs the LLM session that works on the prompt. That LLM session is not the Ravel session. Ravel supervises the harness process, not the conversation of the LLM in that process.

The contract with the selected program is loose. The configuration script selects a program, Ravel runs it, and a program in the session sends one value with end-session. Ravel needs nothing more from the program. The selected program does not have to use an LLM or understand a prompt.

The table separates what Ravel needs from the harness use that this book teaches. The runnable examples use ordinary programs as fake agents.

Part of a sessionWhat Ravel needsWhat this book expects from a harness
Selected commandThe configuration script selects a program and its argumentsThe program runs an LLM session
PromptThe caller supplies --prompt or --prompt-file. Ravel keeps that text unchanged in request.originalPrompt. The script decides whether its program receives request.prompt, which also holds discovery instructions when skill delivery is enabled.The script passes the prompt to the harness
ResultA program in the session sends one value with end-sessionThe LLM follows the caller’s instructions and tells the harness to run that command

The caller’s prompt tells the LLM to run ravel end-session RESULT when the task is complete. RESULT is a placeholder for the text to send. As in the review, the prompt gives the permitted values and tells the LLM when to use each value.

A process group is a set of processes that the operating system can signal together. Ravel puts the selected program in a new group. Its children stay in that group unless they leave it.

In the review, the LLM found a problem. It ran ravel end-session changes-needed, as the prompt told it. The program that Ravel launched, usually a harness that runs an LLM, runs that command. Ravel then stops that program and the rest of its process group. After cleanup, changes-needed becomes the result of ravel start-session.

Ravel writes changes-needed unchanged on the caller’s standard output. The orchestrator interprets changes-needed as a request to read the notes and to request a fix session. Ravel gives changes-needed no meaning and starts no next task. The book calls this text an opaque result, because Ravel does not interpret it.

How end-session finds its session

How does ravel end-session know which session to end? It takes no session ID and no target argument. It finds the session through an environment variable, RAVEL_EXIT_FILE.

Before the launch, Ravel makes a result channel for the session. The result channel is a private temporary directory, with a path for one result file in it. Ravel puts that path in the RAVEL_EXIT_FILE environment variable of the program that it launches. The book calls this path the session-result context.

How does the path reach end-session? When a process starts a child, the child gets a copy of the environment of its parent, unless the parent changes it. A harness runs each command that the LLM requests in a child process, for example a shell. That shell starts ravel end-session. If each parent leaves RAVEL_EXIT_FILE unchanged, each child inherits the same path. Thus, ravel end-session finds the path in its own environment and writes the result to that file.

ProcessWhich process starts itIts RAVEL_EXIT_FILE
ravel start-sessionThe callerNone, unless the caller itself runs in a session
The harness, which is the managed processRavelA new path that Ravel makes for this session
A shell for a command of the LLMThe harnessThe same path, inherited from the harness
ravel end-session changes-neededThat shellThe same path, inherited from the shell. The command writes the result there.

Each child inherits its parent’s path unless its parent changes it. Ravel sets a new path for the inner harness.

Ravel stops the program and returns the result

When the program sends the result, it requests the end of the session. This request does not prove that cleanup succeeded. A process group is an operating-system unit that contains the managed process and the descendants that remain in its group. Ravel stops the harness and each other process that remains in that group. Then it completes the cleanup of the group.

To reap a child process, its parent collects the exit status of that child. Before Ravel returns a successful result, it confirms that the managed process ended and that Ravel reaped it. Ravel also confirms that the process group is gone and that it removed the temporary files of the session. Chapter 3, “A complete session, end to end”, explains these mechanics at the point where a session needs them.

The table follows the action of the LLM to the result that the caller receives. The caller receives a successful result only after Ravel stops the managed process and its process group and completes the cleanup.

StopRavel stops that program and all other processes that still run in its process group.

After a successful session, Ravel writes the result unchanged to standard output. Ravel does not interpret the result and adds no newline. Ravel redirects the standard output of the managed process to standard error. Thus, the caller can keep the output of the managed process and the diagnostics of Ravel separate from the result stream.

Check whether start-session succeeded before you interpret that stream. A failure during the write of the final result can leave only the start of the result on standard output. Thus, the output alone does not prove success.

Some outcomes return no result to the caller:

  • A refusal means that Ravel launches no final managed process. Evaluation harness runs can occur before the configuration script refuses.
  • If the managed process exits and no program sent a result, the session has no result and fails. This is also true when the exit status is zero.
  • Cancellation of the session suppresses the result, even if a program sent the result before the cancellation.
  • A supervision failure or a cleanup failure also prevents success.

But a session with a sent result can succeed after cleanup, even if the managed process then exits with a nonzero status. The result is the value that the caller’s instructions to end the session asked for. The exit status tells how the process ended. The work is what the program changed. None of these three outputs can replace another.

The table keeps the three outputs separate. Thus, you do not confuse an exit status or a changed file with the result that the caller requested.

What the session producesWhat it tells the callerWhat it does not prove
Opaque resultThe value sent with end-session, returned after successful supervision and cleanup That the requested work is correct
Managed process’s exit statusHow that process endedThat it sent a result or that the session succeeded
Work, such as changed filesWhat the selected program changed, such as review-notes.mdThat it sent a result or that the cleanup completed

In short, the caller asks with a kind and a prompt. The prompt gives the permitted results and the end-session instruction. The owner’s Rhai configuration script selects a program, and the routing notice tells the caller what it chose. Ravel launches the program and gives it a path in RAVEL_EXIT_FILE. The program sends a result to that path with ravel end-session. Ravel stops the program, completes cleanup and then returns the result on standard output.

Decide whether Ravel fits

Ravel fits when your program needs to use an LLM session in an interactive harness as a step of its own work. Your program can let the owner’s configuration choose the harness. In each harness that the configuration script selects, the LLM uses the same command, end-session, to send the result. Ravel supervises the session and returns its explicit result after cleanup. Your program still owns the task and the decisions after the session ends.

Use this table to find which part of your need Ravel meets. The other parts need a caller, a service or a selected program.

If you need…Ravel’s partWhat stays outside Ravel
Different owners to choose different harnesses for the same LLM taskEvaluate the configuration script of each owner and run the command that it selectsThe caller’s task meaning and the owner’s decisions in the configuration
An interactive harness to finish as a step of your programAccept the result that end-session sends, stop the group members that remain and return the result after successful cleanupThe caller’s instructions to end the session, the interpretation of the result and all further work
Task queues, schedules, retries or durable historyRun a session when a caller invokes RavelA caller or service that stores and schedules work
Model access, credentials, usage measurement or rules for model selectionSupervise evaluation harness runs and the command that the configuration script selectsThe harness’s model integration, sign-in and usage reports, and the owner’s selection rules
A host that continues to do other work after a launchThe Ravel CLI supervises one session and then exitsA separate host that continues to run after each launch, which Ravel does not provide

The Ravel CLI, the ravel command-line program, is a launcher CLI. One invocation supervises one managed launch, reports its result or failure, and then exits. A persistent runner is a host that continues to run after a launch is complete. Ravel does not provide one. A program that exits after one session does not give what such a host needs.

Do you need a record of past sessions? Ravel keeps none. It has no persistent session store and no history lookup. Its result channel, the private temporary directory that receives the result, exists for one session only. If a caller needs a permanent record, that caller saves it.

The configuration script has no direct filesystem, network or process access. It asks Ravel to read files or run a harness from the settings through host capabilities, the ravel:: functions that Ravel performs for the script. That harness can use files and network services within its own permissions.

Grove, a task-tree driver, is one illustrative caller. It is an orchestrator that runs LLM sessions in harnesses as steps of the work on its task tree. It supplies its own task kinds and interprets its own result values. These conventions belong to Grove. Another caller can use different kinds and results without a Ravel adapter.

This chapter writes INT, TERM, HUP and KILL without the SIG prefix. Other signal names keep that prefix. Code and diagnostic text keep their literal names.

The supervision guarantee has limits. This table shows the consequence of each limit for the caller.

ConditionLimit of the guarantee
A descendant leaves the process group of the managed processGroup cleanup does not reach it. The session can succeed while that descendant continues to run.
An evaluation harness run starts descendants that leave its process groupCleanup of that run does not reach those descendants. The Rhai worker, the separate process that evaluates the configuration script, itself starts no program.
The Ravel CLI stops abruptly, for example because of KILLThe managed process or temporary files can remain. The Ravel CLI cannot catch KILL.
Other code runs as the same user as RavelThat code can tamper with Ravel’s files, RAVEL_EXIT_FILE included. The separation of sessions is not a security check against that code.

Chapter 2 explains why the separation of these roles is useful within these limits.

Why can another program not use Ravel’s parts as a library? Ravel’s runner, keyed-launch, is the Rust code that launches and supervises the managed process. It is a private package of the Ravel CLI. The runner can change process-wide signal state, and its return does not restore that state. Thus, a program that needs supervised harness sessions invokes the Ravel CLI as a child process. The Ravel CLI supervises one session and then exits.

The learning route is to read the chapters in order. The first practical session, in chapter 3, uses a small configuration script and a fake agent. Its directory is ~/ravel-first-session, and the chapter gives each file and command.

A fake agent is an ordinary program that sends a result with end-session. It takes the place of a harness that runs an LLM session. Thus, you can learn the protocol without a model service or a personal agent account. The installation and the configuration of real agents are outside the scope of the book.

See what we tested and what remains unchecked

Which platforms did the project check, and what does that evidence show? This section answers that question. It also says which checks of the book remain open.

Recorded measurements checked how Ravel starts a session and completes its cleanup on two platforms. One platform is aarch64 macOS with Rust 1.99. The other platform is native aarch64 GNU/Linux with Rust 1.85.0, which was the declared minimum at that time. Each measurement applies only to the platform, kernel, C library and compiler that it records.

The project built the x86_64 GNU/Linux target, linted it at Rust 1.85.0 and ran it only under QEMU user-mode emulation. This emulation translates x86-64 programs to run on the kernel of the host. Thus, no x86-64 kernel takes part. No x86-64 kernel is qualified.

These facts are limits of the evidence. The three targets do not have the same evidence. Chapter 11 explains the limits of delivery and of the platforms in detail.
