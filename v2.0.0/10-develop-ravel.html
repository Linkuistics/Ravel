The Ravel book

Develop Ravel

Suppose that you change how Ravel returns a result. You want to be sure that a result with spaces at its ends reaches the caller with those spaces. In this chapter, you prepare a checkout and build Ravel. Then you find the code, choose where a test observes the rule, add the test and run the checks before you hand the change over. The same steps apply to every change to Ravel.

The tests run real processes. They use temporary configuration scripts, Rhai files that select programs, and fake programs that stand in for harnesses. A harness is an agent program, such as Claude Code or Codex, in which an LLM works. The tests need no model account, no personal configuration and no other project checkout.

Chapter 7 explains the parts of Ravel and why each part exists. Chapter 8 follows a session through the code that a change can affect.

Ravel supports no separate component. Its private runner serves the Ravel CLI, which supervises one session and then exits. The runner’s return does not restore process-wide signal state. A program that needs supervised harness sessions invokes the Ravel CLI as a child process. This chapter teaches changes to Ravel itself.

Ravel 1.x evaluated configuration scripts in a TypeScript worker. The checkout built that worker with Bun, typechecked its SDK and installed it beside the CLI. Ravel 2.0.0 removed the worker, its SDK, its build and its typecheck. The Rhai engine is now a Rust dependency inside the one executable, bin/ravel. Bun stays in the checkout only as a tool for two book checks.

Links to files outside the book open repository sources on GitHub. Before a change reaches main, read its evidence and convention files from the checkout.

Prepare a checkout

A checkout needs tools that an installed Ravel does not need. The build uses Rust 1.99.1 and a C linker. On macOS, the Command Line Tools supply the linker. On Linux, the system development tools supply it. The table shows which part of the work needs each tool.

PrerequisitePurpose
rustup, with Rust 1.99.1, rustfmt and ClippyCompile, format and lint the Rust workspace
TaskRun the recipes in Taskfile.yml
cargo-nextestList and run the Rust tests
ShellCheckCheck the shell scripts during task check
Bash, curl, and tar with gzip and xzRun the scripts and unpack the downloaded book tools
shasum or sha256sumCompare each download with its committed SHA-256 pin
GitObtain the checkout, and let scripts read the tracked files

The file rust-toolchain.toml at the root of the checkout selects Rust 1.99.1, with rustfmt, Clippy and the three release target libraries. When rustup’s tools are first on PATH, cargo in the checkout uses that toolchain. rustup toolchain install, run in the checkout, installs that toolchain when rustup does not have it.

  1. Obtain a checkout of the Ravel repository.
  2. Use cd to enter its root directory, where Taskfile.yml is.
  3. Run rustup toolchain install.
  4. Run task setup.
  5. Run task build.

Setup has tool pins for macOS arm64, Linux aarch64 and Linux x86_64. Native x86_64 Linux remains unqualified. The checkout trial below covers only macOS arm64.

The Bun of the checkout is a development tool for the book only. No build of Ravel uses it, and no installation or archive holds it. The Ravel CLI and its Rhai worker need no Bun or Node at run time.

Build the executable

task build runs cargo build --locked --workspace. Cargo builds both Rust packages and writes the executable to target/debug/ravel, with the default Cargo target directory. The Rhai worker is not a separate build. The Ravel CLI starts another copy of target/debug/ravel in an internal role to evaluate a configuration script.

Cargo.lock pins every Rust dependency. crates/ravel/Cargo.toml pins the Rhai engine exactly, at version 1.27.0. A first build can need network access for the dependencies that the Cargo cache on the host does not hold.

The build script crates/ravel/build.rs puts a source identity into the executable. That identity is a digest of the Rust sources of both packages, the package manifest, the build script and Cargo.lock. The worker’s hello holds the identity, and the Ravel CLI compares it with its own. Both roles come from one build, so a change to the worker always agrees with its CLI. Chapter 7 explains this check.

TaskUse it whenOutput or check
task buildYou change Rust sourcetarget/debug/ravel and the runner library
task checkYou hand a change overFormat, lint, script checks and all Rust tests
task rhai:upgrade-proofYou change the Rhai pinThe engine tests and the hostile classes through the CLI
task noticesYou change a dependencyLicence notices for the release graph, under target/notices/

task notices installs cargo-about 0.8.4 into the checkout on its first run, through task notices:setup. It refuses a dependency whose licence is not on the approved list. task install and the release builds run it, because each installation carries the notice file.

In the example of this chapter, the result goes through the result channel. end-session writes the complete result file in one atomic step, and the CLI reads it after cleanup. Tests with real subprocesses check nested session-result context, cancellation, process cleanup, and empty and multiline results. Thus, a change to this boundary needs more than a test of a parser.

Choose a test seam

A test seam is the boundary at which a test supplies inputs and observes behaviour. Choose the nearest seam that can observe the behaviour of your change. For the spaces of a result, a test of the argument parser is too near. It cannot see what end-session writes or what the caller receives. The command boundary can see both.

The table connects each behaviour to a seam and a focused command.

Behaviour to checkSeam and sourceFocused command

A result, refusal or managed launch through the executable crates/ravel/tests/cli.rs, with temporary configuration scripts and fixture processestask test:cli

The test tasks build what they need. Cargo builds the ravel executable before the integration tests of its package, and each test starts that executable. Thus, a test always uses the worker of the same build. The tests need no host Bun or Node, no model account and no installed Ravel.

A configuration script can ask a model through a harness run, as chapter 4 teaches. The tests never make a real call. In rhai_llm_calls.rs, a fake harness on the private PATH plays the model. It prints a fixed answer and records its arguments and its standard input. The test then reads which route Ravel launched and what the fake received. Each case has a control: the same script with another answer must give the other route.

A real call is a separate, opt-in check. task harness:smoke:claude and task harness:smoke:codex make one real call through Claude Code or Codex with the owner’s sign-in, and that call spends subscription usage. No default task runs them. Chapter 4 explains them. task check runs only task harness:smoke:test, which tests the smoke script against fake harnesses.

When you change the Rhai pin, run task rhai:upgrade-proof. It prints the pin and checks that Cargo.lock builds the same version. Then it runs each rhai_* test target, in a fixed order. Last, it runs each hostile class of rhai_limits.rs, such as an endless loop, a deep recursion and a full heap. It fails when a rhai_* file is not on its list, or when a target runs no test.

The runner’s terminal tests create a pseudo-terminal, or PTY. This private terminal lets a test observe foreground ownership and modes without a human terminal. The in_pty helper in crates/keyed-launch/tests/job.rs starts the command as the leader of a new POSIX session. It reads the terminal output all the time, so a full terminal buffer cannot stop the leader. At its deadline, it kills the leader’s process group and fails the test.

Tests that change process-wide signal state use a separate process. The job tests run their own binary in a fixture role, a test function marked #[ignore]. A parent test invokes that role with its required environment. The fixture role is not a check when it runs alone. Chapter 9 explains the terminal behaviour that these tests observe.

task test:list lists the cases before a run. The focused tasks pass the arguments after -- to nextest. A package selector chooses code, --test chooses an integration-test binary, and -E chooses test names with a filter expression.

Fragment from the checkout trial: list first, then run the added tests. The fragment omits their source and the nextest output.

While you edit, run the focused checks. Before handoff, run the full suite.

Run the checks before handoff

task check runs scripts/check.sh. Each stage prints one line with its result. The script stops at the first stage that fails. Its last stage runs the workspace tests with nextest and shows their report. The earlier stages run in this order:

StageWork
formattingcargo fmt --all --check checks the Rust format and changes no file
scriptsShellCheck checks the shell scripts under scripts/
book-bun-integrityOffline fixtures check the book Bun’s download, cache recovery and the refusal of a corrupt download
harness-smoke-fakesThe harness smoke script runs against fake harnesses and makes no real call
installed-recordControls check the script that compares a Homebrew installation record
lintClippy checks the workspace and all targets with the committed lockfile
terminal-recoveryRunner tests produce real-PTY receipts, then a CLI unit test reads them

task test:terminal-recovery runs the last of these checks alone.

The workspace configuration sets Clippy’s all lint group to deny. Thus, a Clippy report from that group fails the lint stage. When a stage fails, scripts/check.sh names its log and shows the last 60 lines.

Each run of task check writes a new target/check.* log. The log holds the output of the earlier stages and the nextest report. The terminal-recovery check creates temporary receipts and removes them when its script exits. The format stage does not change source files.

task check does not build the book or run its example, excerpt, figure or prose checks. It also does not install Ravel or test release archives. Those workflows have their own tasks. The workspace test run uses nextest’s default selection. Thus, a pass does not mean that every ignored fixture or native measurement ran.

Add a test

The following fragments come from tests added to a scratch copy of the checkout for this chapter. They use the helpers and imports of the named files. All five passed on macOS arm64. They show current behaviour and do not change the product.

For a defect, first add an assertion that fails because of that defect. Then change the code and run the same test again. A test that passes before the code change cannot tell the old behaviour from the new behaviour.

Test the command boundary

This is the test for the example of this chapter. In crates/ravel/tests/cli.rs, Fixture gives the executable an empty environment with a private HOME, TMPDIR and working directory. Its PATH contains /usr/bin:/bin. The selecting helper writes a Rhai configuration script that selects /bin/sh with a script of your choice. The real Rhai worker evaluates that configuration script.

Fragment from the scratch copy of crates/ravel/tests/cli.rs: this test omits the imports and the Fixture definition.

#![allow(unused)]
fn main() {
#[test]
fn book_result_keeps_spaces() {
    let fixture = Fixture::new();
    let config = fixture.selecting(r#""$1" end-session -- "$2""#, "  done  ");
    let output = fixture.start(&config, "Check spaces.");

    assert!(
        output.status.success(),
        "{}",
        String::from_utf8_lossy(&output.stderr)
    );
    assert_eq!(output.stdout, b"  done  ");
    assert_eq!(fs::read_dir(fixture.root.join("tmp")).unwrap().count(), 0);
}
}

The helper gives the shell the built Ravel executable as $1 and the result as $2. The shell sends the result with end-session. The assertions check success, the unchanged spaces and the cleanup of the fixture’s temporary directory. A test of the parser alone cannot check this path through both ravel processes.

Test an LLM call with a fake model

You may want to check that a configuration script launches the route that a model’s answer chooses. In crates/ravel/tests/rhai_llm_calls.rs, SELECTION is a configuration script that asks the harness classifier to classify the prompt. It maps each answer to a route. fake_model writes a fake classifier on the private PATH, and settings names it as a harness.

Fragment from the scratch copy of crates/ravel/tests/rhai_llm_calls.rs: this test omits the file’s imports, constants and helpers.

#![allow(unused)]
fn main() {
#[test]
fn book_fake_model_answer_chooses_the_route() {
    let sandbox = Sandbox::new();
    let recorded = sandbox.recording_agent();
    fake_model(&sandbox, "classifier", &format!("echo {LIGHT}"));
    settings(&sandbox, &["classifier"], 1);
    sandbox.personal_rhai(&rhai_script(SELECTION));

    let notice = notice_of(&start(&sandbox, PROMPT, &[], &[]));

    assert_eq!(recorded.argv().unwrap(), ["routed", "quick-route"]);
    assert_runs(&notice, &[("classifier", "exited")]);
}
}

The fake model prints the light answer, so Ravel launches quick-route. The routing notice lists one harness run of classifier. A copy of the test that expected deep-route failed. Thus, the route comes from the answer and not from a default. The file’s own test of this script also checks the other answer.

Test a real child process

In crates/keyed-launch/tests/launch.rs, the test type Harness writes a shell script in a temporary directory. This type is not an agent harness. The launch helper builds the runner request. support::controls() gives the names of the inherited enclosing-session controls, and the runner removes them from the child. Keep tests separate from live sessions lists these controls.

Fragment from the scratch copy of crates/keyed-launch/tests/launch.rs: this test omits the file’s imports and helper definitions.

#![allow(unused)]
fn main() {
#[test]
fn book_child_exit_keeps_its_status() {
    let harness = Harness::new();
    let script = harness.script("exit 23\n");
    let argv = harness.argv(&script);
    let channel = Channel::allocate(&harness.control()).unwrap();

    let ended = run(launch(&argv, &channel, support::controls(), None)).unwrap();

    assert_eq!(ended.status.code(), Some(23));
    assert_eq!(ended.end, End::Exited);
    assert!(!ended.signalled);
}
}

The child exits with status 23 without a completion signal. The assertions separate the exit status, the reason that supervision ended and the channel state. This test needs no PTY, because it makes no claim about a terminal.

For a claim about a terminal, the helper in job.rs supplies the PTY. The launcher role reports its foreground group before and after the child runs.

Fragment from the scratch copy of crates/keyed-launch/tests/job.rs: this test omits the imports, Scratch, the launcher role and the PTY helper.

#![allow(unused)]
fn main() {
#[test]
fn book_normal_exit_restores_foreground() {
    let scratch = Scratch::new();
    let child = scratch.script("exit 23\n");
    let (status, output) = in_pty(
        role_command(
            "launcher",
            &[("JOB_CHILD", &child), ("JOB_REPORT", &scratch.os("report"))],
        ),
        Duration::from_secs(20),
        |_| {},
    );
    assert!(status.success(), "{status:?}\n{output}");
    let report = report(&scratch.path("report"));
    assert_eq!(report["code"], "23");
    assert_eq!(report["before_foreground"], report["group"]);
    assert_eq!(report["after_foreground"], report["group"]);
}
}

The parent checks that the launcher completed its report. Then it reads the child’s status from that report. The two statuses belong to different processes. The table separates those observations in this example.

ProcessWork and observation in this example
Parent testStarts the launcher role through in_pty. Checks the role’s exit status, then reads the report
Launcher roleRuns the same test binary in a separate process on the private PTY. Its linked runner supervises the child. Reports the foreground values and the child’s status
ChildRuns the shell script that exits with status 23. The report’s code field holds this status

This test checks the final foreground ownership. It does not check recovery after a change of modes. The raw-mode test near it changes the modes and checks that the change occurred before it checks recovery.

Test a local rule

A CLI unit test can check the argument parser without a worker or a child process. The separator -- makes a result such as --help into data.

Fragment from the scratch copy of crates/ravel/src/cli.rs: add this test module at file scope. The fragment omits the argument definitions above it.

#![allow(unused)]
fn main() {
#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn book_result_after_separator_is_data() {
        let cli = Cli::try_parse_from(["ravel", "end-session", "--", "--help"]).unwrap();
        let Command::EndSession { result } = cli.command else {
            panic!("expected end-session");
        };
        assert_eq!(result, "--help");
    }
}
}

The parser returns Command::EndSession with the unchanged value. This test does not run end-session or need a result channel. The tests at the command boundary cover the later effect of that command.

Install and test the installed files

task install builds a release executable for the host and generates the licence notices. It copies Ravel’s files into PREFIX, then tests that installation. The default prefix is ~/.local. With an explicit prefix, you can test a build and keep your usual installation.

  1. Choose a disposable prefix for the trial.
  2. Run task install with that prefix.
  3. Read the last line, which names the installed version and the prefix.

Fragment from this chapter’s macOS arm64 trial: these commands omit the output and the removal of the disposable prefix.

task install PREFIX=target/install-trial
task smoke

The installation puts the executable at PREFIX/bin/ravel, the three Rhai examples under PREFIX/share/ravel/examples/ and the notice file under PREFIX/share/ravel/notices/. It removes an old PREFIX/libexec/ravel directory, which held the Ravel 1.x worker and SDK. It does not add the prefix to PATH, and it writes no installation record. Only a Homebrew formula writes share/ravel/installation.json, because only an installation by Homebrew knows the shared skill directory. Chapter 6 describes the installed files. Chapter 11, “Deliver Ravel”, covers release archives, their target checks and the formula.

The installed smoke test, scripts/installed-smoke.sh, starts with env -i. It tests both the direct path to the executable and a relative symlink from another prefix, as a package manager links an installation. Its private PATH has selected system utilities and fixture programs. It refuses to run if that PATH finds bun, node or a Grove command. It checks:

  • the version line of the executable.
  • that no libexec/ravel and no installation record exist.
  • the installed examples and the notice file.
  • ordinary, empty, multiline and option-like results, which return unchanged.
  • child output, which goes to diagnostics and not to the result.
  • relative Rhai imports, measured reads, selection context and --param values.
  • the refusal of a policy.ts entry as config_format_retired, with status 3.
  • end-session without session-result context, which fails.
  • the cleanup of temporary session files.

These tasks passed on macOS 27.0.1 arm64 in this chapter’s trial. This local smoke check does not qualify release archives, Linux floors or a different host.

Check the book

Book checks are separate from task check. A source change can make a quoted excerpt stale even when every Rust test passes. A change to the book can break a command example without a change to product code.

task docs:book first builds the book, then serves it at http://127.0.0.1:8775. The server builds the book again after a source change. PORT=… selects another port. task docs:book:build only builds, under target/book. Its script, scripts/book.sh, fails on an mdBook ERROR or WARN diagnostic, even if mdBook exits with status 0. A successful build does not show that every link resolves or that a figure is legible.

After an intended figure change, run the update task, read the diff and view the built page. Then run the comparison again.

The figure convention describes the shared modules and the visual checks. Equality with a fresh render does not show that a diagram explains the right behaviour.

The example check builds Ravel first. It evaluates real Rhai configuration scripts and runs fake programs with a private home, temporary directory and PATH. Standard input is /dev/null. It compares the declared streams and exit status, with only the scratch path normalised. Every complete example runs on every platform. An <!-- example: ... --> comment is a page error, because the convention has no directive.

Fragments do not run. The example check also does not compare source excerpts. The example convention defines the labels and the output claims.

The excerpt check needs no build. Its comparison keeps spaces and indentation. It refuses untracked sources, symbolic links and generated paths. An exact quotation can still have an incorrect explanation. The excerpt convention describes the label and the comparison.

The STE and prose-break tasks report problems without failure, unless you pass --strict. They run on the book Bun from task setup. By default, the STE check examines all chapter files, SUMMARY.md, CONTEXT.md, README.md and the text of each figure layout record. The prose-break check examines the chapters. A table, figure or code block breaks a prose run. Headings and lists do not.

Neither check can show clear explanations or agreement with every STE rule. A human read still checks meaning, order and the use of active verbs.

The checkers have their own tests. A control gives a checker a known bad input and requires it to refuse that input. A mutant removes a safeguard from a copy of the checker. Keep tests separate from live sessions

A test can run inside an LLM session that Ravel supervises. If a test inherits that session’s real result path, its end-session call can stop the developer’s session. Thus, each test boundary removes the inherited authority before it creates its own fixture inputs. The table maps each test boundary to its guard and the source that applies it.

BoundaryGuardSource
Cargo commandsForce the listed session controls to empty values.cargo/config.toml
Runner subprocess helpersRemove those names from commands, or pass the names as runner scrub controlscrates/keyed-launch/tests/support/mod.rs
CLI, Rhai, skill and hostile fixturesUse env_clear(), a private HOME and TMPDIR, and a fixture PATHcrates/ravel/tests/cli.rs and crates/ravel/tests/support/
Installed smokeStart with env -i, then supply only fixture inputsscripts/install.sh and scripts/installed-smoke.sh

The Cargo guards cover these names:

  • GROVE_LAUNCH_DIR, GROVE_SIGNAL_FILE and GROVE_RUN_SIGNAL_FILE.
  • HARNESS_DISPATCH_EXIT_FILE, HARNESS_DISPATCH_RUN_ID and HARNESS_DISPATCH_STATE_DIR.
  • RAVEL_EXIT_FILE, RAVEL_RUN_ID and RAVEL_STATE_DIR.

An empty value disables the inherited authority. It does not send the authority to another path. The runner helpers also protect direct subprocess invocations that do not go through Cargo. The CLI fixtures create temporary configuration scripts, so tests do not need the developer’s personal configuration script.

The GROVE_* and HARNESS_DISPATCH_* names stay in these guards on purpose. They protect tests from older enclosing-session controls. They are safety exceptions that remain from the extraction of Ravel, not product dependencies. Paths in source provenance and the retired-project record give historical attribution. Ravel does not load those projects or interpret their task trees. The caller-reference inventory classifies these references in source files and dotfiles.

For a new subprocess test, use the fixture of the chosen seam again. Supply only the environment values that the case needs. If the case needs a result channel, create that channel inside its temporary fixture. Never supply the enclosing session’s real result path.

Read the evidence for a change
