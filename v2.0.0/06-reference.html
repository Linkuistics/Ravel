Reference

Do you have a question about one option, one exit status, one line on standard error or one file? This chapter answers it in one entry. You can come here from any page of the book, or directly from an error message. You do not have to read the earlier chapters first.

Each entry explains its terms and links to the chapter that teaches the subject. The entries repeat short explanations so that each entry makes sense alone.

Many entries use the code review of chapter 1 as their example. An orchestrator, a program that runs LLM work as steps of its own work, wants an LLM to review the last commit. It writes a prompt file, review-prompt.txt, and runs this command:

Ravel uses config in file names, options and diagnostic codes, such as config.rhai, --config-env and config_refused. Its diagnostic prose uses “configuration script”.

Why does Ravel evaluate the script in a separate process? The Ravel CLI launches a second copy of its own executable as a child process, the Rhai worker. The parent stays in control while the script runs:

  • The deadline. Each evaluation has a deadline. When it expires, the parent ends evaluation and can signal the worker process. Rhai cannot interrupt some of its own functions, such as sleep. A kernel stall can delay the worker’s exit.
  • Requests from the script. The worker only computes. When the script reads a file or runs a harness, the worker asks the parent. The parent does the work and sends the data back.
  • Isolation of a failure. If the script exhausts the memory of the worker or overflows its stack, only the worker stops. The parent continues, reports the failure to the caller and launches no program.

The worker does not run at the same time as the selected program. Ravel waits until the worker exits and collects its exit status. Only then does Ravel launch the program that the script selected.

What is Rhai? Rhai is a small computer language for programs that are written in Rust. Its engine is part of the ravel executable, so you install no separate language runtime. Rhai looks like a mix of JavaScript and Rust, and its values have dynamic types.

A Rhai script changes things outside itself only through functions that the host program gives it. In Ravel, these are the ravel:: functions. Some are host capabilities, which ask the Ravel CLI to do work. Other helpers run in the worker.

The Rhai Book documents the language, and its language reference lists each statement and operator. The online playground runs Rhai code in your browser. It does not have the ravel:: functions or Ravel’s limits. Chapter 4 teaches the Rhai that a configuration script needs.

start-session

You use ravel start-session when you want a harness, or another program, to do one piece of work and give your program one result. ravel start-session --kind TEXT also needs exactly one of --prompt TEXT and --prompt-file PATH.

What happens after you run the command? The table follows one successful session from your command to your result:

OrderWho actsWhat happens
1The callerRuns ravel start-session with a kind, a prompt and optional caller data
2The Ravel CLIReads the settings, checks the file of the configuration script and launches a second copy of its own executable as the Rhai worker
3The configuration scriptRuns in the Rhai worker and returns a selection: a program, its arguments and labels
4The Ravel CLIReaps the worker, writes the text routing notice on the caller’s standard error and launches the selected program. With --json, the notice follows the supervision attempt.
5The managed processDoes the work, then runs ravel end-session RESULT
6The Ravel CLIStops the program and the rest of its process group, completes cleanup and writes the result on standard output

To reap a process is to collect its exit status from the operating system. After the reap, the operating system can use the process ID again. Ravel launches the managed process in a process group of its own. Each child of the managed process is in that group too, unless the child leaves it. The routing notice is the line that tells the caller which harness, model and effort the configuration script chose.

At row 3, the configuration script can also refuse. After a refusal, Ravel launches no final managed process and tries no alternative route. Before it returns, the script can run harnesses of its own. These harness runs return their output to the script, not to the caller.

At row 6, Ravel writes the sent result unchanged to standard output. This write occurs only after the reap, the confirmed absence of the process group and the required cleanup. Ravel does not interpret the result. Then ravel start-session exits with status 0.

All thirteen options below belong after start-session. Only --param and --config-env accept more than one occurrence. A repeated single-value option or switch is a command-line error. -h and --help are also available on this verb.

Ravel 2.0.0 refuses --confine and --runtime-read, which Ravel 1.1 accepts. Either flag, in any position, gives confinement_withdrawn with status 2. Ravel refuses before it reads the settings or starts the worker. Remove both flags, and select the sandbox of the harness in the configuration script. A word that is the value of another option, such as the text of --prompt --confine, is caller data and gives no refusal. See know what the managed process receives.

--kind TEXT

Why does the caller give a kind? The kind is a short token that tells the configuration script what sort of work the caller wants, such as review or bugfix. The script can use the kind to choose a harness, a model and an effort. It can also use the kind to extend or modify the prompt.

--kind is required and supplies request.kind unchanged. Its value is nonempty UTF-8. An absent or empty kind gives status 2.

Ravel has no catalogue of kinds and gets no kind from a task file. Ravel gives the token no meaning. Only the configuration script and the caller do. See supply the prompt and caller data.

--prompt TEXT and --prompt-file PATH

The prompt is the text of the task for the LLM. It also tells the LLM how to end the session, for example “Then run: ravel end-session changes-needed” in chapter 1’s review. Ravel adds no instructions to end the session. Thus, your prompt gives them.

Exactly one of these two prompt inputs is required.

OptionSource of request.originalPrompt and request.prompt
--prompt TEXTThe argument text, also when its first character is -.
--prompt-file PATHOne read of the file, relative to the caller’s working directory.

The prompt can be empty. It contains no NUL, is valid UTF-8 and has a maximum of 1,048,576 bytes (1 MiB). Ravel puts its bytes unchanged in request.originalPrompt, with trailing newlines.

With skill delivery disabled, request.prompt holds the same bytes. With delivery enabled, it holds the prepared prompt. The configuration script decides how to give that text to its selected program. Usually the script puts it in an argument of the harness, and the script can add text before or after it.

An unreadable prompt file reports prompt_unreadable. Invalid encoding, a NUL or too many bytes reports prompt_invalid. Both give status 2. A command with no prompt input, or with both prompt inputs, also exits 2. Ravel does not implicitly read the prompt from standard input, and it refuses a prompt file that is a terminal. See supply the prompt and caller data.

Note: Shell command substitution removes trailing newlines before Ravel receives an argument. --prompt-file preserves those bytes. An operating system can set a smaller argument limit. This limit also applies when the configuration script puts a prompt from a file into the arguments of the selected command.

--config PATH

You may want to try a configuration script before you install it, or use one script for one project. --config selects that script file, which the book calls the entry. The path is relative to the caller’s working directory. Without the option, Ravel uses $HOME/.config/ravel/config.rhai, which needs an absolute HOME. There is no repository search and no environment variable that selects a different configuration script.

The entry resolves to a readable regular UTF-8 file of at most 1 MiB. Its canonical path is UTF-8. A symlink selects its real file, and the directory of that file is the base for relative imports.

An empty option value is malformed input, status 2. If Ravel cannot accept the entry file, the status is 3. A different entry does not move the settings file from $HOME/.config/ravel/settings.json. See define a configuration script and import other Rhai files.

You may want facts about the task to change the choice of the configuration script. For example, a large change can go to a higher effort. Selection context is a JSON document of such facts, such as a summary and acceptance criteria. The script receives it as the second argument of select.

--timeout-ms MS

You may want more time for evaluation, for example when the configuration script asks a model through a harness run. Evaluation is the work of the Rhai worker, up to the selection or refusal. --timeout-ms replaces the timeoutMs setting for this invocation. The table gives its syntax and values. Ravel validates the settings before the flag replaces a value. Thus, an invalid setting fails even with a valid flag.

The deadline begins when the Ravel CLI spawns the Rhai worker. It covers the worker startup, the import of the configuration script, the loader of the selection context and the selection, with every host call. At expiry, Ravel stops any evaluation harness run, then the worker. It reports selection_timeout, status 124, unless cancellation or failed harness cleanup takes precedence. The deadline does not limit the time that the managed process works. See set bounds and environment grants.

--context-bytes BYTES

You may want a larger budget when the selection context holds a long task description. --context-bytes replaces the contextBytes setting. It takes decimal digits in the inclusive range 1–8,388,608 bytes. With no flag and no setting, the budget is 262,144 bytes.

Invalid syntax or range gives status 2. Ravel validates the settings first. Thus, an invalid setting fails even with a valid flag.

The budget limits the caller document and the encoded selection context that selection receives, with the measured source records. It is also the maximum for a host source read. Ravel refuses data above a bound, and it does not truncate that data. context_too_large uses status 3. See selection context and bounds.

--config-env NAME

You may want the configuration script to read a variable of the caller, for example a mode that selects a different effort. --config-env grants the script one such variable. Repeat the option to grant more names.

Why does the script need a grant? The Rhai worker has an empty environment. When the script calls ravel::env(name), the worker sends the request to the Ravel CLI over a private socket. The Ravel CLI checks the name against the base names and the grants. Then it answers with the value from the caller’s environment, or with () when the variable is unset.

For example, chapter 4 grants BOOK_EFFORT, and the caller sets BOOK_EFFORT=high. Then ravel::env("BOOK_EFFORT") returns "high". A name without a grant throws env_not_granted, also when the caller sets it. See the variables that the script can read for the base names.

Grant diagnostics show each name and whether it is set, never its value. See set bounds and environment grants.

--exit-dir DIR

The result channel is a private temporary directory, with a path for one result file in it. end-session writes the result to that file, and Ravel reads it from there. By default, Ravel makes the channel in the caller’s temporary directory: TMPDIR, or /tmp when TMPDIR is not set. --exit-dir chooses a different parent directory for the channel.

The parent is a writable directory that exists. Ravel resolves it from the caller’s working directory.

The option chooses a parent, not a result filename or a persistent store. An invalid parent can report exit_dir_unusable with status 2. If Ravel later cannot allocate the result channel, it reports session_channel_unavailable with status 5. See know what the managed process receives.

--json

Your program may want to read the routing notice and the failures as data, not as text. The routing notice tells the caller which harness, model and effort the configuration script chose. A failure document tells the caller why a session failed.

--json replaces Ravel’s text routing notice and failure document with JSON documents on standard error. It does not change the result on standard output or the output of the managed process. It is off when it is absent, and it belongs to start-session.

The time of the notice also changes. Ravel writes the text notice before the launch. Ravel writes the JSON notice after the supervision attempt, so the JSON document also records what happened during the session.

end-session RESULT

A harness usually cannot exit by itself when its LLM finishes the task. It waits for more input. Thus, the caller’s prompt tells the LLM to run ravel end-session RESULT when the work is complete. This command sends one UTF-8 argument, the result, to the live session that encloses it. It also tells Ravel to stop that session.

How does end-session find its session? It takes no session ID and no target argument. Before the launch, Ravel makes a private result channel for the session. Ravel puts the path of its result file in the RAVEL_EXIT_FILE environment variable of the program that it launches. Each child process gets a copy of its parent’s environment, unless the parent changes it. The table shows the path when each parent leaves it unchanged:

What happens after the send? Ravel finds the result in the channel. Ravel then stops the harness and the rest of its process group, and completes cleanup. Then ravel start-session writes the result on its standard output and exits 0. Thus, the value that the LLM gave to end-session becomes the result of ravel start-session.

Ravel keeps the first complete result that it receives. After that result arrives, Ravel stops the harness. Thus, a second end-session and that shutdown are in a race: either can occur first. For example, another process in the group can send a result before Ravel stops that process. Ravel keeps the first result, even if the second command succeeds. The shutdown can stop the second command, or the removal of the result channel can make it fail.

A successful end-session exits 0 and prints nothing. It means only that the channel accepted the result, or that a valid first result was already present. It does not mean that the job ended or that the result reached the caller. A cancellation or a failure of required cleanup still returns no result to the caller.

end-session exits 1, with a text diagnostic on standard error, if the session-result context is missing, empty, stale or invalid. It also exits 1 for an oversized value or an I/O failure of the send. If the Ravel CLI finds an argument-count or encoding error, it exits 2. The operating system can set a smaller argument limit before the executable runs.

skills resolve

Do you want an agent to read the skill sources of the owner, but outside a session? ravel skills resolve prepares those sources and prints the discovery instructions. You then give that text to an independent harness.

The command reads the skills object of the settings. Without sources in that object, it reads the default skill directory instead. It evaluates no configuration script, creates no result channel and launches no harness. It takes no skill name, task, prompt or source override. Ravel reads no SKILL.md file, no frontmatter and no skill name.

Each source is a local directory. Ravel runs no Git or other VCS command and makes no network request for a source. A checkout of a repository is an ordinary local source, and a tool outside Ravel makes and updates it.

For each source, the command copies the current bytes of the whole source directory. The copy leaves out each .git and .jj entry, at every level. The command checks each search directory and each mandatory file in the copy. Then it stores an immutable snapshot of the copy in the cache. It also stores an immutable descriptor of the directory set. The skill discovery specification in the repository, docs/specs/skill-discovery.md, owns the complete contract.

Note: Each run writes to the cache $HOME/.cache/ravel/skills/v1. Ravel keeps the snapshots and the descriptors after the command, the session and an upgrade. They also stay after a change or removal of the source and after a change of the settings. Ravel has no automatic collector and no prune command.

Note: A snapshot has no write permission. Remove an object manually only when no reader of it runs. After the removal, the next resolution copies the source again. When the source is gone, the resolution refuses as skill_source_missing. It does not use another snapshot of that source.

The descriptor holds the same schemaVersion, sources, directories and mandatory. The name of its directory is the SHA-256 digest of its bytes. The resourceDigest of a source is the SHA-256 digest of the manifest of its snapshot. Two sources with the same content share one snapshot, and each source keeps its own record.

The discovery instructions give each path as a JSON string literal. They list the search directories, the mandatory files in order and the descriptor path. Then they tell the agent how to read mandatory files, find skills, report problems, recover after a compaction and brief a delegate. They hold no task, and no instruction that ends a session. The instructions are the same text that a launch puts before the task of the caller.

Each run captures current bytes. A run reuses a stored snapshot only when the new copy has the same content digest. An edit of a local source therefore gives a new snapshot, and an earlier snapshot keeps its bytes.

Keep a local source quiet while Ravel copies it. Ravel examines each entry two times: when it lists the entry, and after it copies the entry and its directory. When the entry, its type, its identity, its size or a change time is different, the run refuses as skill_source_changed. Then try again.

This check does not make a copy atomic. An edit that restores the size and both change times is not visible to it. A successful second run does not prove that the first copy was atomic.

Ravel reads back the copy in the cache and compares it with the source. The filesystem of the cache can fail to keep two names apart, for example A.md and a.md on the default macOS volume. It can also change the spelling of a name, for example to another Unicode normalisation form. Then the run refuses as skill_resource_invalid and names the paths. Ravel never writes one entry over another, and it never changes a name. A filesystem that keeps both names keeps both.

Default skill directory

Do you install skill sources with a package manager? Then Ravel can read them with no settings. A package, such as a Homebrew formula, exposes its source in the default skill directory. Ravel reads that directory when the settings name no sources. That includes an absent settings file and a settings file without skills. "sources": [] turns the default skill directory off.

Ravel finds the directory through its installation record, the file share/ravel/installation.json below PREFIX. PREFIX is the parent of the directory that holds the canonical path of the Ravel executable. The record is a JSON object with exactly these members:

Skill delivery at launch

When the settings enable skill delivery, start-session prepares the sources before it evaluates the configuration script. It runs the same capture and checks as skills resolve. This step comes after Ravel reads the settings, the caller inputs and the configuration script entry. It comes before the worker and the result channel. Thus, a skill refusal starts no worker and no managed process.

A launch also protects the directory of the selected configuration entry. A source that overlaps that directory refuses as skill_access_unavailable. With --config, that directory can be outside $HOME/.config/ravel.

The prepared prompt has these parts, in this order:

  1. The discovery instructions that skills resolve prints.
  2. An empty line, then the line Caller task.
  3. The line BEGIN RAVEL CALLER TASK NONCE.
  4. The bytes of the caller’s prompt, unchanged.
  5. A newline, then the line END RAVEL CALLER TASK NONCE, with a final newline.

NONCE is 32 lowercase hexadecimal digits from the random source of the operating system. The nonce occurs only in the two delimiter lines. When it occurs elsewhere in the prompt, Ravel chooses a new nonce. The newline before the last delimiter line belongs to the wrapper, also when the caller’s prompt ends with a newline. An empty caller prompt gives an empty block, and the discovery instructions stay.

The prepared prompt has a maximum of 1,048,576 bytes. A larger prepared prompt refuses as skill_limit_exceeded, and the message gives both byte counts. Ravel never truncates the task and never omits a directory.

RAVEL_EXIT_FILE

RAVEL_EXIT_FILE is the inherited session-result context: the path that end-session uses to send the result to its enclosing session. The path names one result file in the private result channel of the session. The Ravel CLI sets it separately for each managed launch and evaluation harness run. The Rhai worker never receives it.

How does the path reach end-session? Ravel puts it in the environment of the program that it launches. Each child process gets a copy of the environment of its parent, unless the parent changes it. If each parent leaves the path unchanged, a shell that the harness starts and the ravel end-session in that shell have the same path. end-session reads the path from its own environment and writes the result to that file.

What happens when sessions nest? A nested launch replaces the path only for its own managed process. The value of the outer caller does not change. Configuration script and settings

config.rhai

Where does Ravel find the configuration script? The configuration script is a file of Rhai code that chooses the program for each session. The book calls the file that Ravel loads first the entry. The entry can import other Rhai files.

$HOME/.config/ravel/config.rhai is the default entry. This default needs an absolute HOME. --config PATH chooses a different entry, relative to the caller’s working directory. There is no repository search, environment override or fallback script. An explicit entry can have any file name that ends in .rhai, such as review.rhai.

The entry must canonicalise to a readable regular UTF-8 file of at most 1 MiB. Its canonical path must also be UTF-8. A symlink selects its real file. Imports resolve from the directory of that real file. An unacceptable entry gives status 3 before the script runs. See define a configuration script.

Ravel evaluates the entry in the Rhai worker, a second copy of its own executable. At the deadline, the Ravel CLI ends evaluation and can signal the worker. A kernel stall can delay its exit. A memory or stack failure of the script stops only the worker. The configuration script has no direct filesystem, network, process or environment access. It uses the host capabilities for permitted effects.

The worker receives no session-result context. Before the final managed launch, every host call ends and Ravel reaps the worker. Ravel also removes the worker’s private directory.

Host capabilities

A configuration script cannot read a file, read the environment or run a program by itself. When it needs one of these effects, it calls a host capability, a ravel:: function that Ravel gives to the script. For example, ravel::read_json reads a JSON file, and ravel::run_harness runs a harness.

How does a host call work? The Rhai worker sends the request to the Ravel CLI over a private socket and waits. The Ravel CLI checks the request, does the work and sends the answer back. Then the script continues with the returned value. The two reads, env, harnesses, remaining and run_harness work in this way. The data helpers, json_parse, json_encode, json_check, uuid_v4, path_resolve and path_parent, compute inside the worker and send no request.

The ravel namespace supplies the functions below at the module’s top level, in load_context and in select. Calls are synchronous, so only one host call runs at a time. See host capabilities.

The read functions throw catchable maps for absent, non-regular, unreadable, non-UTF-8 or invalid-JSON sources. The data-error table gives each code. A map has code, message and a name when applicable. A wrong argument type or malformed host request ends evaluation as host_request_invalid. Rhai resolves function arity before the host function runs. A wrong argument count therefore raises an ordinary function-call error instead.

A source consumes one count when its bytes arrive, even if UTF-8 or JSON conversion fails. A read with no file consumes none. Repeated reads each consume one. Only successful reads enter the measurement records. Entry and module loads have their own module bound and do not consume this source count.

A read above its byte bound gives source_too_large. A read after the source count reaches 256 gives too_many_sources. Neither failure is catchable. A requested max_bytes above contextBytes also ends evaluation. The source-count check occurs before the read, also a request for an absent file.

The path helpers read no file and resolve no symlink. path_resolve removes empty and . segments and applies .. without a step above /. path_parent keeps the spelling that remains: /a//b gives /a/, and /a/./b gives /a/.. See data helpers for their use.

Engine and conversion bounds

What stops a configuration script that loops for ever or makes too much data? The Rhai engine counts the operations, the call depth and the size of the data of a script. Ravel sets a limit for each of these counts. When the script reaches a limit, evaluation ends and Ravel launches no final managed process.

Ravel uses the same bounds in both development and release builds. An engine limit ends evaluation as script_limit, status 3. The worker heap bound gives memory_limit, status 3. A try block cannot catch either, also inside an array or map callback. See evaluation bounds.

Rhai checks container size when a call returns a value. An in-place change can exceed that container limit before such a check. The worker heap bound still applies. At the whole evaluation deadline, Ravel ends evaluation and stops the worker, even if a native call does not yield.

At cancellation or the whole deadline, Ravel abandons a read and does not wait for its reply. It stops an active harness run before it stops and reaps the worker. Ravel waits at most 8 seconds for harness cleanup: the 5-second kill grace, 2 seconds for a failed reap and 1 second for group confirmation. If the runner has not completed cleanup by that limit, Ravel reports harness_cleanup_failed. Worker teardown follows and has its own 1-second grace before KILL.

Kernel stalls can still delay process exit. These bounds are not a real-time guarantee.

Example configuration scripts

You may want to begin from a configuration script that already runs, instead of an empty file. Ravel installs three example configuration scripts for this purpose.

The examples are editable Rhai files under share/ravel/examples/. Their checkout source is crates/ravel/examples/. That directory also holds harness-table.rhai, an example for Ravel’s own tests, which Ravel does not install. Copy the files that your chosen example imports, then replace the placeholder commands and labels. Ravel installs no personal configuration script and has no init command. See copy a configuration script and its files.

Installed layout

Where are the files of an installed Ravel? You may want the executable for a caller’s configuration, or the example configuration scripts to copy.

PREFIX is the installation root, independent of the owner’s HOME. For the versioned Homebrew formula, brew --prefix ravel@2 gives this path. After promotion, brew --prefix ravel gives the unversioned installation’s path. Chapter 3 selects the versioned executable for this book’s examples.

Ravel 2.0.0 installs one executable with the Rhai engine inside it. It needs no separate language runtime or source checkout. See install Ravel.
