The Ravel book

Jobs, signals and the terminal

What does Ravel do when a program does not stop? Why can a result wait several seconds before it reaches you? And what happens to a slow LLM call when you press Ctrl-C? This chapter answers these questions. It explains how Ravel ends each program that it starts, how it lends the terminal and which signal state each program receives. It also states where these guarantees stop.

In chapter 7 you ran the example ravel-parts. In that session the Ravel CLI started two programs. fake-advisor was a harness run during selection, and fake-agent was the managed process. Both fakes ended by themselves, so the session showed no stop. This chapter changes one fake at a time to make each stop visible.

These are the words that this chapter uses. Each row gives the value that the word has in ravel-parts.

A signal name such as SIGTERM has the prefix SIG. This chapter writes INT, TERM, HUP and KILL without that prefix, as the shell trap command does. Other signals keep their full names.

A result requests the end of a job. It does not prove that the job has ended. The Ravel CLI stays alive to supervise that end before it returns the result to the caller. Chapter 3 introduced a job and its reap through one session. Chapter 8 shows where these operations occur in the code.

Each program runs as a job

The runner starts each program as the leader of a new process group. The group’s ID is the program’s PID. Descendants inherit this group unless they explicitly change it. The program and the members of its group form the job. In ravel-parts, fake-advisor led one job and fake-agent led another.

A signal to a process group can reach its members together. A signal to the program’s PID reaches only that program. If Ravel stopped only the program, a helper could keep a file lock or continue to change the caller’s files. The group gives Ravel a scope for shutdown that includes ordinary descendants.

A POSIX session can contain several process groups and can have a controlling terminal. The two kinds of job differ here. The managed process can need the caller’s terminal, because an interactive harness talks to a human there. A harness run gives its output to the configuration script, so it needs no terminal.

ChoiceUsed forConsequence
A new process group in the caller’s POSIX sessionThe managed processRavel can signal the job together and can lend the caller’s terminal
A new POSIX session through setsidEach harness runThe run starts without a controlling terminal. The terminal’s keyboard signals do not reach it, and /dev/tty names no terminal for it.
Only the program’s PID as the shutdown targetNothingDescendants can survive their parent. This does not meet Ravel’s cleanup contract.

A descendant can leave the job’s group, for example through its own setsid call. Group cleanup does not cover that descendant. Ravel does not promise to track every process descended from the managed process or from a harness run. A new process group also creates no new Ravel session: that term means one start-session invocation. The Rhai worker is no job. It stays in the process group of the Ravel CLI, and the Ravel CLI stops it by its PID.

Follow the escalation after a result

Why did ravel-parts-escalation take at least seven seconds? An interactive harness can finish its work and then wait for another prompt. The caller therefore tells it to send an opaque result with end-session. The command creates the completion file in the result channel. The runner observes that file’s presence. Ravel checks its contents separately.

Until it sends KILL, the runner checks the program and the channel at regular intervals. For the managed process, the interval is 500 milliseconds. For a harness run, it is 20 milliseconds, because a deadline and an output limit bound the run. The first observation of the file starts the grace period. Thus, the schedule starts at observation, not at the instant the sender calls end-session.

StageConditionAction and wait
GraceThe runner observes the completion file while the program still runsAllow 2 seconds for the program to exit
TERMThe program still runs after the graceSend TERM to the group and the program. Allow up to 5 seconds, the kill grace, for the program to exit
KILLThe program still runs after the kill graceSend KILL to the group and the program. Check for exit at 10-millisecond intervals
Final cleanupThe runner observes the program’s exitStop the other group members before the reap, then recover the terminal and confirm group absence

In ravel-parts-escalation, fake-agent passed through every stage. It sent finished and stayed through the grace. It wrote its note at TERM and stayed through the kill grace. KILL ended it, and final cleanup followed.

The figure separates the grace periods from final cleanup. Both exit paths reach the group stops before reap, then the terminal recovery and group query.

Open the escalation figure at full size.

TERM lets the program handle its own shutdown. A program can ignore TERM. It cannot catch or ignore KILL. If the program exits during either grace period, Ravel proceeds to final cleanup without the later escalation stages. Descendants receive no separate grace period after the program exits.

The 2-second and 5-second values belong to the Ravel CLI, as run::ESCALATION. It gives the same values to the managed process and to each harness run. The runner accepts its caller’s durations. These values are not a seven-second deadline for start-session: selection, observation delays and final cleanup also take time. Without a result, a stop request or cancellation, this escalation places no time limit on the managed process.

After the escalation’s first KILL attempt, the runner uses a two-second bound for its exit checks and reap attempts. It does not restart that bound after an error. If the bound expires, the runner reports unresolved ownership, and Ravel returns no result to the caller. This bound limits retries. It cannot guarantee a wall-clock deadline when the scheduler or a kernel operation stalls.

Stop the group before the reap

A process can exit before its parent collects its status. Until that collection, it remains a zombie: the system retains its identity and exit status, although it executes no more code. To reap the child, the parent collects that status and releases the retained process identity.

Ravel first observes exit without a reap. Its waitid call uses WNOWAIT for that purpose. The unreaped child reserves its PID, which is also the job’s group ID. Ravel uses that reservation for the last group signals.

If Ravel reaped first, the system could reuse the ID for an unrelated group. A later KILL to that number could then reach that unrelated group. The normal cleanup path therefore has this order, for the managed process and for each harness run:

StepOperationWhat it establishes
1Observe the child’s exit with waitid and WNOWAITThe child has exited, but still reserves its identity. A stop is not an exit
2Send KILL to its group twice, with a 20-millisecond pauseAttempt to stop the other members while the identity remains reserved
3Reap the direct child with waitpidConfirm the child’s status and release its identity
4Recover the terminal if Ravel lent itCheck foreground recovery and restore the saved modes. A harness run never receives the terminal, so this step does nothing for it
5Query the group without a signal, for up to one secondConfirm absence only when the system returns ESRCH, meaning no such process group

The second KILL addresses a macOS case where a fork overlaps the first group signal and leaves a new member. Both attempts precede the reap. They do not change the direct child’s status: it has already exited. Ravel reaps its direct child. Other descendants’ parents, or the system, reap those descendants.

A successful signal operation does not prove that the group is gone. The final query uses kill with signal 0, which sends no signal. Success or EPERM means that absence remains unconfirmed. An unrelated group that reuses the ID also prevents confirmation. Ravel does not signal that number after the reap.

On macOS, a group with only zombies can reject KILL with EPERM, or Operation not permitted. Ravel can retain this stop report without a session failure, but only after confirmed reap, successful terminal recovery and an ESRCH absence check. The report alone never confirms cleanup. Ravel writes retained reports as ravel: lines on standard error, or in operationReports with --json.

The same refusal can occur before Ravel observes the exit. The result’s TERM can reach the group while its leader is inside its exit teardown. The leader’s own PID still accepts the signal, but waitid does not report the exit yet. Ravel therefore continues to watch after a group stop answers EPERM. The report then waits for the same three checks. A refused stop to the direct child, or another error, ends the watch at once.

These failures prevent success. Their outcome depends on the kind of job:

FailureFor the managed processFor a harness run
The group still answers the query with success or EPERM after the confirmation wait, or the query failsRavel reports the problem and returns no result to the callerThe evaluation ends as harness_cleanup_failed, status 5. The configuration script receives no map.
An observation or reap errorRavel attempts bounded cleanup, reports what it cannot confirm and returns no resultThe same refusal, harness_cleanup_failed, status 5
Ravel cannot remove the result channelsession_cleanup_failed, and no resultThe same refusal, harness_cleanup_failed, status 5

Once the runner loses or releases the child identity, it stops all numeric signal attempts. After a timeout, it never reports a reap that did not occur.

Stop a harness run

In ravel-parts, fake-advisor printed short, sent advice and exited. What if it does not exit? A real LLM call can wait on a slow model service. You may want such a call to stop at a deadline, so that your configuration script can choose a fallback route.

The Ravel CLI does not send a signal to a harness run itself. It asks the runner instead. Each run has a StopRequest, a flag that the runtime thread of the Ravel CLI sets. The runner also keeps a second flag of its own, for the output limit. It reads both flags at its 20-millisecond checks.

When one flag is set, the runner sends TERM to the run’s group and to the run, without the 2-second grace. If the run still exists after the 5-second kill grace, the runner sends KILL. Then it stops the group before the reap, reaps the run and confirms that the group is gone.

Three causes stop a run. Only the third ends the evaluation:

CauseWho asks for the stopWhat the configuration script sees
The deadline of the run: a timeoutMs in the ravel::run_harness call that is less than the time that remainsThe Ravel CLI, at that deadlineThe map with status timed_out. The script continues.
More than 1 MiB on standard output or standard errorThe runner’s own thread that reads the run’s pipes, through the runner’s second flagThe map with status output_limit. The script continues.
A stop of the whole evaluation: its deadline, a cancellation, the output limit of the script, or a worker that dies or breaks the protocolThe Ravel CLI, in Host::settleNothing. The worker receives no more replies, and Ravel refuses.

Without a timeoutMs, or with one that is not less than the time that remains, the run has no deadline of its own. The evaluation deadline then stops it as the third cause, and the script never sees timed_out.

Stop the evaluation at its deadline

The evaluation has one deadline for all of its work: the worker start, the reads, each harness run and select. The owner sets it as timeoutMs in the settings, and --timeout-ms replaces it for one session. The smallest permitted value is 1,000 milliseconds.

When that deadline expires during a harness run, the Ravel CLI stops the evaluation in this order:

  1. It records the first cause. A later cause does not repeat the stop.
  2. It abandons a file read in progress, and it does not wait for it.
  3. It asks the runner to stop a harness run in progress. The runner escalates from TERM to KILL, clears the group and reaps the run.
  4. It stops the worker with TERM, kills it if it is still there after one second, and reaps it.
  5. It removes the private directories and reports every cleanup failure.
  6. It reads the cancellation latch again, and then it refuses.

The sequence shows why harness cleanup precedes worker teardown, and why a later signal changes the final refusal.

Open the deadline sequence at full size.

The latch is a variable of the Ravel CLI. Its signal handlers keep the first INT, TERM or HUP there.

Only one host call runs at a time, so only one of steps 2 and 3 applies. A stop drops the host call that waits, which abandons a read at once. A run continues after that drop, until Host::settle asks the runner to stop it. The worker only waits for its reply and holds nothing that needs a graceful stop.

Host::settle waits at most 8 seconds for the runner. That is the 5-second kill grace, plus the runner’s bounds for a failed reap and for the group query. A process that survives is a worse outcome than the deadline. Thus, each failure of the run below replaces the deadline with harness_cleanup_failed, status 5:

Failure of the runHow Ravel then stops the worker
The runner does not settle the run in 8 secondsNo TERM. Ravel waits up to one second for the worker to exit, then kills it. The reap of the run is unconfirmed.
The run’s group stays after its reapNo TERM. Ravel waits up to one second for the worker to exit, then kills it.
The reap of the run failsNo TERM. Ravel waits up to one second for the worker to exit, then kills it.

Let a signal win over the deadline

Step 6 above reads the cancellation latch again. Why? A signal can reach the Ravel CLI while it stops the evaluation for another cause. The completion contract gives cancellation the first priority. Thus, a signal that the Ravel CLI consumed before its final read wins over the deadline.

During evaluation, the runner holds no signal handler. The Ravel CLI installs its own handlers for INT, TERM and HUP at the start of start-session. They keep the first signal in its latch. A signal that was ignored when the Ravel CLI started keeps that state and never reaches the latch.

The runtime thread reads that latch every 50 milliseconds. A harness run is in a POSIX session of its own, so a signal to the caller’s process group does not reach it. The Ravel CLI stops the run through its StopRequest.

Change one line of fake-advisor in ~/ravel-parts-deadline to see the rule. The new trap line also sends TERM to the fake’s parent, the Ravel CLI. That TERM arrives after the deadline and before the kill grace of the run ends.

Handle cancellation

Cancellation differs from a sent result. INT, TERM or HUP received by the Ravel CLI suppresses the result, even if the managed process already sent it. What Ravel stops depends on where the signal arrives:

Where cancellation occursWho holds the signalProcess actionResult
During selection, with a harness run in progressThe latch of the Ravel CLIStop the harness run through its StopRequest, then stop and reap the Rhai worker. Do not start the managed process.selection_cancelled, then session_cancelled. Return no result to the caller.
During selection, with no harness runThe latch of the Ravel CLIStop and reap the Rhai worker. Do not start the managed process.selection_cancelled, then session_cancelled. Return no result to the caller.
During supervisionThe runner’s handlers, which replace those of the Ravel CLI for the managed launch Forward the signal to the group and the direct child. If the child still runs after the kill grace, send KILL.session_cancelled. Complete cleanup attempts and return no result.

During supervision, the runner checks for cancellation before it accepts an observed child exit. The Ravel CLI also checks signals around supervision and final cleanup. Cancellation skips the result’s initial grace. If the kill grace has already begun, cancellation does not restart it.

The sequence shows why a sent result cannot survive cancellation during supervision. Ravel attempts cleanup before it raises the signal again.

Separate the three launch modes

The runner has three launch modes. The Ravel CLI uses two of them. The table compares the three modes:

ModeRunner interfacePOSIX session and inputOutput, completion and signals
Ordinary launch, for the managed processrun_observed_with_start_checkA new process group in the caller’s POSIX session. Inherited input, with terminal access when availableOutput goes to the caller’s standard error. A result can request shutdown. The runner installs cancellation handlers.
Captured launch, for each harness runrun_captured, with CapturedLaunchA new POSIX session, no controlling terminal, no inherited descriptors above 2 after exec. Standard input is the run’s stdin text, or end-of-file (EOF) without itThe runner’s thread reads both streams into buffers of 1 MiB each. A result requests shutdown, and so does a StopRequest. run_noninteractive has no production caller in Ravel. A test of crates/ravel/src/cancellation.rs calls it.

Why does a captured launch install no signal handler? The Ravel CLI owns its signals during evaluation. Its runtime thread watches the latch, the deadline and the worker together, and it decides when to stop the run. If the runner replaced the handlers of the Ravel CLI, that thread could lose a signal.

A new POSIX session removes the inherited controlling terminal relationship. It does not restrict file access, and a descendant can still move to another group. No mode of the runner restricts file access. These distinctions explain why the runner hides process mechanics behind separate launch interfaces, while the Ravel CLI owns the configuration script and result decisions.

Lend and recover the terminal

A controlling terminal belongs to a POSIX session. It has one foreground process group at a time. That group can read terminal input. With the default terminal modes, Ctrl-C sends INT to that group. A background group’s attempt to read can instead stop it with SIGTTIN.

Start the Ravel CLI in the foreground of an interactive shell. During selection, its group is then the foreground group, and the Rhai worker is in that group too. A harness run is in another POSIX session, so Ctrl-C does not reach it. During supervision, the runner lends the foreground to the managed group, under the rules below.

The runner opens /dev/tty, which names its controlling terminal. Redirected standard input does not remove that relationship. If the open fails, the runner proceeds without terminal job control. Detached modes, such as a harness run, do not open the terminal at all.

An open terminal alone permits no handoff. The runner queries its foreground group with tcgetpgrp and lends it only when the runner’s own group holds it. A Ravel CLI that starts in the background takes no foreground for itself. A shell can later give the foreground to the Ravel CLI’s group, for example with fg. Then a later supervision poll can lend the terminal to the managed group.

Before the first handoff, the runner saves the terminal attributes with tcgetattr. These terminal modes control such behaviour as character echo, line input and keyboard signals. An interactive program can change them to receive individual characters without echo. If KILL ends that program, the program cannot restore the modes itself.

The ordinary foreground launch follows these steps:

A background group can receive SIGTTOU when it changes terminal foreground. The runner therefore temporarily ignores SIGTTOU for the handback (the return of foreground to the runner’s group) and for mode restoration. Then it restores its previous disposition. It checks both the terminal operation and that restoration. The child also suppresses SIGTTOU for its handoff before it restores its entry signal state.

The lease remembers whether this launch ever held foreground. If it never did, the runner takes no foreground and restores no modes. For a lease that did hold foreground, the child’s outcome changes the rule:

Outcome and current holderForeground and mode action
The runner’s group already holds foregroundRestore the saved modes
Normal child exit, with the child’s group still foregroundTake foreground back, confirm it, then restore the modes
Normal child exit, with another group foregroundPreserve that holder and its modes
Known child death by signalReclaim from a positive foreground group other than the runner’s group or the POSIX session leader’s group. Restore modes only after confirmed ownership
Failed spawn or unknown child status, with the recorded child’s group foregroundAttempt the conditional handback described below, then restore modes after confirmed ownership
Failed spawn or unknown child status, with an unrelated group foregroundPreserve it and report unconfirmed foreground and mode recovery

The wider signal-death rule covers a managed supervisor that gives foreground to another group, then dies without cleanup. Otherwise, that delegated group could retain a raw terminal and continue to read input. The accepted cost is that a nested job-control shell can lose its foreground after such a death. Unknown child status does not permit this wider takeover. The POSIX session leader is the process that created the terminal’s POSIX session.

Exec can fail after the child takes foreground. The parent therefore retains the lease across a spawn error. The private pipe closes across exec and provides an attempted-group record, not proof of exec or a live group. If the record is missing or invalid, recovery is unconfirmed and Ravel reports it. The runner never signals that recorded number after failed spawn.

Failed-spawn handback requires two conditions through recovery: no other process or thread changes foreground, and no unrelated group reuses the recorded ID. These conditions also apply to recovery from unknown status. The foreground query and handback are separate operations. A one-session lifetime of the Ravel CLI does not make them atomic or establish those conditions.

Ravel reports failures of foreground queries, handback, mode restoration and temporary SIGTTOU restoration. After a recovery failure, Ravel returns no result to the caller. After failed spawn, the original spawn error stays primary unless cancellation overrides it. Recovery reports remain visible beside that outcome.

The tests use a pseudo-terminal, or PTY, to observe these operations without a human terminal. A PTY has two ends. The fixture uses one as its controlling terminal, while the test controls input and reads output through the other. Separate fixture processes keep terminal and signal changes out of the test runner itself.

Preserve the entry signal state

A signal’s disposition is the process-wide choice to use its default action, ignore it, or call a handler. A thread’s signal mask names signals whose delivery that thread blocks. A blocked signal can remain queued until the thread permits delivery. An ignored signal and a blocked signal are different states.

Exec replaces the program but preserves the thread’s signal mask. It resets caught handlers to default actions. It preserves ignored dispositions with one exception: portable code cannot assume that an ignored SIGCHLD stays ignored after exec. The POSIX exec specification states that exception. Ravel explicitly restores its recorded ignore/default values before exec on its supported targets.

On its supported targets, Ravel gives the managed process and each harness run the signal state that the Ravel CLI had at its executable entry. That is the state before Rust startup changes it. The table below gives the exclusions. For example, Rust startup ignores SIGPIPE. A capture in main would see that new ignore instead of the state that Ravel inherited.

The initialiser of the Ravel CLI in signal_state.rs records the ignored set and the initial thread’s mask before those runtime changes. It keeps that record separate from later repairs by the Ravel CLI and the runner. If a required query fails, the Ravel CLI refuses the launch. It does not accept a partial record. The runner receives the values through EntrySignals, in Launch.transparent for the managed process and in CapturedLaunch.transparent for each harness run. It does not capture them itself.

StateChild behaviour in a transparent launch
Recorded ignoreSet the signal to ignored before exec
Other recorded dispositionSet the signal to its default action. Do not copy a host handler
Recorded maskApply the mask after the dispositions, so delivery uses the restored actions
KILL and SIGSTOPLeave these unchangeable dispositions alone
Unsupported or runtime-reserved signal numbersExclude the platform’s specified numbers. A failure for another required number remains an error

The Ravel CLI and the runner also need signal state of their own. An ignored SIGCHLD or the SA_NOCLDWAIT flag can let the system discard child status without a parent reap. That would remove both the wait result and the identity reservation needed for group cleanup. The Ravel CLI checks and repairs this state before the Rhai worker starts. The runner checks it before each job starts: each harness run and the managed process. These repairs do not change the immutable child entry values.

For the managed launch, the runner installs handlers for nonignored TERM and HUP. It also handles nonignored INT when no terminal exists or the launch is transparent. Ravel uses a transparent launch, so a nonignored INT sent directly to the Ravel CLI can cancel it even while the managed group owns foreground. The runner leaves ignored cancellation signals ignored. For a harness run, the runner installs nothing, and the handlers of the Ravel CLI stay.

Terminal INT follows foreground ownership. Before handoff, it can reach the group of the Ravel CLI. After handoff, it reaches the managed group. The child’s death from that signal is not itself a cancellation observation by the Ravel CLI. Ravel can still return a result after child signal death if the Ravel CLI observes no cancellation and all required cleanup succeeds.

The runner’s handlers and SIGCHLD repair persist after its call returns, on success or failure. A synchronous return does not restore a host’s prior state. The table gives the restoration responsibility at each boundary:

BoundaryRestoration responsibility
EntrySignalsSupply the child’s ignore/default state and mask. It restores no host state
Runner returnReport the child outcome and recovery failures. Retain installed cancellation handlers and any SIGCHLD repair
Final cleanup of the Ravel CLICheck temporary masks and restore the saved INT/TERM/HUP dispositions under the conditions below
A host that resumes other workNeeds its own signal lifetime, late-cancellation policy and restoration contract. The current runner supplies no such guarantee

The Ravel CLI blocks its handled signals across the spawn transition of the managed process. After spawn reports success, its checked Started transition restores the parent’s entry mask. Failure enters bounded child teardown and terminal recovery. It does not return early with an abandoned child.

Started means spawn-reported success, not confirmed exec. A child can die before exec and still produce that event. Only an actual wait produces Reaped.

Which thread receives a signal? The system can deliver a process signal to any thread that does not block it. Ravel therefore blocks INT, TERM and HUP in each helper thread for its whole life:

ThreadWhat it doesHow it gets the block
config-stdout and config-stderrRead the worker’s standard output and standard errorThe Ravel CLI blocks the signals before it creates them, then restores its own mask
ravel-readerDoes every file read and every harness run of the evaluationThe same, through Shield::block in rhai_worker/reader.rs
keyed-launch-pipesReads the pipes of a harness runThe reader thread creates it, and a new thread inherits the mask of its creator

A block on only the main thread would leave another thread able to consume a signal during handoff. A stop can leave a reader thread alive until the Ravel CLI exits, for example after a bounded output drain or an abandoned file read.

On both success and failure, final cleanup keeps handlers installed while the Ravel CLI restores its entry mask and collects cancellation observations. It then blocks the handled signals, reads queued signal state and consumes the runner’s late signal. Under that block, it restores its saved handled dispositions. A failed block keeps the handlers. Unknown queued signal state never means that cancellation is absent.

Final conditionAction of the Ravel CLI
Known state, successful disposition restoration, no cancellationRestore the entry mask. Other cleanup checks still precede result output
Cancellation selectedReport it and cleanup failures, then check the default action, unblock and raise the selected signal. Use a numeric fallback if propagation cannot succeed
Queued signal query failed while signals remain blocked, with no selected cancellationKeep them blocked through diagnostics. Return failure without a result
Required mask or disposition operation failedRetain the failure report and return no result

An entry-blocked signal does not become cancellation merely because it is queued. The managed child receives that entry block too. The final signal decision of the Ravel CLI follows the priority in chapter 8. Its cleanup restores the saved handled dispositions and temporary masks. It does not undo the SIGCHLD repair or restore every runtime signal change for a host that continues after the call.

Know the guarantees and their limits

Each guarantee below includes the boundary within which it holds. The successful result is evidence of the required checks, not proof that every descendant or hostile same-user process is absent.

Native-entry behaviour has measured support on aarch64 macOS and aarch64 GNU/Linux. Each measurement covers its named kernel, libc and compiler, not every combination. The GNU/Linux measurement used Rust 1.85.0. Native x86-64 Linux remains unqualified: builds, lint checks and QEMU user-mode execution do not qualify an x86-64 kernel.

The current runner is a private package within Ravel. Neither that package boundary nor these checks deliver a persistent runner for an arbitrary host.

Ravel supports no separate component. The runner serves the Ravel CLI, which supervises one session and then exits. The runner’s return does not restore process-wide signal state. Another program invokes the Ravel CLI as a child process. Thus, the signal state that the runner changes stays in that child process and ends when it exits.
