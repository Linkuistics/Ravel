The Ravel book

Run sessions

Chapter 1 followed one code review. An orchestrator, a program that runs LLM work as steps of its own work, wanted an LLM to review the last commit. It wrote a prompt file, review-prompt.txt. The prompt told the LLM to run ravel end-session approved if it found no problem. If it found a problem, the LLM wrote review-notes.md and ran ravel end-session changes-needed. Then the orchestrator ran this command:

Fragment: the request of chapter 1’s review. This block omits the code of the orchestrator that runs the command.

ravel start-session --kind review --prompt-file review-prompt.txt

The LLM found a problem. Ravel wrote changes-needed on standard output, and ravel start-session exited with status 0. Then the orchestrator read review-notes.md and requested a session of the kind fix.

Now you want to write the orchestrator’s side of that review, or of your own work. What does your program give to Ravel? What does each output and each exit status mean, and what does your program do next? This chapter answers these questions with the review and with other real examples.

The chapter also shows how to read the routing notice. That notice tells the caller which harness, model and effort the configuration script chose. It shows how to run a session inside another session. It also states what the managed process receives from Ravel.

Supply the prompt and caller data

What does the selected program receive, and how can you give the configuration script more facts about the task? You may want the LLM to receive your instructions exactly as you wrote them. You may also want the configuration script to choose a program from facts such as a profile name or a task file. This section shows the inputs of start-session that do these things.

First, look at the prompt. The orchestrator of the review wrote this file before it ran start-session:

Ravel adds no instructions to end the session. An interactive harness does not exit when its LLM completes the task. It waits for more input. Thus, your prompt tells the LLM to run ravel end-session RESULT when the task is complete. RESULT is a placeholder for the text to send.

The values and their meanings are your convention. Ravel gives them no meaning.

Pass exactly one of --prompt TEXT and --prompt-file PATH. Ravel gives the text to the configuration script unchanged in request.originalPrompt, also when it is empty or ends with newlines. With skill delivery enabled, request.prompt also holds discovery instructions before that text. It never reads a prompt from its standard input. A prompt is UTF-8, contains no NUL and has a maximum size of 1 MiB. Ravel does not truncate input that is not valid, but stops the invocation with status 2.

InputWhen to use itWhat Ravel reads
--prompt TEXTA short prompt that you write in the commandThe argument, as the shell gives it to Ravel
--prompt-file PATHA prompt whose exact text is important, for example with trailing newlinesThe file, relative to the caller’s working directory

The argument limits of the operating system can be smaller than 1 MiB. These limits also apply when the configuration script puts a prompt from a file into the arguments of the selected program.

Why is a file safer for exact text? Shell command substitution removes trailing newlines. Thus, --prompt "$(cat prompt.txt)" can change the text before Ravel receives it. --prompt-file prompt.txt reads the file directly. With skill delivery disabled, Ravel changes no text before the configuration script receives it. Then the script makes the arguments of the selected command and decides how to give the prompt to that program.

The kind is a required caller token that is not empty. Ravel has no catalogue of kinds and does not get a kind from a file name. A configuration script can select a program for review, refuse it or treat it as any other kind. The caller and the owner agree on these tokens.

The caller can also use the kind to extend or modify the prompt. For example, if the harness supports skills, the caller can add a line to the prompt for the kind review. That line tells the LLM which skill to load. The configuration script can also put text before the prompt for a kind. Ravel gives neither the kind nor the prompt a meaning.

Ravel does not run your configuration script in the Ravel CLI’s own process. It launches a second copy of the ravel executable as a child process. That child is the Rhai worker. The worker evaluates the configuration script and sends the selection or the refusal to its parent. Chapter 1 gives three reasons for a separate process:

  • The deadline. At the deadline, the parent ends evaluation and can signal the worker. A kernel stall can delay the worker’s exit.
  • Requests from the script. The worker only computes. When the script reads a file or runs a harness, the worker asks the parent, and the parent does the work.
  • Isolation of a failure. If the script exhausts the memory of the worker or overflows its stack, only the worker stops. The parent reports the failure and launches no program.

The worker ends before Ravel launches the selected program. Ravel waits until the worker exits and collects its exit status. Only then does Ravel launch the managed process.

The request of the script in the second reason uses a host capability, a ravel:: function such as ravel::read_text or ravel::run_harness. Each such request is a host call.

How long can evaluation take? The evaluation deadline defaults to 30 seconds and covers every host call. An LLM call is a harness run that asks a model a question. It uses that same deadline.

The owner can set timeoutMs in the settings. For one invocation, --timeout-ms replaces that value. The permitted range is 1,000–600,000 ms. This bound applies to the evaluation of the configuration script, not to the time that the managed process works.

The owner also sets budgets.harnessRuns, from 0 to 16, in the settings. This evaluation budget limits the number of harness runs in one evaluation. Its default is 0, and callers have no flag that raises it.

The selected program runs in the caller’s working directory. The form of its program path sets the base that Ravel uses to find the program:

Selected programResolution base
Absolute pathThe path itself
Relative path that contains /The caller’s working directory
Bare program nameThe caller’s PATH

Ravel gives the argument strings directly to the program, without shell word splitting or expansion.

How does the managed process get its environment? A child process gets a copy of the environment of its parent. Thus, the managed process gets the environment of the Ravel CLI, which is the caller’s environment. Ravel makes these changes to that copy before the launch:

  • It removes RAVEL_RUN_ID, RAVEL_STATE_DIR, HARNESS_DISPATCH_EXIT_FILE, HARNESS_DISPATCH_RUN_ID and HARNESS_DISPATCH_STATE_DIR. These variables are controls of an enclosing session or of another launcher.
  • It replaces RAVEL_EXIT_FILE with the path of the result file of the new session.
  • It replaces RAVEL_SKILL_DIRECTORIES with this session’s descriptor path, or removes it when skill delivery is disabled. The descriptor records the retained skill directories. It grants no authority to end the session.

Thus, end-session in the program and its children finds only the path of the session that Ravel made for them. Put the installed ravel on the PATH of the managed process. As an alternative, write the absolute path of ravel in the prompt’s instructions to end the session.

Give the agent the owner’s skill directories

The owner can configure skill sources in the skills object of the settings. Without that configuration, Ravel reads the sources that packages install in its default skill directory. With Homebrew, that directory is $(brew --prefix)/share/ravel/skills. "sources": [] in the skills object turns the default skill directory off.

When there are sources, each start-session prepares them before it evaluates the configuration script. The caller and the configuration script need no new input for this. Ravel finds no skill and gives no meaning to a skill name. The agent finds and reads the skills that apply to its work.

Ravel puts the discovery instructions before the caller’s prompt in request.prompt. The caller’s bytes follow, unchanged, between two delimiter lines. request.originalPrompt keeps the caller’s prompt alone. Your instructions to end the session stay exact, because Ravel does not read or change them. A caller instruction to load a skill “first” comes after the mandatory reads. Write “after any mandatory guidance” when that order matters to you.

The managed process and each harness run also receive RAVEL_SKILL_DIRECTORIES, the path of the descriptor of the directory set. An agent that loses the path from its prompt can read it there. With delivery disabled, Ravel removes that name from their environment. When the agent loses both paths, it reports that the discovery context is missing. Ravel supplies no other path, and the cache holds no pointer to a latest descriptor.

The snapshots and the descriptor stay after the session. At the end of the session, Ravel stops only the processes in the process group of the managed process. A delegate that left that group can read the resources after the session ends. So can a harness that you start with the output of ravel skills resolve. The resources also stay after a change or removal of the source and after a change of the settings.

A skill refusal stops the launch before the worker starts. For example, a missing source or a missing mandatory file refuses with status 3, and no managed process starts.

Ravel refuses a skill source that overlaps a protected path before it copies the source. That refusal is skill_access_unavailable, with status 3. Keep each source apart from these paths:

Accept a result only after success

When can your program trust the result? You may want to act on the result as soon as a program in the session sends it. But Ravel can still fail after that moment, for example during cleanup. Thus, keep the result bytes and the status of start-session together, and accept the result only with status 0.

Two operating-system words explain the conditions of status 0:

WordWhat it meansWhy status 0 depends on it
Process groupA set of processes that the operating system can signal together. Ravel puts the managed process in a new group. Its descendants stay in that group unless they leave it.When the group is gone, no process of the session that stayed in the group still runs.
ReapA parent collects the exit status of its child process.After the reap, Ravel knows that the managed process ended.

Status 0 means that all of these conditions are true:

  • A program in the session sent a valid result.
  • Ravel reaped the direct child, which is the managed process.
  • Ravel confirmed that the process group of the managed process is gone.
  • The required cleanup succeeded.
  • The final write and flush of the result succeeded.

An empty sent result is a successful result with zero bytes. If a managed process exits with status 0 and sends no result, the status is 1. Ravel then returns no result to the caller. But if a program sends a result and the child then exits with a nonzero status, start-session can still give status 0. Ravel’s status shows whether Ravel delivered a sent result after cleanup. It does not show whether the work in the prompt was correct.

end-session takes one UTF-8 argument with a maximum size of 1 MiB. Quote it, and put -- before a value that looks like an option, such as --help. Ravel writes an empty, multiline or Unicode value unchanged to standard output and does not interpret it. The operating system can apply a smaller limit for command arguments before end-session runs.

How does Ravel receive the result? end-session writes it through the result channel, the private directory and result file that Ravel made for the session.

Ravel keeps the first complete result that it receives. When that first result arrives, Ravel starts to stop the harness. Thus, a second end-session call and the shutdown are in a race: either can occur first. For example, another process in the group can send a result before Ravel stops that process. Ravel keeps the first result, even if the second command succeeds.

end-session returns before the enclosing session finishes its cleanup. When Ravel detects the sent result, a job that still runs gets 2 seconds to finish. Then Ravel sends TERM, waits for up to 5 more seconds and sends KILL if necessary. These waits end early if the direct child exits. Ravel then stops the other group members before it reaps the child. Those members do not get a new 2-second wait.

Send the result after the work that has to finish, because Ravel can stop code that comes after end-session.

For an automated caller that needs trailing newlines intact, redirect standard output to a file. Read the file only after you check the status. Shell command substitution removes trailing newlines. Use it only when the caller’s result convention accepts this change. A failed final write can leave only the first part of the result in the file, so the bytes alone do not prove success. Ravel has no persistent store for results, so it cannot recover a result after a failed delivery.

Keep nested sessions separate

You may want the program of one session to start another session. For example, an orchestrator can run as a harness and ask Ravel for a review session as one step of its work. Then it uses the review’s result in its own work. The program that asks is the caller of the inner session. How does each end-session reach the right session?

The answer is the path in RAVEL_EXIT_FILE. Chapter 1, “How end-session finds its session”, explains it, and this section restates it for nested sessions. Before each launch, Ravel makes a result channel, which is a private temporary directory with a path for one result file. Ravel puts that path in the RAVEL_EXIT_FILE environment variable of the program that it launches. The book calls this path the session-result context.

A child process gets a copy of the environment of its parent. Thus, each descendant of the managed process inherits the same path, unless its parent changes the environment. ravel end-session finds the path in its own environment. end-session takes no session ID and no target argument. Know what the managed process receives

Ravel launches the selected program as an ordinary child process.

Ravel does not restrict the filesystem access of the managed process. The process can read and write each path that your account permits, within the limits of the harness sandbox. The configuration script selects that sandbox through the arguments of the harness, such as --sandbox workspace-write for Codex. Evaluation harness runs have the same rule. Chapter 2 states this trust limit.

Ravel 2.0.0 refuses --confine and --runtime-read with confinement_withdrawn and status 2. It refuses before it reads the settings or starts the worker. Remove both flags, and select the sandbox of the harness in the configuration script. Ravel 1.1 keeps --confine.

The managed process inherits the caller’s environment, with the changes that Supply the prompt and caller data lists. --config-env grants a variable to ravel::env, the environment helper of the configuration script. It adds no variable to the managed process or to a harness run. Managed-process environment gives each name.

Ravel puts the private result channel of the session in the caller’s temporary directory. That is TMPDIR, or /tmp when TMPDIR is not set. --exit-dir DIR puts the channel in DIR instead. Name a writable directory that exists. Before selection, Ravel refuses a path that is not a directory with exit_dir_unusable and status 2. If Ravel cannot allocate the channel after selection, it stops with session_channel_unavailable and status 5.

Ravel launches the managed process in a new process group in the caller’s POSIX session. A POSIX session is an operating-system set of process groups that can share one controlling terminal. It is not a Ravel session.

To lend the terminal, Ravel makes the group of the managed process the foreground group of the terminal. Then that group receives the keyboard input. Ravel lends the terminal only if its own process group is the foreground group of the terminal. After the session, Ravel attempts recovery if it lent the terminal. Recovery also depends on which group holds it then, as chapter 9 explains.

The managed process can also read the caller’s standard input. Chapter 9, “Jobs, signals and the terminal”, teaches the mechanism.

Read notices separately from results

Your program needs the result. It can also want to know what the configuration script chose. For example, the orchestrator of the review can record which harness, model and effort did each review. Ravel gives these two kinds of information on two different streams. This section shows what each stream carries and when Ravel writes to it.

In chapter 1’s run of the review, the two streams had these lines:

StreamLine in the reviewWho reads it
Standard outputchanges-needed, with no newlineThe orchestrator, as the result
Standard errorravel: starting provider local, model fake, effort low for kind "review"The person or the log that watches the session

The line on standard error is the routing notice. Where do its values come from? The configuration script gives back a selection or a refusal.

A selection is the map that select returns when it chooses a program. It holds program and args, the command that Ravel runs. It also holds the labels provider, model, effort and reason. In the review, the labels were local, fake, low and Reviews go to the fake agent.

A label describes the choice of the configuration script, but it does not configure the harness. For example, a script that selects Claude Code puts the model option of Claude Code in args. The model label only tells the caller which model the script chose. These labels are owner text, not integrations with model providers.

The caller does not read the owner’s configuration script. Thus, Ravel tells the caller what the script chose in the routing notice:

  • Who writes it: the Ravel CLI.
  • When: in text form, after the configuration script selects a program and before Ravel launches it. In JSON form, after the supervision attempt.
  • Where: the caller’s standard error. Standard output carries only the result.
  • Who reads it: the caller, or the person who watches the terminal.
  • Why: this notice is the way in which Ravel tells the caller which harness, model and effort the configuration script chose.

The text form is one line that starts with ravel: starting provider. It gives the selected provider, model, effort and kind. --json replaces that line with the JSON routing notice, a JSON document on one line. The document gives more detail, such as the reason and the program file that Ravel found. When Ravel cannot complete a session, --json also replaces the text diagnostic with a JSON document, the failure document.

Thus, a process API reports termination by that signal, not a numeric exit. If the propagation of the signal fails, Ravel reports that failure and exits with the same number as a fallback. A caller that uses a process API handles both forms.

A signal such as KILL can stop the Ravel CLI at any point. The normal procedure of Ravel does not apply to such a signal. Then the shell status does not show that cleanup or result delivery occurred. Also, a new signal that arrives after the final cancellation decision can interrupt the result write. No atomic guarantee covers both the arrival of a signal and an arbitrary write to standard output.

After evaluation decides its failure, the final cleanup does not replace that failure’s status. During evaluation, failed harness cleanup can first replace a deadline with harness_cleanup_failed. Only a valid result with confirmed cleanup reaches the final write.

Cancel during selection or supervision

You may need to stop a session before it ends. For example, the person at the terminal presses Ctrl-C, or your orchestrator stops its wait. A cancellation is an INT, TERM or HUP signal that reaches the Ravel CLI. Ravel then stops the work, attempts cleanup and returns no result to the caller. What Ravel stops depends on the phase of the session:

PhaseWhat runsWhat Ravel does at a cancellation
Skill resolutionThe copy and the storage of the skill sources, when the owner settings enable deliveryRemoves its private temporary directory. Starts no worker. The refusal is skill_resolution_cancelled.
SelectionThe Rhai worker, and any harness run that the configuration script startedAttempts to stop and reap the harness run, then the worker. Launches no managed process.
SupervisionThe managed process and its process groupAttempts to stop the group, to reap the managed process and to recover the terminal. Returns no result, even after a sent result.

A cancellation during selection stops evaluation and prevents the managed launch. Ravel abandons a read in progress and does not wait for it. If a harness run is in progress, Ravel first stops its group and attempts its reap. Then it stops and reaps the worker and removes the private directories. Ravel reports the cancellation with any cleanup problems.

The worker has no session-result context. Thus, it cannot send a result for an enclosing session through the usual end-session interface.

Know when Ravel cannot guarantee cleanup

What can an unsuccessful invocation leave behind? Ravel’s cleanup guarantee does not apply under the conditions in this table. Use the table to decide what the caller examines after such an invocation:

ConditionConsequence
Code that runs as the same user makes unauthorised changes to the result channel or the installation.Private paths and the inherited session-result context keep ordinary sessions apart. They are not a defence against hostile code of the same user. The worker identity check confirms that the re-executed binary reports the expected build. It does not check a trusted signature.
The Ravel CLI stops abruptly, for example because of KILL.It cannot complete supervision or cleanup. The group of the managed process and the temporary directories can remain. There is no successful completion and no persistent recovery record.
A managed descendant deliberately leaves its process group.It is outside the cleanup guarantee of that group. The absence of the group does not prove that the detached process is gone.
An evaluation harness run starts a descendant that leaves its process group.Cleanup of the run does not reach that descendant. The Rhai worker itself starts no program.
Another process changes the foreground group of the terminal during recovery, or the system gives a recorded group ID to an unrelated group.Recovery assumes two conditions between the runner’s check and its handback. No other process or thread changes the foreground group. No unrelated group gets the recorded group ID. Ravel reports a failed handback. Do not treat a launch failure as proof that Ravel restored the terminal. Chapter 9 explains the conditions.
The host is different from the measured platforms.The project measured how Ravel handles inherited signal settings, cancellation, cleanup and terminal recovery. It measured them on aarch64 macOS and aarch64 GNU/Linux. The project built Ravel for x86_64 GNU/Linux and ran it only under emulation. Native x86-64 qualification is not complete. These checks do not cover all combinations of kernel, libc and compiler.

Chapter 2 explains these trust limits. Ravel issue 1 tracks the native x86-64 qualification. The examples in this chapter check the choice of command, the delivery of the result and the status. They do not show the behaviour of real agents, interactive terminal operation or whether a new reader can use the book.

Check your caller before real use

In short, the caller runs ravel start-session with a kind, a prompt and optional caller data. The configuration script selects a program, and the Ravel CLI tells the caller about that choice in the routing notice on standard error. Ravel launches the program with a new path in RAVEL_EXIT_FILE. A program in the session sends one result to that path with ravel end-session. Ravel stops the program and its process group, completes cleanup and writes the result unchanged on standard output.
