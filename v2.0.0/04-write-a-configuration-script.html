Write a configuration script

In chapter 1, an orchestrator asked Ravel for a code review with the kind review. A short Rhai script chose the program for that kind, and Ravel ran it. You write that script. This chapter teaches you to write and check a configuration script, and to let an LLM help it choose.

Know the Rhai language

What is Rhai? Rhai is a small computer language for programs in the Rust language. The Rhai engine is part of the ravel executable. Thus, you install no separate language runtime for your configuration script. Chapter 1 introduces Rhai with a short script. These characteristics of Rhai are important for a configuration script:

  • A familiar syntax. Rhai looks like a mix of JavaScript and Rust. It has variables, functions, if, loops, arrays and maps.
  • Dynamic types. You do not declare a type. Each value has its type while the script runs.
  • A sandbox. Rhai code changes things outside the script only through functions that the host program gives it. In Ravel, these are the ravel:: functions.
  • Protection against runaway scripts. Ravel sets limits on the operations, the call depth and the data size of a script. One deadline covers each evaluation.
  • Modules. A configuration script can import other Rhai files.

Each example explains the Rhai that it uses. Rhai also has its own documentation:

  • The Rhai Book is the manual. On 27 October 2026, it documented Rhai 1.27.0, the version that Ravel contains.
  • The language reference gives the syntax in a short form.
  • The online playground runs Rhai code in your web browser. It has no ravel:: functions and none of Ravel’s limits. Thus, a script that calls a ravel:: function does not run there.

Follow the evaluation of a configuration script

What happens between the caller’s command and the start of a program? Start with the review of chapter 1. The orchestrator ran the command below.

The configuration script of that chapter had one rule. For the kind review, it selected fake-agent and put You are a careful code reviewer. before the caller’s prompt. The table follows that request from the command to the start of fake-agent. In the table, the Rhai worker is a second copy of the ravel executable that evaluates the script. This section explains it after the table.

OrderWho actsWhat happens in the review
1The orchestratorRuns ravel start-session with the kind review and the prompt file
2The Ravel CLIReads the settings, finds the configuration script and starts the Rhai worker
3The Rhai workerRuns the top-level statements of the script one time. Here, they are only the two export const lines.
4The Rhai workerCalls select(request, context). request.kind is review, so select returns a selection of fake-agent.
5The Ravel CLIChecks the map that select returned, reaps the worker and checks the selection again before launch
6The Ravel CLIWrites ravel: starting provider local, model fake, effort low for kind "review" on the orchestrator’s standard error, then starts fake-agent

A successful selection follows this order. The values depend on the request and the script. A script can also define load_context(request), which the worker calls between steps 3 and 4. The section “Supply selection context” teaches it. With --json, the routing notice is a JSON document, and it follows the supervision attempt.

To reap a child process, its parent collects the exit status of that child. Ravel reaps the worker before it starts the selected program. Thus, the Rhai worker no longer runs when the selected program starts.

A selection is the map that select returns when it chooses a program. In the review, it held fake-agent, one argument and the labels local, fake and low for the provider, model and effort. A refusal is a map that says why Ravel starts no final managed process. The routing notice is the line in step 6. It tells the caller which provider, model and effort the configuration script chose. Chapter 1, “The selection and the routing notice”, shows both with real values.

What is the Rhai worker? The Ravel CLI, the ravel command-line program, does not run your script in its own process. It starts a second copy of its own executable as a child process. That child is the Rhai worker. The worker evaluates the configuration script and sends the selection or the refusal to its parent.

The worker has an empty environment. It has no direct access to files, the network or other programs.

Why a separate process? The parent stays in control while the script runs:

ReasonWhat the separate process permits
The deadlineWhen the deadline expires, the parent ends evaluation and can signal the worker process. Rhai cannot interrupt some of its own functions, such as sleep. A kernel stall can delay the worker’s exit.
Requests from the scriptThe worker only computes. When the script reads a file or runs a harness, the worker asks the parent. The parent does the work and sends the data back.
Isolation of a failureIf the script exhausts the memory of the worker or overflows its stack, only the worker stops. The parent continues, reports the failure to the caller and starts no program.

The worker does not run at the same time as the selected program. Ravel waits until the worker exits and collects its exit status. Only then does Ravel start the program that the script selected.

How does the script read a file or start a program, if the worker cannot? It asks the Ravel CLI. A host capability is an operation that the configuration script asks Ravel to perform. Each host capability is a function in the ravel namespace, such as ravel::read_text.

When the script calls a host capability, the worker sends the request to the Ravel CLI over a private socket and waits. The Ravel CLI does the work within the limits of your settings and sends the answer back. For the script, the call looks like an ordinary function call. The data helpers, such as ravel::json_parse, are different. They run inside the worker and send no request.

The script can call host capabilities at the top level of the module, in load_context and in select. A measured read is a read of a file through ravel::read_text or ravel::read_json. Ravel reads the file for the script and records its canonical path, its byte count and its SHA-256 digest. The JSON routing notice lists each measured read and each harness run of the evaluation.

A harness is the program in which an LLM works on a prompt, such as Claude Code or Codex. Your configuration script can use a harness in two different ways:

Use of the harnessWhen it runsWhere its answer goes
A harness runDuring evaluation, when the script calls ravel::run_harnessBack to the script, as data for its choice
The managed processAfter evaluation, when the script selects the harnessTo the caller, as the result of the session

The managed process is the program that Ravel starts and supervises for the session. Ravel starts it only after the evaluation ends and Ravel reaps the worker.

Define a configuration script and read the request

The config.rhai of fixed-route has two export const lines and one function. What must a configuration script contain, and where does Ravel find it? Ravel looks in one place. The default script is $HOME/.config/ravel/config.rhai. HOME must be absolute for that default.

--config PATH selects another file, relative to the caller’s working directory. Ravel searches no parent directory and tries no fallback script. Thus, a missing script is an error. It is not a silent change of route.

The file must be readable UTF-8, regular, and at most 1 MiB. A symlink identifies its canonical real file.

A configuration script is a Rhai module. A module is one file of Rhai code, which can export constants for other code to read. Your script exports two constants and defines a function:

DeclarationPurpose
export const SCHEMA_VERSION = 4;Name the version of the interface between Ravel and the script that this file uses.
export const VERSION = "fixed-route-1";Name this revision of your script. The JSON routing notice shows it.
fn select(request, context)Return a selection or a refusal.
fn load_context(request)Optionally assemble selection context before select.

SCHEMA_VERSION is independent of the Ravel release and of the version of the context document. VERSION is a nonblank string that you change when your script changes. The functions need the parameter counts shown above. Top-level statements run once before the functions.

The select function of fixed-route used this Rhai:

  • #{ ... } makes a map, which is a set of named fields.
  • request.prompt reads the field prompt of the map request.
  • [request.prompt] makes an array with one element.
  • The last expression of a function, without a semicolon, is its return value. return value; returns earlier.

What can the script read about the request? The request is a map with these fields. Optional inputs have the value () when they are absent. In Rhai, () means “no value”, and it becomes null in JSON.

FieldValue
schemaVersionThe integer 4.
kindThe caller’s kind token, from --kind.
originalPromptThe caller’s prompt, unchanged.
promptThe prompt to give to the harness. With skill delivery disabled, it holds the same bytes as originalPrompt. With delivery enabled, it holds the discovery instructions, then the caller’s prompt in one delimited block.
cwdThe caller’s working directory.
paramsA map of strings from --param NAME=VALUE.
taskFileThe absolute --task-file path, or (). Ravel does not read it.
taskIdThe --task-id string, or ().
contextThe caller’s checked context document, or ().
skills() with skill delivery disabled. Otherwise a map with descriptorPath, sources, directories and mandatory.
limitsThe effective bounds that the script can read.

Put request.prompt into the arguments of the harness. Read request.originalPrompt when the script examines the task, for example when it asks a model to classify the task.

The owner can enable skill delivery in the settings. Then request.prompt also holds the skill directories and the discovery instructions, and the script needs no change for them. A harness that reads only some directories needs a read grant for the skill snapshots. Make that grant from request.skills, for example one argument for each snapshotRoot. The shipped example harness-table.rhai does this for its lead harness.

Excerpt from crates/ravel/examples/harness-table.rhai: the function that lists the snapshot roots. The function harness_args puts each root after --add-dir.

fn skill_reads(skills) {
    if skills == () { return []; }
    let reads = [];
    for source in skills.sources { reads.push(source.snapshotRoot); }
    reads
}

Skill delivery at launch gives the parts of the prepared prompt and the members of request.skills.

The second argument, context, is the delivered selection context: JSON data for the choice. A loader can make it different from request.context. Neither value gives the script authority to end the session.

Ravel checks undefined variables when it compiles the script. It also refuses an absent map property when the script reads it. Check request.params.contains("name") before you read an optional parameter. The documented request fields themselves are always present.

Select a command or refuse

Your configuration script gives one of two answers to each request. A selection tells Ravel which program to start. A refusal prevents the start of the final managed process. Why refuse? You may want a request that does not fit your routes to stop with a clear message, and not go to the wrong harness.

A selection is the map that select returns when it chooses a program. Its status field is "selected". A selected map holds seven fields, and Ravel needs each of them. Ravel refuses an unknown field.

FieldWhat the script supplies
statusThe literal "selected".
programA nonblank program name or path, without NUL.
argsAn array of strings after the program. Empty strings are valid, but NUL is not.
providerA nonblank owner label for the model origin.
modelA nonblank owner label for the model.
effortA nonblank owner label for the effort.
reasonA nonblank explanation of the choice.

A bare program name resolves through the caller’s PATH. A relative path with / resolves from the caller’s working directory. Each member of args is one argument. Ravel performs no word splitting, shell expansion or template substitution. A prompt with spaces therefore stays one argument when the script puts it there.

program and args are the command that Ravel starts. provider, model, effort and reason are labels. A label describes the choice of the script, but it does not configure the program. For example, model: "haiku" records a label, whereas args: ["--model", "haiku"] gives a model option to a program. Your script sets both, and Ravel does not compare them.

Why have labels, then? The caller usually wants to know what the script chose, but the caller does not read your script. Ravel tells the caller in the routing notice. Before it starts the program, the Ravel CLI writes one line on the caller’s standard error. For the first example of this chapter, fixed-route, that line was:

Fragment: the routing notice of fixed-route, on standard error. This block omits the command, the reports of cleanup operations and the result on standard output.

ravel: starting provider example, model fake, effort low for kind "question"

With --json, a JSON document replaces this line after the supervision attempt. That document also gives the reason. Chapter 5, “Read notices separately from results”, teaches both forms.

A refusal is a map with status: "refused" and three more strings. Each string is nonblank:

FieldWhat the script suppliesWho reads it
codeA short token that names the reason, such as unknown_kindA caller program that acts on the reason
messageA sentence that says what is wrongThe person who reads standard error
remedyA sentence that says what to changeThe person who reads standard error

After a refusal, Ravel reports config_refused with exit status 3. Your code appears separately as configCode in the JSON failure document. No managed process starts, and Ravel tries no other route. The caller receives no result.

{"skills":{"schemaVersion":1,"sources":[]}}

config.rhai

export const SCHEMA_VERSION = 4;
export const VERSION = "checked-route-1";

fn refuse(code, message, remedy) {
    #{ status: "refused", code: code, message: message, remedy: remedy }
}

fn select(request, context) {
    if request.kind != "question" {
        return refuse("unknown_kind", "This configuration script accepts question only.",
                      "Use --kind question.");
    }
    if request.params.contains("model") {
        return refuse("owner_model", "The owner chooses the model.",
                      "Remove the model parameter.");
    }
    #{ status: "selected", program: "fake-agent", args: [request.prompt],
       provider: "example", model: "fake", effort: "low", reason: "question route" }
}

Validate a configuration script with fake agents

How do you know that your configuration script does what you want before a real harness runs? You test it with fake agents. Ravel has no separate command that type-checks a script or evaluates it without the start of a program. start-session evaluates the script and then runs the selected program. Thus, each test of a script is a real session. A fake agent makes that session cheap and safe, because it only sends back its arguments.

For each route, test the arguments and the result. For each refusal, test the diagnostic and absence of a managed process. Include absent optional inputs, unknown kinds and malformed local data. The examples in this chapter show success and failure at that same boundary.

You may also want to see values while the script runs. print(text) writes to the script’s standard output, and debug(text) writes to the script’s standard error. Ravel captures both streams of the Rhai worker. Then it writes the captured text on its own standard error, before the routing notice. Each line starts with config stdout: or config stderr:.

These lines are diagnostics for you. They are not the opaque result on Ravel’s standard output, which Ravel does not interpret. The managed process sends that result with end-session. With --json, the JSON routing notice holds the captured text in its diagnostics member.

Supply selection context

You may want facts about the task to change the choice. For example, a large change can go to a higher effort, or a task with a security label can go to a particular model. Selection context carries such facts to select.

The book uses the word “context” for three different things. This section is about the second:

NameWhat it isWho uses it
Session-result contextThe path in RAVEL_EXIT_FILE, through which end-session sends the resultThe managed process. The configuration script never receives it.
Selection contextA JSON document of data for the choiceselect, as its second argument
The caller’s working directoryThe directory of the request, in request.cwdThe script, for measured reads and relative program paths

Selection context is data for the decision, not authority to execute a command. The caller can supply a JSON context document with --context PATH. Without a loader, select receives that document with its measured source, or () when no document exists.

Why write a loader? You may want facts that the caller does not send, such as a file in the caller’s repository. A load_context(request) function can assemble a different document. Ravel calls it before select.

The loader can read the caller’s input at request.context and read local sources. Ravel checks its return value before it calls select. A loader that returns () gives context_invalid. A loader can also return a refusal, in which case select never runs.

Check JSON with the data helpers

Your configuration script reads JSON from files, and later from models. You may want to be sure that this JSON has the shape that you expect before the script acts on it. A model can give an answer with a wrong field or a value that you did not offer. The data helpers let the script parse, check and write JSON strictly.

Ravel supplies strict JSON operations in the ravel namespace. They run inside the Rhai worker and send no request to the Ravel CLI. Use them for data that crosses between the script and another program. The Rhai built-in parse_json accepts syntax that strict JSON rejects. Its to_json can produce string escapes that are not JSON.

Set bounds and environment grants in the settings

You may want to give a slow configuration script more time, or let the script read an environment variable of the caller. You may also want to name the harnesses that the script can run. Your settings do each of these things. They are the second part of your configuration, in a JSON file next to the default script.

Ravel reads the settings from $HOME/.config/ravel/settings.json. It reads this file also when --config selects another script. Thus, a script that you copy to another place does not carry its own settings. An absent file sets nothing. Each key is optional, and Ravel refuses unknown keys.

KeyMeaning and range

The whole deadline covers module loads, the context loader, selection and all host calls. It does not bound the final managed process. At expiry, Ravel reports selection_timeout, exit status 124. Run a harness during evaluation

You may want an LLM to choose the best harness, model, effort and prompt additions for a kind and a prompt. You can do this with a harness run in your configuration script. A harness run is one run of a program from your harnesses settings, during evaluation. The script starts it with the host capability ravel::run_harness. Then the script reads the output of the run as data and makes its own choice.

How does the answer get back to the script? Follow one harness run:

OrderWho actsWhat happens
1The configuration scriptCalls ravel::run_harness with the name of a settings entry, the arguments and the text for standard input
2The Rhai workerSends the request to the Ravel CLI and waits
3The Ravel CLIFinds the entry’s program, checks the run budget and starts the program in a new POSIX session with its own result channel
4The harness runReads its standard input, writes its answer on standard output and exits
5The Ravel CLIStops the processes that remain in the group of the run, completes cleanup and sends a map back to the worker
6The configuration scriptReads status, exitCode and stdout from the map, then continues

The harness run returns its answer to the script before Ravel starts the final managed process.

The answer goes back to the script, not to the caller. The caller sees the script’s selection in the routing notice and receives the final session’s result after cleanup. The JSON routing notice also records each harness run, but not its prompt or its answer.

harnessRequired name of a settings entry.
argsRequired array of argument strings, without NUL.
stdinOptional text for standard input. Without it, input is at end of file.
timeoutMsOptional positive integer in milliseconds, capped by the time left for evaluation.

The call is synchronous: the script waits until the run ends. Only one host call runs at a time.

The run starts in request.cwd, without a terminal, in a new POSIX session. A POSIX session is the operating system’s group of process groups, which setsid makes. It is not a Ravel session. It receives the environment of a managed process. Ravel does not restrict its filesystem access, as chapter 2 states. The arguments that the script supplies select the sandbox of the harness, such as codex exec --sandbox read-only.

The script supplies every argument and chooses where the prompt goes. Ravel builds no argument that is specific to a harness.

The returned map describes the completed run:

FieldValue
statusexited, signalled, timed_out, output_limit or unavailable.
exitCodeAn integer or ().
signalA signal name or ().
stdout, stderrCaptured text. Invalid UTF-8 becomes the replacement character.
resultThe value sent by the run with end-session, or ().
elapsedMsElapsed milliseconds.
error(), or a map with code and message for an unavailable run.

A run can finish by natural exit and return standard output to the script. It does not have to call end-session. If it does, that result belongs only to this run. It cannot complete the outer session. The final managed process later receives a different result channel.

An unavailable run reports unknown_harness, harness_not_found, harness_not_executable or harness_launch_failed and consumes no run budget. Each run that starts consumes one. Each output stream has a 1 MiB bound. A per-run timeout or output overflow stops the run and returns its status. A cleanup failure ends evaluation as harness_cleanup_failed, exit status 5.

Can a harness run start a Ravel session of its own? No. Ravel puts the marker RAVEL_CONFIG_RUN in the environment of each harness run, and each child of the run inherits it. start-session finds the marker and refuses as config_reentry_refused, before it reads the settings or a configuration script. Thus, a harness run cannot start a second evaluation inside the first.

Do you need the route of another kind during evaluation? Call that route’s function in your script directly. The final managed process never receives the marker, so a session that the final harness nests stays allowed.

The marker does not protect against code that removes it. A descendant that leaves the process group is outside group cleanup.

Ask a model through Claude Code

Do you want an LLM in Claude Code to help your configuration script choose? This section gives the recipe. An LLM call is a harness run that asks a model a question. Claude Code runs the call under your own sign-in, so the call can use your subscription. Ravel stores no model credential.

The script reads the answer and decides what it means. A model can give an unexpected answer, so the script asks for structured output. Structured output is an answer in JSON, in a shape that a JSON Schema describes. The script then checks the answer against the same schema with ravel::json_check. The fake below uses the same arguments as a real call, but it returns a fixed answer.

       remedy: "Check the harness and its output." }

fn select(request, context) {
    let schema = #{ type: "object",
                    properties: #{ prime: #{ type: "string", enum: ["yes", "no"] } },
                    required: ["prime"], additionalProperties: false };
    let run = ravel::run_harness(#{

Select Claude Code or Codex for the caller’s work

The harness runs above answer a question for the configuration script. Usually, you also want a harness to do the caller’s work, such as the review of chapter 1. Then the harness is the managed process: the program that Ravel starts and supervises for the session. An interactive harness waits for more input when its LLM completes the task. Thus, the caller’s prompt tells the LLM to run ravel end-session RESULT, and that command ends the session.

A final interactive harness is the managed process, not a harness run. Select its program and args directly. This selection needs no harnesses entry or harness-run budget.

The caller’s prompt gives the complete task. In the review of chapter 1, the prompt named the two files to review. It gave two permitted results, approved and changes-needed, and the condition for each result. It told the LLM to send the result with ravel end-session. The orchestrator then acted on each result.

These values are the caller’s convention. Ravel assigns them no meaning, and it returns the value unchanged after cleanup.

Your script passes request.prompt to the harness. With skill delivery enabled, that field also holds discovery instructions before the caller’s unchanged text. request.originalPrompt always holds only the caller’s text. Ravel does not add the instruction to end the session.

How does ravel end-session find the session? Ravel puts the path of the session’s result file in the RAVEL_EXIT_FILE environment variable of the harness. The harness runs each command of the LLM in a child process, for example a shell. Each child inherits RAVEL_EXIT_FILE from its parent unless the parent changes it. Thus, ravel end-session finds the path in its own environment. Chapter 1, “How end-session finds its session”, shows the paths of a real nested run.

Review your configuration script before real use

In short, the caller asks with a kind and a prompt. Ravel evaluates your Rhai configuration script in the Rhai worker, a second copy of the ravel executable. The script can read measured files, read granted environment variables and run harnesses through ravel:: functions. Each of these host capabilities asks the Ravel CLI to do the work, within the limits of your settings. Then select returns a selection or a refusal.

After a selection, Ravel reaps the worker and starts the selected program as the managed process. Ravel writes the routing notice on the caller’s standard error. The text notice comes before the start of the program, and the JSON notice follows the supervision attempt. The program sends a result with ravel end-session, as the caller’s prompt tells it. After cleanup, that result becomes the result of ravel start-session, unchanged. The caller gives the result its meaning.
